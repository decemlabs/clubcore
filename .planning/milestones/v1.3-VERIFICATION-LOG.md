## Regressions

### REG-29-01 — admin-web http mode dev login fails (CORS + no Vite proxy)

**Severity:** blocker
**Disposition:** fixed_in_aea55f3 (during Plan 29-03)
**Discovered:** Plan 29-03 Task 3, sceanrio #3 first attempt — operator received "Ошибка соединения. Проверьте сеть и попробуйте снова." when clicking Login.

**Root cause:** Two-fer:
1. Backend has no CORSMiddleware — `OPTIONS /api/v1/auth/login` returns 405 Method Not Allowed, blocking browser preflight on cross-origin POST.
2. `apps/admin-web/vite.config.ts` had no `server.proxy` entry, so admin-web at `:5173` was making real cross-origin requests to backend at `:8000`.
3. Cookies set by backend (`SameSite=lax`) would not be sent on subsequent cross-origin requests anyway.

**Fix (commit aea55f3):** Added Vite `server.proxy` for `/api` → `http://localhost:8000` and a gitignored `apps/admin-web/.env.development.local` setting `VITE_API_BASE_URL=` (empty), so the admin-web fetch layer issues relative paths that Vite proxies. Same-origin under `:5173` → no CORS preflight, cookies survive.

**Production impact:** None. Vite `server.proxy` only runs in `vite dev`; production builds assume a reverse proxy (nginx) that already provides same-origin between admin-web and backend.

**Re-verification:** After commit, login succeeded (200 + Set-Cookie observed in operator browser). Scenario #3 then proceeded.

**v1.4 follow-up consideration (informational, not blocking):** if admin-web ever ships as a separate origin (e.g. a CDN), CORSMiddleware + `SameSite=none; Secure` cookies would become necessary. For v1.3's single-origin topology this is not required.
