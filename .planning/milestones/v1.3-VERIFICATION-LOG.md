## Regressions

### REG-29-04 — `run_expiring_cron_once.py` misses eager FK model imports

**Severity:** minor (verification-tooling only)
**Disposition:** fixed_in_1dfc7a8 (during Plan 29-04)
**Discovered:** Plan 29-04 wave 3 step 7 — first 7d cron firing dispatched the Telegram DM but crashed at `INSERT INTO audit_log` with `NoReferencedTableError: Foreign key associated with column 'audit_log.actor_user_id' could not find table 'users'`.

**Root cause:** SQLAlchemy resolves FK references lazily at first flush. The cron callable (`send_expiring_notifications`) only transitively imports its own module's models, not `users` / `clients` / `memberships` / `visits` FK targets. When the audit row commits, SQLAlchemy can't find the referenced tables in `Base.metadata`. This is **runner-only**; the real production worker (the ARQ container path through `WorkerSettings`) imports `app.workers` which transitively imports everything, so this bug is invisible in prod.

**Fix (commit 1dfc7a8):** Eager-imported four `models` modules (`auth`, `clients`, `memberships`, `visits`) at the top of `run_expiring_cron_once.py` so all FK target tables are registered before `WorkerSettings.on_startup(ctx)` opens a session. `# noqa: F401 — eager FK reg` markers explain the unused imports.

**Production impact:** None — only the operator-only verification script was affected. ARQ-managed prod path is unchanged.

**Verification:** ruff clean, mypy --strict clean. Re-run of cron three times after fix: each firing returned `count=1` with no errors, three Telegram DMs delivered, three `audit_log` + `membership_notifications` rows committed cleanly.

### REG-29-03 — telegram-bot worker missing Protocol slot registrations (production blocker)

**Severity:** blocker
**Disposition:** fixed_in_f3cd01f (during Plan 29-03)
**Discovered:** Plan 29-03 Task 3, scenario #6 — bot answered "У вас нет активного абонемента" despite correct DB linkage (`clients.telegram_user_id = 6884162810`, active membership with valid `end_date`).

**Root cause:** Bot worker is a separate process from FastAPI's app (`app.workers.telegram_bot` vs `app.main:create_app`). Protocol slot resolvers in `core.dependencies` are registered only inside `create_app()`, so the bot worker process leaves them as `None`. Both `resolve_client_by_telegram_user_id` and `resolve_active_membership_by_client` return `None` for every lookup, and the visits service throws `ClientNotLinkedError` (or `NoActiveMembershipError`) — both of which the bot maps to the oracle-safe shared DM "У вас нет активного абонемента" (D-20-9 anti-enumeration design).

**Impact in production:** /checkin is **dead** — every Telegram self-checkin would answer "no active membership" regardless of the user's actual state. NTF-COPY-01 strings + bot routing all built, but the resolver chain breaks at the very first hop.

**Fix (commit f3cd01f):** Added two `register_*` calls inside `apps/backend/app/workers/telegram_bot.py:main()` to match `app.main.create_app()`:
- `register_client_by_telegram_resolver(clients_service.resolve_client_by_telegram_user_id)`
- `register_active_membership_resolver(memberships_service.resolve_active_membership_by_client)`

Two-stage discovery: the first fix attempt only registered the client-resolver; bot then started returning `visit_rejected_no_membership` (the second resolver was still unregistered). Final fix covers both. User-loader is auth-only and not on the bot path — left unregistered intentionally.

**Validation:** ruff clean, mypy --strict no issues, lint-imports 3 kept / 0 broken. Bot worker image rebuilt + force-recreated. Re-verified end-to-end: sub-tests 6a (N=7) and 6b (last-day) both received verbatim D-22-11 locked Russian copy.

**Lesson:** This bug would have shipped to prod silently without `/gsd-execute-phase 29 --wave 2` running the human-smoke against a real Telegram sandbox. Strong vindication of the DEBT-04 verification phase as a milestone close gate.

### REG-29-01 — admin-web http mode dev login fails (CORS + no Vite proxy)

**Severity:** blocker
**Disposition:** fixed_in_aea55f3 (during Plan 29-03)
**Discovered:** Plan 29-03 Task 3, sceanrio #3 first attempt — operator received "Ошибка соединения. Проверьте сеть и попробуйте снова." when clicking Login.

**Root cause:** Two-fer:
1. Backend has no CORSMiddleware — `OPTIONS /api/v1/auth/login` returns 405 Method Not Allowed, blocking browser preflight on cross-origin POST.
2. `apps/admin-web/vite.config.ts` had no `server.proxy` entry, so admin-web at `:5173` was making real cross-origin requests to backend at `:8000`.
3. Cookies set by backend (`SameSite=lax`) would not be sent on subsequent cross-origin requests anyway.

**Fix (commit aea55f3):** Added Vite `server.proxy` for `/api` → `http://localhost:8000` and a gitignored `apps/admin-web/.env.development.local` setting `VITE_API_BASE_URL=` (empty), so the admin-web fetch layer issues relative paths that Vite proxies. Same-origin under `:5173` → no CORS preflight, cookies survive.

**Production impact:** None. Vite `server.proxy` only runs in `vite dev`; production builds assume a reverse proxy (nginx) that already provides same-origin between admin-web and backend.

**Re-verification:** After commit, login succeeded (200 + Set-Cookie observed in operator browser). Scenario #3 then proceeded.

**v1.4 follow-up consideration (informational, not blocking):** if admin-web ever ships as a separate origin (e.g. a CDN), CORSMiddleware + `SameSite=none; Secure` cookies would become necessary. For v1.3's single-origin topology this is not required.
