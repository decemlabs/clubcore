## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| reception staff → check-in API | clientId from the picker crosses to POST /api/v1/visits; server derives membership/gymDate/channel/checkedInBy. |
| check-in anti-fraud chain | 3 server-enforced 409s gate the write; UI must surface, never bypass. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-103-02-409CHAIN | Tampering | CheckInModal / useCheckIn | mitigate | The 3 distinct 409s (outside_gym_hours / no_active_membership / duplicate_checkin) are rendered as distinct read-only Callouts; modal stays open; no auto-retry, no client-side override. duplicate_checkin is DB-UNIQUE 1/day — UI never re-submits to bypass. |
| T-103-02-OPTIMISTIC | Tampering | useCheckIn optimistic row | mitigate | Optimistic row is purely a cache illusion (`_optimistic:true`); on ANY error it is rolled back via onError snapshot restore, so a rejected check-in never persists a fake visit in the UI. |
| T-103-02-PII | Information Disclosure | VisitsList / CheckInModal error states | mitigate | 409/error Callouts use fixed Russian copy from the UI-SPEC — no raw backend message, stack, clientId, or PII is rendered in error states (generic fallback for non-409). |
| T-103-02-CHECKIN-RBAC | Elevation of Privilege | «Чек-ин» button | accept | Check-in is reception+owner by design (can(role,'check_in','visits')===true for both); not an owner-only action. Backend enforces CHECK_IN permission authoritatively. |
| T-103-SC | Tampering | npm installs | mitigate | No new packages. All UI reuses existing AdaptiveModal/fields primitives + lucide icons. |
</threat_model>
