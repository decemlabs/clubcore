<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| login form input → /api/v1/auth/login | untrusted credentials cross here |
| /me probe → app shell render | authorization decision (render app vs redirect to login) |
| backend error envelope → UI message | error text must not leak which credential field was wrong |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-100-07 | Information Disclosure (user enumeration) | LoginForm `invalid_credentials` handling | mitigate | A 401 `invalid_credentials` renders ONE generic banner «Неверный email или пароль.» with no field-level `aria-invalid` — the UI never reveals which field was wrong (anti-oracle, mirrors backend's lowercased-email/uniform-401 design). |
| T-100-08 | Spoofing (unauthenticated access) | RequireAuth guard | mitigate | App routes render only after `useSession()`/`/auth/me` succeeds; an errored probe (after the transport's refresh attempt) redirects to `/login` — no app data renders for an unauthenticated principal. UI gating is defense-in-depth; the backend remains the authority (every endpoint enforces auth). |
| T-100-09 | Information Disclosure (stale-data on expiry) | mid-session 401 redirect | mitigate | `session_expired` → `removeQueries(authKeys.me)` + `Navigate('/login?state=expired')`; the session query cache is cleared so no stale role/identity persists; existing ExpiredScreen surfaces without a crash or redirect loop (`_redirecting` flag from plan 100-02). |
| T-100-10 | Tampering (weak password on reset) | usePasswordResetConfirm | mitigate | Client enforces `newPassword.min(12)`; the backend re-enforces and a `weak_password` 422 maps to an inline field error — the client never bypasses the server check. |
</threat_model>
