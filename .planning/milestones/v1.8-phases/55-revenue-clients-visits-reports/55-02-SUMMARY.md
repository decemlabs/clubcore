# Phase 55 Plan 02: Clients + Visits Reports Summary

Clients snapshot and visits composite report endpoints end-to-end — active/expiring/new client counters (CLR-01..04) and daily/hourly/averagePerDay visits (VIS-R-01..04) — both owner-only with reception 403.

## What Was Built

### Task 1: Repository readers + service functions + routes

**repository.py** (5 new readers appended below `fetch_revenue_buckets`):
- `fetch_active_memberships_count(session)` — `memberships.status='active' JOIN clients WHERE deleted_at IS NULL`, `.mappings().one()`, returns `int` (CLR-01)
- `fetch_expiring_memberships_count(session, within)` — active memberships with `end_date BETWEEN now()::date AND now()::date + CAST(:within AS integer)`, live clients only (CLR-02)
- `fetch_new_clients_count(session, from_date, to_date)` — `clients WHERE deleted_at IS NULL AND (created_at AT TIME ZONE 'Europe/Moscow')::date BETWEEN :from_date AND :to_date` (CLR-03/04)
- `fetch_visits_daily(session, from_date, to_date)` — `GROUP BY gym_date ORDER BY gym_date`, filter `gym_date BETWEEN` (VIS-R-01/04, no secondary TZ conversion)
- `fetch_visits_hourly(session, from_date, to_date)` — `EXTRACT(HOUR FROM checked_in_at AT TIME ZONE 'Europe/Moscow')::int AS hour`, `GROUP BY hour ORDER BY hour` (VIS-R-02)

**service.py** (2 new functions):
- `get_clients_report(session, query)` — validates range (D-05/D-06), validates `within` 1..30 (D-07), gathers 3 counters, returns `ClientsReportResponse(active_count, expiring_count, new_clients_count, within_days)`. Read-only.
- `get_visits_report(session, query)` — validates range, fetches daily+hourly, computes `calendar_days = (to - from).days + 1`, `average_per_day = round(total / calendar_days, 2)`. Returns composite `VisitsReportResponse`. Read-only.

**router.py** (2 new routes):
- `GET /clients` — `ClientsReportQuery`, `ClientsReportResponse`, same `require_permission(VIEW, REPORTS)` RBAC gate
- `GET /visits` — `VisitsReportQuery`, `VisitsReportResponse`, same RBAC gate

## Key Decisions

### D-10: averagePerDay as 2-dp float

Decision: `round(total / calendar_days, 2)` per researcher discretion noted in the plan. Frontend owns formatting. The denominator is always the full calendar range `(to - from).days + 1`, not days-with-visits — D-08 sparse buckets policy applies to the list, not the average.

### D-07: within validation in service layer (not Pydantic ge/le)

`within` is validated in `service.get_clients_report()` with an explicit `ValidationAppError` for consistent 422 codes (same error code pattern as `ReportRangeTooLargeError`). The schema stores `within: int = 7` without constraints — validation in service layer for consistent DX.

### No Alembic migration (D-13 default)

Clients/visits aggregate queries run on existing indexes:
- `ix_memberships_client_id_status_end_date` covers the active/expiring queries
- `ix_visits_client_id_checked_in_at` covers the visit range queries
No new migration created per D-13 default.

### CAST(:within AS integer) required for asyncpg

asyncpg raises `AmbiguousFunctionError: operator is not unique: date + unknown` when using `:name` bind params in a `date + N` expression. The `::int` cast after a bind param (`:within::int`) causes a `PostgresSyntaxError` in asyncpg's prepared statement mode. The fix is `CAST(:within AS integer)` which provides an explicit type to Postgres before the date arithmetic.

### Two distinct clients per-day visit tests

The `uq_visits_client_id_gym_date` unique constraint prevents the same client from visiting twice on the same MSK date. For the "same-day count=2" test, two distinct clients are created to produce two visit rows with the same `gym_date`.
