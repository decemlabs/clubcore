### Memberships — Freeze (MEM-FRZ)

- [x] **MEM-FRZ-01**: Alembic migration `0007_freeze.py` adds `freeze_days_limit` (INT NOT NULL CHECK > 0) column to `membership_plans`; existing rows backfilled with `14` then default dropped; field is **immutable post-creation** (PATCH 422 if attempted, mirrors `duration_days`); response/request schemas include `freezeDaysLimit`.
- [x] **MEM-FRZ-02**: Same migration creates `membership_freeze_periods` table: `id` (UUID PK gen_random_uuid()), `membership_id` (UUID NOT NULL FK memberships.id ON DELETE RESTRICT), `started_at` (TIMESTAMPTZ NOT NULL), `ended_at` (TIMESTAMPTZ NULL while active), `started_by` (UUID NOT NULL FK users.id), `ended_by` (UUID NULL FK users.id ON DELETE SET NULL), `created_at` (TIMESTAMPTZ NOT NULL DEFAULT now()). Partial unique index on `(membership_id) WHERE ended_at IS NULL` so only one active freeze period per membership.
- [x] **MEM-FRZ-03**: Same migration adds `freeze_days_limit_snapshot` (INT NOT NULL) to `memberships`; existing rows backfilled from current plan (or `14` if plan archived); new sales snapshot from plan at sale time (mirrors price/duration snapshot semantics from v1.2 MEM-01).
- [x] **MEM-FRZ-04**: `service.freeze_membership(session, membership_id, actor)` — only when `status='active'`; computes `days_used_so_far + projected_period <= freeze_days_limit_snapshot` precondition (preventive); inserts active `membership_freeze_periods` row; transitions membership to `status='frozen'`. 409 `invalid_transition` for non-active source; 409 `freeze_limit_exceeded` if no days remaining.
- [x] **MEM-FRZ-05**: `service.unfreeze_membership(session, membership_id, actor)` — only when `status='frozen'`; closes the open freeze period (`ended_at = now()`, `ended_by = actor.id`); recomputes `end_date += ceil((ended_at - started_at) in Europe/Moscow days)`; transitions back to `status='active'`. Half-day rounds up so client never loses partial days.
- [x] **MEM-FRZ-06**: Resolver (MEM-04 + DEBT-01) treats `frozen` as **not active**; Telegram `/checkin` and reception check-in return `no_active_membership` 409 for frozen memberships (no oracle leak — same DM as stranger / expired-membership).
- [x] **MEM-FRZ-07**: `service.cancel_membership` allows `frozen → cancelled` (owner-only path); closes any open freeze period without extending `end_date` (cancellation supersedes the freeze); audit emits `membership_unfrozen` then `membership_cancelled` in the same transaction.
- [x] **MEM-FRZ-EP-01**: `POST /api/v1/memberships/{id}/freeze` (CSRF) — `(CREATE, MEMBERSHIPS)` → reception+owner; empty body; returns 200 with updated membership including `currentFreezePeriod` field.
- [x] **MEM-FRZ-EP-02**: `POST /api/v1/memberships/{id}/unfreeze` (CSRF) — `(CREATE, MEMBERSHIPS)` → reception+owner; empty body; returns 200 with updated membership (new `endDate`, `freezeDaysUsed`, `freezeDaysRemaining`).
- [x] **MEM-FRZ-EP-03**: `GET /api/v1/memberships/{id}` and list responses include `freezeDaysLimitSnapshot`, `freezeDaysUsed` (sum of completed periods + ongoing if `frozen`, in Europe/Moscow days), `freezeDaysRemaining`, `currentFreezePeriod` (object with `startedAt`/`startedBy` or null).
- [x] **MEM-FRZ-AUDIT-01**: `audit.emit("membership_frozen", actor, freeze_period_id, started_at)` on freeze; `audit.emit("membership_unfrozen", actor, freeze_period_id, days_added)` on unfreeze.
- [x] **MEM-FRZ-TEST-01**: integration test — full freeze cycle: sell 30-day membership → freeze for 5 days → unfreeze → `end_date` shifted exactly 5 days forward; total `freeze_days_used = 5`.
- [x] **MEM-FRZ-TEST-02**: integration test — second freeze attempt with cumulative days exceeding `freeze_days_limit_snapshot` returns 409 `freeze_limit_exceeded`.
- [x] **MEM-FRZ-TEST-03**: race test — concurrent freeze on same membership: partial unique index `WHERE ended_at IS NULL` rejects the second insert with IntegrityError → service returns 409 `already_frozen`.

### Memberships — Renewal (MEM-REN)

- [x] **MEM-REN-01**: Migration `0007` adds `previous_membership_id` (UUID NULL FK memberships.id ON DELETE SET NULL) to `memberships` for renewal audit chain.
- [x] **MEM-REN-02**: `service.renew_membership(session, source_membership_id, actor)` — reads **current** plan from `source.plan_id` (404 `plan_not_found` if hard-deleted, 409 `plan_archived` if `deleted_at IS NOT NULL`); snapshots from current plan (`name_snapshot`, `duration_days_snapshot`, `price_kopecks_snapshot`, `freeze_days_limit_snapshot`); `start_date = source.end_date + 1` (Europe/Moscow); `end_date = start_date + duration_days_snapshot - 1`; `status='active'`; `previous_membership_id = source.id`. Allowed source statuses: `active`, `frozen`, `expired` (NOT `cancelled` — 409 `cannot_renew_cancelled`).
- [x] **MEM-REN-03**: Resolver (MEM-04) tiebreak rule extended: when client has multiple `status='active' AND end_date >= today` rows, prefer the one with **lower** `start_date` (the currently-running one), then `created_at DESC`. Covers the "renewal sold while active still has days" case so `/checkin` keeps using the current membership until its `end_date`, then the renewal naturally takes over.
- [x] **MEM-REN-04**: Renewal of an `expired` source: `start_date = today (Europe/Moscow)` (not `source.end_date + 1`) so the new membership begins immediately rather than retroactively; documented in service docstring; `audit.emit` payload includes `start_date_strategy='from_today_expired_source'` for traceability.
- [x] **MEM-REN-EP-01**: `POST /api/v1/memberships/{id}/renew` (CSRF) — `(CREATE, MEMBERSHIPS)` → reception+owner; empty body; returns 201 with the new follow-up membership row.
- [x] **MEM-REN-AUDIT-01**: `audit.emit("membership_renewed", actor, source_membership_id, new_membership_id, source_plan_id, current_price_kopecks, start_date_strategy)`.
- [x] **MEM-REN-TEST-01**: integration test — renewal of active membership creates follow-up with `start_date = source.end_date + 1`, snapshots from current plan; resolver returns source until `end_date`, then renewal.
- [x] **MEM-REN-TEST-02**: integration test — plan price changed between sale and renewal: renewal snapshot reflects **current** price, not source snapshot.
- [x] **MEM-REN-TEST-03**: integration test — renewal of archived plan returns 409 `plan_archived`; renewal of cancelled source returns 409 `cannot_renew_cancelled`.
- [x] **MEM-REN-TEST-04**: integration test — renewal of expired membership: `start_date = today`, not `end_date + 1` of expired source.

### Notifications — Expiring-soon (NTF)

- [x] **NTF-01**: Alembic migration `0010_notifications.py` creates `membership_notifications` table: `id` (UUID PK), `membership_id` (UUID NOT NULL FK memberships.id ON DELETE CASCADE), `kind` (VARCHAR NOT NULL CHECK IN ('expiring_7d','expiring_3d','expiring_1d')), `sent_at` (TIMESTAMPTZ NOT NULL DEFAULT now()), `telegram_chat_id` (BIGINT NOT NULL), `created_at`. UNIQUE INDEX on `(membership_id, kind)` for cron idempotency.
- [x] **NTF-02**: `app/workers/scheduled/send_expiring_notifications.py` exposes `async def send_expiring_notifications(ctx) -> int`; selects memberships matching `status='active' AND end_date IN (today+1, today+3, today+7) AND client.telegram_chat_id IS NOT NULL AND NOT EXISTS (membership_notification of matching kind)`; sends DM via `telegram.bot_api.send_message`; inserts `membership_notifications` row only on successful send (failure → WARNING log, no row → retry next tick).
- [x] **NTF-03**: `app.workers.WorkerSettings.cron_jobs` adds `cron(send_expiring_notifications, hour=3, minute=15, unique=True, keep_result=60)` (06:15 Europe/Moscow with container `TZ=UTC`, after `expire_memberships` at 06:05).
- [x] **NTF-04**: Frozen, cancelled, and expired memberships skipped (filter `status='active'` in select); also skipped when client has no Telegram link (`telegram_chat_id IS NULL`) or when client soft-deleted (`clients.deleted_at IS NOT NULL`).
- [x] **NTF-05**: Send failure (network, rate-limit, blocked DM, deactivated chat) — `structlog.warning("expiring_notification_send_failed", ...)` with reason; Telegram error 403 (bot blocked) does NOT permanently mark this kind as sent (so a re-linked client still gets future pings); the idempotency table is the single source of truth.
- [x] **NTF-06**: `audit.emit("expiring_notification_sent_<kind>", actor=None, membership_id, client_id, telegram_chat_id, kind)` per successful send (3 locked event names, see INFRA-15).
- [x] **NTF-COPY-01**: `app/integrations/telegram/copy.py` exposes 6 locked Russian DM strings: `EXPIRING_7D_VARIANT_A/B`, `EXPIRING_3D_VARIANT_A/B`, `EXPIRING_1D_VARIANT_A/B` (selected by `client_id` hash for stable per-client variant — anti-oracle pattern from v1.2 D-5); each contains `end_date` formatted via Europe/Moscow date-fns `ru` locale; owner sign-off recorded in PROJECT.md Key Decisions for v1.3.
- [x] **NTF-TEST-01**: integration test — membership expiring in 7 days + linked Telegram → DM sent, idempotent on second cron run (no duplicate row, no second send).
- [x] **NTF-TEST-02**: integration test — frozen membership at `end_date - 7` does NOT trigger notification.
- [x] **NTF-TEST-03**: integration test — Telegram send raises 403 → no `membership_notifications` row inserted → next tick retries; once succeeds, row inserted; second tick same day is a no-op.
