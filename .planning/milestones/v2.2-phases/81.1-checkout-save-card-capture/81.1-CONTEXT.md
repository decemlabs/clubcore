# Phase 81.1: Checkout Save-Card Capture (audit gap closure) - Context

**Gathered:** 2026-06-03
**Status:** Ready for planning
**Source:** v2.2 milestone audit — PAYM-01 PWA-capture gap

<domain>
## Phase Boundary

PWA-only closure of the v2.2 audit gap: the backend already saves a card when a checkout request
carries `save_payment_method=true` (Phase 79 — webhook step 8.5), and the CardSheet manages a saved
card (Phase 81 PAYM-05), but no PWA surface ever sends the flag, so a card can never be linked
through the UI. This phase threads a `savePaymentMethod` opt-in from `CheckoutSheet` through the two
checkout mutation hooks into the request body. NO backend change, NO migration, NO contract change
(`savePaymentMethod` is already in the frozen openapi.json/schema.d.ts from Phase 79).

</domain>

<decisions>
## Implementation Decisions

### Save-card opt-in
- Add a `savePaymentMethod?: boolean` arg to `useClientCheckoutMembership` and `useClientCheckoutPtPackage` (`apps/client-pwa/src/lib/clientQueries.ts`, ~lines 590 + 616); when true, include `savePaymentMethod: true` in the request `body` alongside the existing optional `promoCode`. Default false → byte-identical body to today (no `savePaymentMethod` key) when off.
- Add a save-card opt-in control to `CheckoutSheet.jsx` (e.g. a checkbox "Сохранить карту для будущих оплат"); pass its state into both `launchCheckout` mutation calls (membership ~line 230, PT ~line 235).
- Mere card storage is NOT a recurring charge — no ФЗ-376 consent is required at checkout (consent is only for autopay enable, handled in the CardSheet). The opt-in copy should make clear the card is saved for convenience, not auto-charged.

### Contract stability
- Do NOT edit openapi.json or schema.d.ts by hand. After the change, re-run `uv run python -m scripts.export_openapi` + `pnpm --filter @clubcore/api-client codegen` and confirm `git diff --exit-code` is clean on both (the field already exists in the contract → zero diff expected).

### Claude's Discretion
- Exact checkbox placement/copy in CheckoutSheet, the arg name plumbing, and test structure — follow existing CheckoutSheet + clientQueries conventions.

</decisions>

<specifics>
## Specific Ideas

- Default OFF; when OFF the request body must be byte-identical to current behavior (no `savePaymentMethod` key) to avoid surprising the backend / contract.
- Saving a card ≠ enabling autopay; no ФЗ-376 consent gate at checkout.
- The live card-save round-trip remains OPERATOR-PENDING (no live YooKassa) — this phase wires the UI + flag; the E2E payment leg is verified by mocked tests + deferred for live.

</specifics>
