# Phase 999.3: client-pwa Home — newbie (no-subscription) state - Context

**Gathered:** 2026-05-31
**Status:** Ready for planning

<domain>
## Phase Boundary

`apps/client-pwa` `HomeScreen.jsx` renders a dedicated onboarding ("newbie") Home state for an authenticated client with **no active subscription**, matching the approved mockup (`home-newbie.html`): hero card with "Выбрать абонемент" CTA, onboarding strip (4 steps + progress), "Первый визит — бесплатно" nudge, locked QR placeholder, and quick tiles (Тренеры / Чат). The existing active-subscription Home variants (classic / qr-hero / minimal) are preserved and selected by subscription status.

**Scope change vs original ROADMAP entry:** The phase is **no longer frontend-only.** Distinguishing a true newbie from a lapsed (expired) member requires a new backend field on `/client/home` (decision D-01). The visual/interaction contract is locked by `999.3-UI-SPEC.md`; this discussion captures the **logic/wiring** decisions the UI-SPEC left open.

</domain>

<decisions>
## Implementation Decisions

### Newbie vs lapsed gate (render trigger)
- **D-01:** Distinguish a true newbie from a lapsed (expired) member via a new **`membershipState` enum** on the `/client/home` response: `'active' | 'newbie' | 'lapsed'`. The PWA renders `HomeNewbie` **only** when `membershipState === 'newbie'`. This requires a small backend addition — the phase is therefore **not** frontend-only.
  - Rejected: "any `membership === null` = newbie" (a lapsed member would wrongly see onboarding copy "Аккаунт создан / Остался один шаг"); `hasEverSubscribed` boolean (logic split across two fields); client-side heuristic from past bookings (fragile, false positives).
- **D-02:** **`lapsed`** keeps the existing expired/danger treatment (`ExpiredAlert` + "Продлить" CTA in the current variants). **`active`** keeps the existing `tweaks.homeVariant` dispatch (classic / qr-hero / minimal) unchanged. Only `newbie` routes to `HomeNewbie`.
- **D-03:** The backend `membershipState` change is **folded into Phase 999.3 scope** (not a separate prerequisite mini-phase). ROADMAP scope note for 999.3 must be updated to reflect the backend addition.

### Dev-panel previewability
- **D-04:** **No dev-panel toggle** for the newbie state. The newbie Home is purely data-driven off the real `membershipState` from `/client/home`. To preview/demo, use a real (or seeded) client account whose `membershipState` is `'newbie'`. The dead `subState` tweak is NOT revived for this purpose, and no `homeVariant: 'newbie'` option is added.

### Onboarding strip step states (live, not hardcoded)
- **D-05:** All 4 onboarding steps reflect **live data** (not the hardcoded mockup states). Step completion rules:
  - **Step 1 «Аккаунт»** — always `done`.
  - **Step 2 «Абонемент»** — always `pending` in the newbie state (by definition `membershipState === 'newbie'` means no active subscription).
  - **Step 3 «Профиль»** — `done` if **any** of the profile fields (фото / рост / вес) is filled, read from `/client/me`.
  - **Step 4 «Первый визит»** — `done` if the client has **any** booking (upcoming or past), via existing client bookings read endpoint(s).
- **D-06:** The progress bar fill, the count badge ("N / 4"), and the strip title ("Ещё N шагов до полного старта") are computed **dynamically** from the live done-count — they are NOT the hardcoded "1 / 4" / 25% / "Ещё 3 шага" values shown in `999.3-UI-SPEC.md`. **This overrides the UI-SPEC's static onboarding values.** All UI-SPEC visual tokens (spacing, color, typography, step state classes `.step.done`/`.step.next`/`.step`) still apply; only the source of the step/progress data changes from static to live.

### Claude's Discretion
- Exact derivation of "next" step styling (`.step.next`) when multiple steps are pending — follow UI-SPEC's visual rule (current actionable step gets dark border/icon); planner/executor choose which pending step is "next" (Step 2 Абонемент is the natural next action).
- Field-presence checks for profile (what counts as "filled" for фото/рост/вес) — use the real `/client/me` shape; planner verifies field names.
- Whether "any booking" for Step 4 needs an extra query beyond `homeData.nextBooking` (past bookings) — researcher to confirm the available client bookings endpoint.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `HomeScreen.jsx` `toSubInfo(membership)` (line ~27) — current adapter; `membership === null` currently maps to a danger/empty sub. New gate keys on `membershipState`, not on `toSubInfo`.
- `GymStatusPill`, `QuickTile`, `Icon`, `PullToRefresh`, `LoadError`, `.btn`/`.btn-accent`/`.card`/`.press` classes, `progress-track`/`progress-fill`, `fade-up`/`pulse-soft` keyframes — all reused per UI-SPEC.
- `useClientMe()` — source for Step 3 (Профиль) live state.
- `homeData.nextBooking` — partial source for Step 4; researcher to confirm whether a past-bookings query is also needed for "any booking".

### Established Patterns
- Home render currently dispatches on `tweaks.homeVariant` after `isLoading`/`isError` guards. New `membershipState` gate runs **before** the variant dispatch (per UI-SPEC Interaction Contract): `newbie → HomeNewbie`; `lapsed`/`active` → existing flow.
- Sub card and `subState` dev tweak are now API-data-driven; `subState` is effectively dead and stays so (D-04).
- camelCase API serialization (`daysUntilEnd`, `planNameSnapshot`, `expiringSoon`) — `membershipState` follows the same camelCase convention. Existing adapter tests (`HomeScreen.adapters.test.jsx`) assert the camelCase contract.

### Integration Points
- **Backend:** `/api/v1/client/home` response must add `membershipState: 'active' | 'newbie' | 'lapsed'`. Server determines `newbie` (never subscribed) vs `lapsed` (had a subscription, now expired) vs `active`.
- **Frontend:** `HomeData` type in `clientQueries.ts` gains `membershipState`; `HomeScreen` adds the gate + `HomeNewbie`/`HeroNewbie`/`OnboardingStrip`/`FirstVisitNudge`/`QrPlaceholder` per UI-SPEC.

</code_context>

<specifics>
## Specific Ideas

- User explicitly wants honest, data-reflecting onboarding steps over a static "looks-done" mockup (D-05/D-06).
- User accepts the backend addition to get correct newbie/lapsed semantics rather than shipping a copy mismatch for lapsed members (D-01).

</specifics>

<deferred>
## Deferred Ideas

- **Hero meta chips live data** — "3 тарифа · от 3 500 ₽/мес" stay hardcoded static strings (UI-SPEC Impl Note 5). Wiring them to a live catalog count/min-price query is deferred to a future phase.
- **Onboarding dismiss persistence** — dismissal is session-scoped React state only (UI-SPEC Impl Note 7). Persisting dismissal across sessions (localStorage / backend flag) is deferred.
- **Richer lapsed-member experience** — beyond keeping the existing expired screen, a dedicated win-back/re-onboarding state for lapsed members is out of scope for 999.3.

None of these are blocked — they are intentionally out of this phase's boundary.

</deferred>
