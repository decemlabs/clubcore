## Accepted Risks Log

### T-999.3-03 — Information Disclosure: new `membershipState` schema field

**Accepted at:** plan time (999.3-01-PLAN.md threat register)
**Rationale:** `membershipState` is a low-sensitivity three-value enum (`active` | `newbie` | `lapsed`) that describes only the requesting client's own membership history. It exposes no other client's data, no economic values, no PII, and no internal IDs. Field-projection discipline (D-69-05) is preserved — the field is additive to `ClientHomeResponse` and does not relax any existing projection guard.
**Residual risk:** None identified at ASVS Level 1.

## Verification Detail

### T-999.3-01 — IDOR bind discipline on `client_has_any_membership`

Mitigation plan required: mandatory `:client_id` bind cast to `str`; EXISTS query scoped to the authenticated principal's `client_id`; no request param feeds the query; coverage by existing IDOR sweep.

Evidence found:

1. **Bind param with UUID cast** — `repository.py:65-75`:
   ```python
   row = (await session.execute(
       text("SELECT EXISTS(SELECT 1 FROM memberships WHERE client_id = :client_id) AS ever"),
       {"client_id": str(client_id)},
   )).mappings().one()
   ```
   The `:client_id` placeholder is bound from the `UUID` argument cast to `str` — no raw string interpolation, no request-supplied value.

2. **No ORM import of Membership** — `grep "from app.modules.memberships" repository.py` returns 0 matches. Cross-module read discipline (D-54-08/D-20-MODULE) is intact.

3. **`__all__` registration** — `repository.py:29`: `"client_has_any_membership"` is in the `__all__` tuple, alphabetically ordered.

4. **IDOR sweep coverage** — `test_idor_sweep.py:92-93`: `/api/v1/client/home` is parametrized in both attack directions (`attacker_is_a=True` and `False`). The sweep actively seeds victim data (T-69-11 hollow-gate guard) so a leaking query produces a real assertion failure.

5. **Service wiring** — `service.py:134`: `ever = await repository.client_has_any_membership(session, client_id)` — `client_id` comes from the `get_client_home(session, client_id: UUID)` parameter which is bound from the authenticated principal (not from the request body/path/query).

### T-999.3-02 — Server-side derivation, no client override path

Mitigation plan required: state derived in `service.py` from DB rows only; never accepted from the client; no client-side override path.

Evidence found:

1. **Server-side ternary** — `service.py:135`:
   `state = "active" if membership is not None else "lapsed" if ever else "newbie"`
   Both inputs (`membership` from `get_client_membership` and `ever` from `client_has_any_membership`) are DB-derived.

2. **Schema field is output-only** — `schemas.py:55`: `membership_state: str` is declared on `ClientHomeResponse` (response schema), not on any request schema. No request body, path param, or query param maps to this field.

3. **No dev toggle** — `HomeScreen.jsx:190`: the render gate `homeData?.membershipState === 'newbie'` reads the server-provided value without a local override. No `tweaks.homeVariant === 'newbie'` branch exists (D-04 confirmed: the `variant` variable at line 137 drives only `classic`/`qr-hero`/`minimal`; the newbie gate is a separate pre-dispatch check keyed solely on the API field).

4. **Frontend type is read-only** — `clientQueries.ts:83`: `membershipState: 'active' | 'newbie' | 'lapsed'` is a field on the `HomeData` response interface. It is never included in any request body or mutation.
