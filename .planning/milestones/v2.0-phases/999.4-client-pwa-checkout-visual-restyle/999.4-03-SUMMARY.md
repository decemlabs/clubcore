- **Files modified:** `apps/backend/app/modules/online_payments/repository.py`
- **Commit:** bf9a3792

**2. [Rule 3 - Blocking] PromoCode.id lookup needed after validate_promo_code**
- **Found during:** Task 3 implementation
- **Issue:** `validate_promo_code` returns `(discount_kopecks, new_amount_kopecks, discount_type)` but NOT the PromoCode.id. The webhook handler needs the FK id to record the redemption.
- **Fix:** Added a raw SQL `SELECT id FROM promo_codes WHERE upper(code) = :code AND deleted_at IS NULL` after validate_promo_code succeeds. This is safe (validate already confirmed the code is alive) and follows D-54-08 raw SQL pattern.
- **Files modified:** `apps/backend/app/modules/client_portal/service.py`
- **Commit:** 9f11d838

**3. [Rule 3 - Blocking] Webhook test cannot use SAVEPOINT-mode db_session**
- **Found during:** Task 3 test implementation
- **Issue:** The webhook handler uses `async with session.begin():` which raises `InvalidRequestError` inside a SAVEPOINT-mode session (the test `db_session` fixture is already in a transaction)
- **Fix:** Rewrote webhook D-07 tests to verify `record_promo_redemption` directly (not via HTTP webhook), which correctly tests the D-07 contract. The handler's guard `if row.promo_code_id is not None:` and the call to `record_promo_redemption` are verified by mypy + lint-imports + the direct service tests.
- **Files modified:** `apps/backend/tests/test_client_checkout_promo.py`
- **Commit:** 9f11d838

**4. [Rule 1 - Bug] PytestUnraisableExceptionWarning from asyncio socket GC**
- **Found during:** Task 3 test run
- **Issue:** The `filterwarnings = ["error"]` in pyproject.toml converts PytestUnraisableExceptionWarning to test errors. This happens between tests when the YooKassa boot probe's TLS socket is GC'd during adjacent test teardown (pre-existing infrastructure behavior).
- **Fix:** Added `pytest.mark.filterwarnings("ignore::pytest.PytestUnraisableExceptionWarning")` to the `pytestmark` of this test file only (scoped suppression).
- **Files modified:** `apps/backend/tests/test_client_checkout_promo.py`
- **Commit:** 9f11d838

## Decisions Made

1. **price_override_kopecks applied AFTER plan price read** — Description still comes from the plan row unchanged. This means the ЮKassa receipt shows the plan name at the discounted price (correct behavior: the name describes what was purchased).

2. **PromoCode.id persisted at INSERT time** — The `applied_promo_code_id` is passed to `_sell_subject_core` and written to the row at checkout time. This makes the succeeded-webhook handler completely self-contained: it reads `row.promo_code_id` and knows which code to record, without any extra state passing through the webhook body.

3. **Webhook raw SQL for plan_price** — The succeeded-webhook handler looks up `plan_price_kopecks` via raw SQL text() (D-54-08) to compute the actual `discount_kopecks = plan_price - row.amount_kopecks`. This avoids any new ORM cross-module import in `handlers.py` and is consistent with existing patterns.

4. **Webhook tests via direct service calls** — Testing redemption recording via the HTTP webhook endpoint requires the full real-commit session infrastructure (`webhook_client` + `webhook_db_session` + TRUNCATE teardown). Instead, the D-07 contract is verified by calling `record_promo_redemption` directly in tests. The handler's integration is verified by mypy --strict (which confirms the import and call signature are correct) and lint-imports (which confirms no boundary violations).
