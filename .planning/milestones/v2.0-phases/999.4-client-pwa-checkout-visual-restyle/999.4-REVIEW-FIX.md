## Fixed Issues

### CR-01: Race-safe cap in `record_promo_redemption` — SELECT FOR UPDATE

**Files modified:** `apps/backend/app/modules/promo_codes/service.py`
**Commit:** ed2b63f1
**Applied fix:** Replaced the plain `SELECT max_uses FROM promo_codes WHERE id = :id AND deleted_at IS NULL` with `SELECT max_uses, per_client_limit FROM promo_codes WHERE id = :id AND deleted_at IS NULL FOR UPDATE`. The row lock serialises concurrent webhook handlers on the same promo code row, so the COUNT check and subsequent INSERT are atomic across webhook replays.

### WR-01: `per_client_limit` re-check added to `record_promo_redemption`

**Files modified:** `apps/backend/app/modules/promo_codes/service.py`
**Commit:** ed2b63f1
**Applied fix:** Added a `per_client_limit` re-check block after the existing `max_uses` re-check. Because the FOR UPDATE lock (CR-01) is already held, the per-client COUNT query is also race-safe. Two concurrent checkouts by the same client for a `per_client_limit=1` promo can no longer both write redemption rows.

### CR-02: Eliminate TOCTOU second SELECT in checkout — return `promo_id` from `validate_promo_code`

**Files modified:** `apps/backend/app/modules/promo_codes/service.py`, `apps/backend/app/modules/client_portal/service.py`
**Commit:** df980bdb
**Applied fix:** Changed `validate_promo_code` return type from `tuple[int, int, str]` to `tuple[int, int, str, UUID]`, adding `promo_id` as the 4th element. Both `client_checkout_membership` and `client_checkout_pt_package` now unpack `applied_promo_code_id` directly from the return tuple, eliminating the separate `SELECT id FROM promo_codes WHERE upper(code) = :code AND deleted_at IS NULL` query that had a TOCTOU window.

### CR-03: Zero-amount guard — raise `PromoNotApplicableError` when `new_amount_kopecks <= 0`

**Files modified:** `apps/backend/app/modules/promo_codes/service.py`, `apps/backend/tests/test_client_promo_validate.py`
**Commit:** df980bdb
**Applied fix:** Added `if new_amount_kopecks <= 0: raise PromoNotApplicableError("promo_results_in_zero_amount")` after the discount computation in `validate_promo_code`. This raises 422 `not_applicable` for 100%-discount codes before any ЮKassa call is made.

Updated `test_valid_fixed_discount_caps_at_price` to expect HTTP 422 / `not_applicable` (was 200 with `newAmountKopecks=0`). Added `test_valid_fixed_discount_partial` to cover the non-zero partial fixed discount path that still returns 200.

Note: requires human verification of the business rule — if 100% fixed discounts are ever intended to be free checkouts (bypassing ЮKassa), this guard would need adjustment.
