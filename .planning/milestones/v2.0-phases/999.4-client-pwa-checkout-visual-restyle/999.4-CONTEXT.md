# Phase 999.4: client-pwa Checkout — visual restyle - Context

**Gathered:** 2026-05-31
**Status:** Ready for planning

<domain>
## Phase Boundary

Restyle the existing client checkout surfaces — `apps/client-pwa/src/screens/sheets/CheckoutSheet.jsx` (review / paying / error stages) and `apps/client-pwa/src/routes/PaymentReturnScreen.jsx` (pending / canceled, plus a new success state) — to match the visual language of the approved mockup `payment.html` (amount header, order-summary card, state screens).

**The ЮKassa hosted-redirect flow is unchanged (D-71-04):** the PWA does **not** build an in-app card-entry form and does **not** collect PAN/CVC/expiry — card data stays on the ЮKassa hosted page. Webhook-only activation and anti-oracle behavior (criterion #1) are untouched. The mockup's card-form, СБП bank-selection, and 3-D Secure panels are **non-binding visual reference**, not a contract to collect card data client-side.

**SCOPE EXPANSION (decided in this discussion):** the phase is **no longer a pure visual restyle / frontend-only.** Real promo codes are added (frontend + backend). This mirrors the 999.3 precedent (D-03 there), where a "visual" phase folded in a backend addition. The ROADMAP §Phase 999.4 scope note MUST be updated and new requirements added. Admin CRUD UI for promo codes is **explicitly deferred to the backlog** (the admin frontend is not ready yet) — see Deferred Ideas.

Visual tokens (spacing, color, typography, exact copy) are to be locked by a forthcoming `999.4-UI-SPEC.md` via `/gsd:ui-phase`. This CONTEXT captures the logic / wiring / scope decisions that the UI-SPEC leaves open.

</domain>

<decisions>
## Implementation Decisions

### Payment method block (review screen)
- **D-01:** **Remove the decorative card picker entirely** ("Visa •••• 4821" / "Apple Pay" / "Новая карта", the `PayOption`/`Divider2c` components, the `card` state, and the associated "save card / Подписаться на акции" switch). Replace it with a **non-collecting info plate** — e.g. "Оплата на защищённой странице ЮKassa · Карта, СБП, Мир" + a lock affordance. Rationale: in the redirect flow the actual method/PAN is chosen and entered on the ЮKassa hosted page, so any in-app picker is purely decorative and misleading. This reaffirms D-71-04 (no in-app card form, no PAN/CVC). The mockup's card-form and СБП panels are visual reference only — **not implemented in-app.**
  - Rejected: keep a decorative Карта/СБП segmented control (creates a false expectation that the in-app choice is honored); keep the current fake card picker restyled (hardcoded fake card keeps misleading the user).

### Promo codes (scope expansion — frontend + backend)
- **D-02:** Promo codes are **real**, not the current fake client-side 10% discount. The phase scope expands to include backend work. ROADMAP §Phase 999.4 scope-note updated; new requirements added.
- **D-03:** **Discount types — support BOTH** percentage (e.g. −10%) and fixed-amount (kopecks, e.g. −500 ₽). Each code carries its own discount type + value.
- **D-04:** **Codes live in a DB table** (`promo_codes`), populated via **seeds / migration** for 999.4. **No admin UI in this phase.** The model is designed so a future admin CRUD UI simply does CRUD over it.
- **D-05:** Promo applies to **both** membership checkout (`kind='sub'`) and PT-package checkout (`kind='pt'`) — both flow through `CheckoutSheet`.
- **D-06:** **Application flow = separate validate, then checkout.** "Применить" calls a server validate endpoint → server returns the discount / new authoritative amount → UI shows the discounted "К оплате" + order summary. On pay, the **code** (not a client-computed price) is passed to the checkout mutation; the server recomputes the authoritative amount and sends it to ЮKassa. The client never computes price (reaffirms server-authoritative pricing).
- **D-07:** **Usage limits are fully configurable per code** — the model must support all of: per-client one-time (`per_client_limit`), multi-use / unlimited, and a global cap (`max_uses`). This requires a redemptions table (e.g. `promo_redemptions`) to enforce per-client and global counts. A redemption is recorded on **successful** payment.
- **D-08:** **Validity fields:** `valid_from` + `valid_until` + `is_active`. The validate endpoint checks the activity window and the flag.
- **D-09:** **Promo validation errors are shown inline under the field, with a distinct message per reason** (not found / expired / not yet active / used up / not applicable / inactive). Minor security note: distinct messages allow probing a code's status — **accepted** for this single-gym pet-project scope.

### Success state (`PaymentReturnScreen` on `succeeded`)
- **D-10:** **Add an in-app "Готово!" success screen,** shown **only** when the confirmed payment `status === 'succeeded'` (anti-oracle / criterion #1 preserved — never shown while pending). `PaymentReturnScreen` no longer does an immediate `Navigate("/")` on succeeded; it renders the success state with a primary CTA ("Хорошо") → Home. The screen shows **amount + plan name** (NOT a card "•••• 4821" — we have no card data in the redirect flow).
- **D-11:** Secondary **"Открыть чек"** button = **link to the ЮKassa fiscal receipt, IF** the payment-status response exposes a receipt URL. **Dependency:** researcher must verify whether the status response (or `fiscal_receipts` module) exposes a receipt URL; if absent, the button is hidden (or a follow-up exposes it). Do not fabricate a receipt screen.

### State screens (errors / pending)
- **D-12:** **Restyle only the real, reachable states** under the mockup's visual language (state-icon / title / desc / actions): the pre-redirect `CheckoutError` kinds (`email-required`, `offline`, `payment`, `slot-busy`), the `PaymentReturnScreen` pending spinner, and the canceled view. **Do NOT implement** the mockup's unreachable card-decline screens (`declined` / `insufficient` / `wrong-cvv` / `timeout`) — those failures occur on the ЮKassa hosted page and are never returned to the app. Building them = dead code.
- **D-13:** Keep the existing **D-71-02 error-code → kind mapping** unchanged (`mapApiErrorToKind`); only the visual presentation of each kind changes.

### Claude's Discretion
- Exact copy, icon choices, spacing, and animations — defer to the forthcoming `999.4-UI-SPEC.md` + `payment.html` mockup.
- Where the promo capability lives on the backend — a new module (`app/modules/promo_codes/`) vs folding into `client_portal` / `billing`. Planner/researcher decide while respecting the import-linter module boundaries.
- Promo code normalization (recommend uppercase, matching the current UI's `toUpperCase()`), and whether to add an optional `min_order_amount` field to the model for future use.
- Currency rounding rule for percentage discounts (kopecks, integer minor units).

</decisions>

<specifics>
## Specific Ideas

- The user consistently prefers **honesty over mockup fidelity** where they conflict: remove the fake card picker (D-01), kill the fake client-side discount (D-02/D-06), don't build unreachable error screens (D-12), don't promise a receipt screen that doesn't exist (D-11). This matches the 999.3 philosophy (honest, data-reflecting UI over a "looks-done" mockup).
- The user **intentionally expanded scope** for real promo codes but **deferred the admin UI** because the admin frontend isn't ready — capture now, build later.

</specifics>

<deferred>
## Deferred Ideas

- **Admin CRUD UI for promo codes** — captured to backlog, **not implemented in 999.4** (admin frontend not ready). The `promo_codes` model is designed so a future admin UI just does CRUD over it. Build when the admin frontend is ready.
- **Receipt deep-link plumbing** — if the payment-status response does not already expose a ЮKassa receipt URL, exposing it (likely via `fiscal_receipts`) is a possible follow-up so D-11's "Открыть чек" button can be shown.
- **Mockup СБП bank-selection + 3-D Secure in-app screens** — not built; handled entirely on the ЮKassa hosted page.
- **Apple Pay / saved-card affordances** from the current mock — dropped (D-01), not revived.

None of these block the phase — they are intentionally outside its boundary.

</deferred>
