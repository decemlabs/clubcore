# Phase 999.4: Code Review Report

**Reviewed:** 2026-05-31T12:00:00Z
**Depth:** standard
**Files Reviewed:** 23

## Summary

This phase adds promo-code validation/redemption plumbing and a checkout visual restyle. The
architecture is generally sound: server-authoritative discount computation, CSRF gates on write
endpoints, integer-kopeck money math throughout, and a correct anti-oracle success screen gate. Four
blockers were found, primarily around concurrency safety of the redemption cap check, a promo-code
ID resolution race window, the fiscal-receipt JOIN correctness, and a missing zero-amount guard.
Five warnings address lesser correctness gaps and one quality issue. No in-app card data is
collected — D-01/D-71-04 is clean.

## Critical Issues

### CR-01: Promo redemption cap re-check in `record_promo_redemption` is not race-safe — concurrent webhooks can over-grant

**File:** `apps/backend/app/modules/promo_codes/service.py:310-348`

The `record_promo_redemption` helper re-reads `max_uses` and then does a second `COUNT(*)` query
before the `INSERT ... ON CONFLICT DO NOTHING`. These two SELECT statements are outside any
row-level lock, so two concurrent succeeded-webhook handlers for two different payments that both
used the same promo code with `max_uses=1` can both see `global_count=0 < 1`, both pass the cap
check, and both then reach the `pg_insert ... on_conflict_do_nothing` on the
`uq_promo_redemptions_online_payment_id` constraint. Because the UNIQUE constraint is keyed on
`online_payment_id` (not on `promo_code_id`), the `on_conflict_do_nothing` will **not** fire for
two distinct payments — both rows will insert, exceeding the cap.

The docstring acknowledges a bounded over-grant "at most 1-per-payment" for `validate_promo_code`
(T-999.4-09), but `record_promo_redemption` is supposed to be the final enforcement point. The
actual DB-level constraint that could prevent this — a per-promo redemption count constraint — does
not exist in the schema. The current implementation provides only a soft "belt-and-suspenders"
comment, but the code path it was meant to guard is silently vulnerable.

**Fix:** Use a `SELECT ... FOR UPDATE` on the `promo_codes` row inside the existing
`session.begin()` transaction (the caller already holds an open `async with session.begin()` block
in the webhook handler). This serialises concurrent redemptions for the same promo code:

```python
# Acquire a row lock on the promo_codes row before the COUNT check so
# concurrent webhook handlers serialise on this promo code.
promo_row = (
    await session.execute(
        text(
            "SELECT max_uses FROM promo_codes "
            "WHERE id = :id AND deleted_at IS NULL FOR UPDATE"
        ),
        {"id": str(promo_code_id)},
    )
).mappings().one_or_none()
```

Alternatively, add a DB-level partial UNIQUE or CHECK on `(promo_code_id)` with a deferred trigger,
but the SELECT-FOR-UPDATE approach is simpler and consistent with how the webhook handler itself
serialises on the `online_payments` row.

### CR-02: Promo code ID resolved in a separate query after `validate_promo_code` — TOCTOU window allows wrong ID (or None) to be stored

**File:** `apps/backend/app/modules/client_portal/service.py:535-546` and `614-625`

Both `client_checkout_membership` and `client_checkout_pt_package` call
`_promo_service.validate_promo_code(...)` to validate the code and then immediately issue a
**second** `SELECT id FROM promo_codes WHERE upper(code) = :code AND deleted_at IS NULL` query to
resolve the `promo_code_id` FK. Between these two queries:

1. The promo code could be soft-deleted (operator action), in which case the second query returns
   `None` — `applied_promo_code_id` stays `None`, the discount is applied to the price sent to
   ЮKassa, but no `promo_code_id` is recorded on the `online_payments` row. The webhook handler
   then skips the redemption write (`if row.promo_code_id is not None`), so the promo is consumed
   without being ledgered.

2. Less likely: a different promo code with the same normalised code is created between deletes. The
   second query would return the new code's UUID, attaching the new code's ID to a redemption that
   was validated against the old code's parameters.

**Fix:** `validate_promo_code` should return the `promo_id` UUID as part of its return tuple
(or as a dataclass), eliminating the separate lookup:

```python
# In promo_codes/service.py — extend return type:
async def validate_promo_code(...) -> tuple[int, int, str, UUID]:
    ...
    return discount_kopecks, new_amount_kopecks, discount_type, promo_id

# In client_portal/service.py:
_discount_kopecks, price_override, _discount_type, applied_promo_code_id = (
    await _promo_service.validate_promo_code(...)
)
# No second SELECT needed.
```

### CR-03: `new_amount_kopecks` can be zero — ЮKassa will reject a payment for 0 ₽

**File:** `apps/backend/app/modules/promo_codes/service.py:225-230`

For a `fixed` discount where `discount_value >= price_kopecks`, the code correctly caps
`discount_kopecks = min(discount_value, price_kopecks)` and returns `new_amount_kopecks = 0`. This
zero amount is then passed as `price_override_kopecks` into `_sell_subject_core` and sent to
ЮKassa via `create_payment(amount_kopecks=price_kopecks)`. ЮKassa requires `amount > 0` and will
return a validation error for a zero-amount payment.

The validation endpoint (`/promo/validate`) exposes `newAmountKopecks: 0` to the PWA, which
renders it as "0 ₽" in the checkout sheet and allows the user to tap "Оплатить". Only after the
ЮKassa API call fails does the PWA show an error state. The correct fix is a server-side guard.

**Fix:** In `validate_promo_code` (or at the call-site in `_sell_subject_core`), reject a zero
final amount before the ЮKassa call:

```python
# In promo_codes/service.py, after computing new_amount_kopecks:
if new_amount_kopecks <= 0:
    # 100% discount: free checkout is not supported via ЮKassa redirect flow.
    # Treat as not applicable (or a dedicated error code).
    raise PromoNotApplicableError("promo_results_in_zero_amount")
```

### CR-04: D-11 fiscal receipt JOIN can match the wrong membership or PT package

**File:** `apps/backend/app/modules/client_portal/service.py:692-720`

The receipt URL JOIN uses:

```sql
op.membership_plan_id = m.plan_id
```

This joins `online_payments.membership_plan_id` to `memberships.plan_id` — i.e., it finds **any
membership for this client under this plan**, not specifically the membership activated by this
payment. If a client has purchased the same membership plan more than once (e.g., after expiry),
the sub-query returns multiple `membership.id` values. The subsequent `payments` join then matches
any `payment` whose `subject_id` is one of those memberships, including older ones. The outer
`fiscal_receipts` join then returns the receipt for the **first succeeded payment** to any of those
memberships, not necessarily the one corresponding to `op_id`.

Concretely: Client buys Plan A in January (payment P1, fiscal F1). Plan expires. Client buys Plan A
again in March (payment P2, fiscal F2). After P2 succeeds, a GET on P2's status returns F1's
receipt URL (whichever `LIMIT 1` returns first).

**Fix:** The join must anchor on the specific membership activated by this payment. The correct join
goes through `online_payments.id` → membership activator audit / the `online_payment_id` column on
`memberships` (if it exists), or via the `payments` table's `audit_correlation_id` chain. The
simplest surgical fix is to add `AND m.id = (SELECT subject_id FROM payments WHERE ... AND
method='online' ORDER BY ... LIMIT 1)` anchored to the correct `online_payment_id`, but this
requires knowing the exact schema of the memberships-payments linkage. At minimum, `ORDER BY
m.created_at DESC LIMIT 1` in the sub-query narrows to the most recent membership, which reduces
(but does not eliminate) the multi-row risk:

```sql
-- Replace the sub-query with a most-recent anchor:
SELECT m.id FROM memberships m
INNER JOIN online_payments op
    ON op.membership_plan_id = m.plan_id
WHERE op.id = :op_id
  AND m.client_id = op.client_id
ORDER BY m.created_at DESC
LIMIT 1
```

## Warnings

### WR-01: `validate_promo_code` usage limit check is read-only — discount granted even if limit is exceeded between validate and checkout

**File:** `apps/backend/app/modules/promo_codes/service.py:187-214`

The `per_client_limit` and `max_uses` checks in `validate_promo_code` are plain `COUNT(*)` SELECTs
with no locking. Two concurrent checkout requests by the same client for a promo with
`per_client_limit=1` can both pass validation simultaneously and both proceed to create payments.
The `record_promo_redemption` belt-and-suspenders re-check in the webhook path addresses the global
`max_uses` cap (imperfectly — see CR-01), but does **not** re-check `per_client_limit`. Once both
payments succeed, two redemption rows with the same `client_id` and `promo_code_id` will be written
(different `online_payment_id` values, so no UNIQUE conflict fires).

This is a known single-gym scale trade-off (T-999.4-09) but the `per_client_limit` gap is not
documented as accepted; only `max_uses` is mentioned. At minimum, `record_promo_redemption` should
also re-check `per_client_limit`.

**Fix:** Mirror the `max_uses` re-check in `record_promo_redemption` for `per_client_limit`:

```python
if per_client_limit is not None:
    client_count_row = (
        await session.execute(
            text(
                "SELECT COUNT(*) AS cnt FROM promo_redemptions "
                "WHERE promo_code_id = :promo_id AND client_id = :client_id"
            ),
            {"promo_id": str(promo_code_id), "client_id": str(client_id)},
        )
    ).mappings().one()
    if int(client_count_row["cnt"]) >= per_client_limit:
        _log.warning("record_promo_redemption_per_client_cap_met", ...)
        return
```

Note: with a SELECT-FOR-UPDATE fix (CR-01), this per-client check also becomes safe.

### WR-02: `promo_codes/service.py` imports `pg_insert` and `PromoRedemption` at module level even for the validate-only path — circular import risk

**File:** `apps/backend/app/modules/promo_codes/service.py:30-34`

`from sqlalchemy.dialects.postgresql import insert as pg_insert` and
`from app.modules.promo_codes.models import PromoRedemption` are top-level imports. The module
docstring documents this as a read-only validate path. The `.importlinter` boundary
(`client_portal → promo_codes`) is registered as an Option B direct import. However, `pg_insert`
is only needed by `record_promo_redemption`; pulling it at module level is not wrong per se, but
`structlog.get_logger(...)` is placed at line 265 (after the function definitions), which means the
logger is set up after all the functions are defined. This is a minor structural oddity but not a
correctness issue. The actual risk is that the import `from app.modules.promo_codes.models import
PromoRedemption` inside `service.py` (same module as the model) is fine, but the file-level import
of `pg_insert` is a sign that the module's two public APIs (validate vs. record) have different
dependency footprints — if the module is ever split, the read path accidentally drags in write-side
imports.

**Fix:** Move the `pg_insert` import and the `structlog` logger initialisation to the top of the
file (before function definitions), or accept as-is and add a comment clarifying the intent.
Relocate `_log = structlog.get_logger(...)` to line 30 area so all module-level bindings are
co-located.

### WR-03: `CheckoutSheet.jsx` sends `promoCode` to the checkout mutation even on a replay/retry if the user removed the promo between attempts

**File:** `apps/client-pwa/src/screens/sheets/CheckoutSheet.jsx:100-101`

```js
const appliedPromoCode = promoResult ? promoCode : undefined;
```

`promoCode` (the input state) and `promoResult` (the validated result) are separate state values.
If the user types a code, validates it (setting `promoResult`), then edits the input field without
clicking "Убрать", `promoCode` changes but `promoResult` still holds the old validated result. On
the next "Оплатить" click, `appliedPromoCode` will be the **newly typed, unvalidated string**, not
the validated code that produced `promoResult`.

This causes `startPay` to send an unvalidated promo code string to the server. The server will
re-validate it (secure), but the UX is inconsistent: the user sees a discount for code A but the
request is made with code B.

**Fix:** Either disable the promo input once validated (already done via `disabled={!!promoResult}`
on the `<input>` — the user cannot edit after validation, so this path is unreachable in practice)
**or** derive `appliedPromoCode` from the validated result's code snapshot, not the input state.
Confirm the `disabled` attribute on the input is always enforced to prevent state divergence. The
current code is safe because of the `disabled` attribute, but it is fragile — remove the reliance
on input-disabled-ness as a correctness invariant:

```js
// Derive applied code from the result snapshot, not live input state:
const appliedPromoCode = promoResult ? promoResult._code : undefined;
// Or store the validated code string in promoResult when it's set.
```

### WR-04: `PaymentReturnScreen` test does not assert the receipt URL button conditional (D-11)

**File:** `apps/client-pwa/src/routes/PaymentReturnScreen.test.jsx:48-62`

The succeeded test case sets `receiptUrl: null` and never tests the case where `receiptUrl` is a
non-null URL. The D-11 requirement states the "Открыть чек" button must appear only when
`receiptUrl` is non-null. There is no test that:

1. Renders with `receiptUrl: 'https://yookassa.ru/my/receipt/xxx'` and asserts the link appears.
2. Renders with `receiptUrl: null` and asserts the link is absent.

The anti-oracle criterion is tested, but the receipt URL conditional (the primary D-11 guard) is
untested.

**Fix:** Add two additional test cases:

```js
it('succeeded state with receiptUrl: shows "Открыть чек" link', () => {
  useClientPaymentStatus.mockReturnValue({
    data: { id: 'test-id', status: 'succeeded', receiptUrl: 'https://yookassa.ru/my/receipt/abc' },
    isLoading: false,

  render(<PaymentReturnScreen />)
  const link = screen.getByText('Открыть чек')
  expect(link).toBeInTheDocument()
  expect(link.getAttribute('href')).toBe('https://yookassa.ru/my/receipt/abc')

it('succeeded state without receiptUrl: "Открыть чек" is absent', () => {
  useClientPaymentStatus.mockReturnValue({
```

### WR-05: `seed_demo_data.py` — `_seed_promo_codes` is called on a session whose transaction was already committed by `_seed_catalog`

**File:** `apps/backend/scripts/seed_demo_data.py:188-190`

`_seed_catalog(session)` and `_seed_promo_codes(session)` are called sequentially on the **same**
`session` object. Each helper calls `await session.commit()` internally. After `_seed_catalog`
commits, the session is in a clean state. Then `_seed_promo_codes` is called with the same session,
which starts a new implicit transaction. This is functional but architecturally inconsistent: the
two helpers share a session but each own their own commit. If `_seed_promo_codes` raises after
partial inserts but before commit, the session is in an indeterminate state.

More importantly, in `_seed_promo_codes`, the `pg_insert(...).on_conflict_do_nothing(index_elements=
[func.upper(PromoCode.code)], ...)` uses `index_elements` with a function expression. PostgreSQL
`ON CONFLICT` with `index_elements` requires the expression to match the index definition exactly.
The partial UNIQUE index `uq_promo_codes_code_alive` is a **functional expression index** on
`upper(code)` with a `WHERE deleted_at IS NULL` predicate. The `on_conflict_do_nothing` call does
not pass `index_where`, so it may fail to resolve the correct index and fall through to a constraint
violation rather than a no-op.

**Fix:** Add `index_where=PromoCode.deleted_at.is_(None)` to the `on_conflict_do_nothing` call,
mirroring the pattern used for `MembershipPlan` and `PtPackagePlan` in `_seed_catalog`:

```python
stmt = (
    pg_insert(PromoCode)
    .values(**c)
    .on_conflict_do_nothing(
        index_elements=[func.upper(PromoCode.code)],
        index_where=PromoCode.deleted_at.is_(None),  # required for partial index resolution
    )
)
```

### IN-01: `Icon.jsx` — undefined icon name silently renders an empty SVG

**File:** `apps/client-pwa/src/components/Icon.jsx:65`

```js
{paths[name]}
```

If `name` is not a key in `paths` (e.g. a typo in a caller), `paths[name]` is `undefined` and
React renders nothing inside the SVG. There is no runtime warning. The `aria-hidden="true"` means
screen readers are unaffected, but the visual slot is empty.

**Fix:** Add a fallback or a development-only assertion:

```js
const content = paths[name]
if (process.env.NODE_ENV !== 'production' && content === undefined) {
  console.warn(`Icon: unknown name "${name}"`)
}
return (
  <svg ...>
    {content ?? null}
  </svg>
)
```

### IN-02: `validate_promo_code` checks `is_active` before time-window — order differs from natural user expectation and D-09 docs ordering

**File:** `apps/backend/app/modules/promo_codes/service.py:165-185`

The validation order is: `is_active` → `applicable_to` → time window. The D-09 spec lists the
error codes as `not_found / expired / not_yet_active / used_up / not_applicable / inactive`, which
implies `expired` is checked before `not_applicable` / `inactive`. This means an expired AND
inactive code returns `inactive` rather than `expired`. This is not a security issue but can confuse
operators reviewing error logs — an expired code that was also deactivated will appear as
`inactive`.

**Fix:** Reorder validation: `not_found` → `is_active` → time window → `applicable_to` → usage.
Or document the chosen order in the function docstring.
