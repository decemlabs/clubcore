<decisions>
## Implementation Decisions

### OpenAPI Tagging (HND-01)
- **D-72-01 (Claude's discretion — default: unify):** HND-01 says "ALL client-facing paths under `Client-Portal`." Today Phase-68 auth/profile endpoints are tagged `"Client"` (and `"Client"` is in the ordered `OPENAPI_TAGS` list at `app/main.py:150`), while Phase 69–71 portal endpoints are tagged `"Client-Portal"` (NOT yet in the ordered list). **Default decision:** re-tag the Phase-68 auth/profile endpoints `"Client"` → `"Client-Portal"`, drop/rename the `"Client"` tag entry, and add a single `"Client-Portal"` entry to `OPENAPI_TAGS` ordering — one unified client tag, the literal HND-01 reading. **Override only if** re-tagging endangers the v1.11 staff drift gate or Redocly lint; the two-tag fallback ("Client" auth + "Client-Portal" portal, just adding "Client-Portal" to the ordered list) is acceptable since the drift check (criterion #1) is scoped to staff paths. Either way, `Client-Portal` MUST be added to `OPENAPI_TAGS` so it has a deterministic position in the curated spec.

### Contract Forward-Guards (HND-02)
- **D-72-02:** The new `_v20Checks` `AssertNonNever` block covers **all v2.0 client paths** — both Phase-68 auth/profile (OTP request/verify, refresh, logout, `GET`/`PATCH /client/me`) AND Phase 69–71 portal paths (membership, visit/PT/payment history, plans/PT-packages/trainers catalog, bookings create/cancel/slots, QR token/check-in, checkout membership/PT, payment status). ~24 operations in a single `_v20Checks` tuple with a runtime `toHaveLength(...)` assertion, mirroring the established `_v14Checks`/`_v15Checks`/`_v18Checks`/`_v19Checks` precedent in `schema.contract.test.ts`. Existing `_v1xChecks` blocks are not touched.

### CI Gates (HND-03)
- **D-72-03:** Add a **dedicated parallel `client-pwa` job** to `.github/workflows/ci.yml` (no `needs:` — runs alongside `backend`, `frontend`, `redocly-lint`). Matches criterion #3's "in parallel with existing backend and admin-web gates" literally and isolates client-pwa failures from the shared frontend gate.
- **D-72-04:** The `client-pwa` job runs **typecheck + lint + test + build** (`pnpm -F @clubcore/client-pwa {typecheck,lint,test,build}`). The `build` gate is included because `vite build` + `vite-plugin-pwa` service-worker/manifest generation is a real failure surface not covered by `tsc -b --noEmit` typecheck.
- **D-72-05:** Scope the **existing `frontend` job's `pnpm -r` steps so client-pwa gates don't double-run** (e.g. `--filter '!@clubcore/client-pwa'` or equivalent) — avoids running client-pwa lint/typecheck/test twice across two jobs. Keep the existing `schema.d.ts` drift gate and api-client codegen in the frontend job.

### Live E2E + Verification (VER-01..04)
- **D-72-06 (hybrid E2E gate):** The **live read-path is the hard completion gate**: `docker compose up` + PWA walkthrough of phone-OTP login → home → book slot → QR check-in → history, run live with evidence captured (HUMAN-UAT / OPERATOR-EVIDENCE file). The **ЮKassa checkout leg is operator-pending** — deferred for human execution before real handoff, because it needs the hosted-page test card + manual webhook fire (external/credentialed). This breaks the read-path portion out of the prior "fully operator-pending" pattern (v1.6/v1.9/v1.11) since a documented local path exists, while keeping the payment leg deferred.
- **D-72-07 (seed state — Claude's discretion, default: dev seed script):** The read-path's book/QR steps need an **active membership + PT-package** for the dev client, which normally comes from checkout. Establish it **without** the deferred payment leg by using the existing dev seed (`scripts/seed_dev_client` + `scripts/seed_demo_data`, per the documented local-stack path) to grant the dev client an active membership + PT-package directly. Override to a staff-side sell/activate only if the seed path proves insufficient.
- **D-72-08:** Automated truths are the **firm** gate (CI must be green): VER-02 (IDOR / anti-oracle / two-principal tests — these already exist from Phases 68–70; this phase confirms they run in CI), VER-03 + HND-01 (drift gate confirms staff byte-identical to `contract-freeze-v1.11.0`).

### Runbook (VER-04)
- **D-72-09:** Author a **full client-journey + auth** v2.0 runbook — bilingual, curl + PWA steps for the complete flow (phone-OTP login → home → book → checkout → QR check-in → history), the dev-seed / dev-OTP setup, and the ЮKassa test-card + manual-webhook procedure (marked operator-pending). Mirrors the depth of the existing `clubcore-auth-runbook.md`; doubles as the execution guide for the deferred checkout leg (D-72-06).

### Claude's Discretion (planner/researcher decides)
- Final tag scheme (D-72-01) — unify vs two-tag — gated on drift-gate safety.
- Whether to drop or repurpose the existing `"Client"` `OPENAPI_TAGS` description if unifying.
- Exact `_v20Checks` operation list and tuple length (D-72-02) — enumerate from the live client router set.
- The precise `frontend`-job scoping mechanism that prevents double-run (D-72-05).
- Seed-vs-staff-grant for read-path state (D-72-07), defaulting to dev seed.
- Runbook filename/location under `.planning/handoff/` and the exact evidence-file path for the live read-path walkthrough.

</decisions>
