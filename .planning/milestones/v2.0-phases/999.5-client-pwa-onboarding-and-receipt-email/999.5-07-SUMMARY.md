# Phase 999.5 Plan 07: Fiscal-Receipt Phone-Aware Foundation Summary

One-liner: A phone-only «Чек не нужен» fiscal receipt can now be persisted (email NULL, phone set, guarded by an at-least-one-contact CHECK) and fiscalized — `create_receipt` POSTs `receipt.customer.phone` when only a phone is supplied, mirroring the create_payment email-OR-phone pattern Plan 03 deferred.

## What Was Built

### Task 1 — Migration 0049 + integration test (commit f631db1a)
- `0049_fiscal_receipts_customer_phone` with `down_revision = "0048_client_onboarding_fields"` (mirrors 0048 style). upgrade(): ADD COLUMN `customer_phone` (nullable Text); ALTER `customer_email` → nullable; CREATE CHECK `ck_fiscal_receipts_contact_present` = `customer_email IS NOT NULL OR customer_phone IS NOT NULL`. downgrade() reverses in order: drop CHECK → restore `customer_email` NOT NULL → drop `customer_phone`. Docstring documents the additive-then-restrictive, no-backfill rationale.
- Integration test (mirrors the 0035 pattern): asserts customer_phone exists + nullable, customer_email now nullable, the contact-present CHECK exists; row-level: phone-only row persists, email-only row persists, both-NULL row rejected by the CHECK.

### Task 2 — Phone-aware FiscalReceipt model + repository (commit 5169e911)
- models.py: `customer_email` → `Mapped[str | None]` nullable; added `customer_phone: Mapped[str | None]` nullable; added `CheckConstraint("customer_email IS NOT NULL OR customer_phone IS NOT NULL", name="contact_present")` (NAMING_CONVENTION expands to the migration's exact constraint name).
- repository.py: `insert_fiscal_receipt` signature `customer_email: str` → `customer_email: str | None = None`, added `customer_phone: str | None = None`; both threaded into the `FiscalReceipt(...)` constructor. Caller-owns-txn preserved (no flush/commit). No call site touched.

### Task 3 — create_receipt email-OR-phone (TDD: RED 27fe0901, GREEN d807d55a)
- RED: 4 failing tests (email-path posts customer.email only; phone-path posts customer.phone only and never `{"email": "+7..."}`; neither raises ValueError; customer_phone never leaks to structlog). Existing 11 tests stayed green.
- GREEN: signature `customer_email: str` → `customer_email: str | None = None` + `customer_phone: str | None = None`; customer object built with the create_payment if/elif/raise shape (email key, else phone key, else `ValueError`); `kind`/`link_field`/`send`/`tax_system_code`/`items` untouched; never-re-raise (SC1) and PII discipline preserved; docstring updated with the email-OR-phone contact note.
