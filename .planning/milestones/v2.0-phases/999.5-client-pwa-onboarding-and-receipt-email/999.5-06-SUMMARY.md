# Phase 999.5 Plan 06: Idempotence-Key Collision Single-Retry Summary

One-liner: A burned deterministic day-key with a changed receipt body now retries ЮKassa `create_payment` exactly once with a fresh key (gated on `parameter == "Idempotence-Key"`), returning a `confirmation_url` instead of a 502 — without weakening same-body double-tap replay safety.

## What Was Built

### Task 1 — Surface the ЮKassa error-envelope parameter (commits f2f357c2 RED, c4c5eb71 GREEN)
- Added `error_parameter: str | None = None` to `YooKassaPaymentResult` (back-compat default; success and parameter-less envelopes leave it `None`).
- Extended `_classify_http_status_error` to also extract `body["parameter"]` (when a str) and return it as a 4th tuple element; updated the return-type annotation and all four internal callers (`create_payment`, `get_payment`, `create_refund`, `create_receipt`, `get_refund`) to unpack it.
- `create_payment`'s `HTTPStatusError` branch threads the extracted parameter into the returned result and into the existing forensic `_log.warning` kwargs (parameter is non-PII metadata).
- Classification taxonomy unchanged: a 400 `invalid_request`/`Idempotence-Key` still classifies `permanent_error` at the client layer.

### Task 2 — Single-retry on Idempotence-Key collision in `_sell_subject_core` (commits effc351e RED, 1ca797a0 GREEN)
- After the `create_payment(...)` call and before the classification switch, a single `if` retries once with `idem_key = f"{idem_key}:retry-{uuid4().hex}"` (mirroring the existing canceled-row retry-key shape) when `classification == "permanent_error"` AND `error_code == "invalid_request"` AND `error_parameter == "Idempotence-Key"`.
- The retry fires even when NO local `online_payments` row exists — the UAT-10 burned-key-without-row case.
- Bounded to one attempt: a second consecutive collision falls through to the existing `permanent_error → BadGatewayAppError` path.
- Replay short-circuit (replay branch) still runs first, so genuine same-body double-taps replay the existing row with no second ЮKassa call.
- PII discipline (T-999.5-12 / T-999.5-G1-03): the pre-retry `_log.warning("online_payment_idempotency_key_collision_retry", ...)` logs only `subject_kind` + `client_id` — never the key or any receipt contact.
- The PWA client checkout path benefits automatically: it delegates into the same `_sell_subject_core` via the composition-root `invoke_client_checkout_core` Protocol (no client_portal change needed).
