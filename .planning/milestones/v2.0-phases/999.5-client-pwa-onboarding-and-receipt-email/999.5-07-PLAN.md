<objective>
Fix the persistence + outbound-fiscalization foundation for Issue 2 (BLOCKER, UAT test 12). The diagnosis flagged the webhook handler, but the root cause is deeper: `fiscal_receipts.customer_email` is DB-level `NOT NULL` (models.py:67), and the downstream ARQ `create_receipt` (client.py:478) hardcodes `customer_email: str` → `{"email": customer_email}`. A phone-only «Чек не нужен» payment (email NULL by D-10) therefore cannot be persisted OR fiscalized.

This plan delivers the schema + persistence + outbound contract so a phone-only fiscal receipt can be stored and sent. It does NOT touch the webhook handler or the ARQ dispatch task — those are wired in Plan 08 (wave 2) against the contract this plan establishes.

Purpose: make the fiscalization stack phone-aware end-to-end at the storage + ЮKassa-call layer (mirrors what Plan 03 did for create_payment, closing the "second customer.email site" caveat Plan 03 explicitly deferred).
Output: migration 0049, a phone-aware FiscalReceipt model + repository, and an email-OR-phone create_receipt.
</objective>
