# Phase 999.5: Code Review Report

**Reviewed:** 2026-06-01T10:43:36Z
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

Phase 999.5 adds client-PWA onboarding (4-step questionnaire + new `clients` profile
fields) and a receipt-email gate before ЮKassa checkout, backed by an additive migration
(goal / height_cm / weight_kg / onboarding_completed_at + a `goal` CHECK constraint), a
`PATCH /client/me` write path, and receipt-contact exposure on the succeeded
payment-status endpoint.

Security posture is generally solid: IDOR is enforced via principal-derived `client.id`
(never read from the body); the profile UPDATE parameterizes all values and interpolates
only fixed SET-clause literals (no injection surface); the receipt-contact anti-oracle is
correctly gated inside the `succeeded` branch only; the migration is additive and
reversible.

One **BLOCKER**: the succeeded payment-status endpoint can return a receipt with **no
contact at all** for a client whose email is the empty string, because the email and phone
fallbacks use inconsistent null checks — a 54-ФЗ receipt-destination display defect on a
real-money path. Six warnings cover a permanently-broken onboarding step (reads fields the
API never returns), a triplicated checkout-launch closure, a missing soft-delete guard, a
hand-maintained field list that silently drops data, and a skip path that loops on failure.

## Critical Issues

### CR-01: Succeeded receipt-status returns NO contact when `clients.email` is the empty string (inconsistent null checks)

**File:** `apps/backend/app/modules/client_portal/service.py:850-855`

```python
if contact_row is not None:
    client_email = contact_row["email"]
    client_phone = contact_row["phone"]
    receipt_email = client_email if client_email else None
    receipt_phone = client_phone if client_email is None else None
```

`receipt_email` uses a **truthiness** check (`if client_email`), so an empty-string email
collapses to `None`. But `receipt_phone` uses an **identity** check (`if client_email is
None`). When `clients.email == ""` (empty string, not `NULL`):

- `receipt_email` → `None` (empty string is falsy), and
- `receipt_phone` → `None` as well, because `"" is None` evaluates to `False`.

The succeeded `ClientPaymentStatusResponse` then carries `receipt_email=None` AND
`receipt_phone=None`, so `PaymentReturnScreen`'s "ЧЕК ОТПРАВЛЕН НА …" block
(PaymentReturnScreen.jsx:171-195) renders nothing — the user is shown a successful payment
with no indication of where their legally-required 54-ФЗ receipt went, even though the row
has a valid phone. This is a data-correctness defect on the post-payment path.

Empty-string email is reachable: `clients.email` is nullable `Text` with no NOT-empty CHECK
(clients/models.py:77), and the email-format gate
(`_read_client_receipt_contact_or_raise`, online_payments/service.py:128) only checks
`email is None`, so an empty string passes the create-payment gate and reaches this read.
The two branches must use identical emptiness semantics.

**Fix:** normalize once, then derive both from the same value:

```python
client_email = contact_row["email"] or None
client_phone = contact_row["phone"]
receipt_email = client_email
receipt_phone = client_phone if client_email is None else None
```

## Warnings

### WR-01: Onboarding "Профиль" step reads `me.birthday` / `me.gender`, which `/client/me` never returns — step is permanently stuck `pending`

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:60`

```js
const profileDone = !!(me?.birthday && me?.gender)
```

`ClientMeData` (clientQueries.ts:88-97), `ClientMeResponse` (schemas.py:297-312), and
`fetch_client_me` (repository.py:555) expose only
`firstName/lastName/phone/email/goal/heightCm/weightKg/onboardingCompletedAt` — there is
**no `birthday` and no `gender`** on the `/client/me` payload. `me.birthday` and
`me.gender` are therefore always `undefined`, so `profileDone` is always `false`. The
onboarding strip's "Профиль" step can never reach `done` from live data, and
`doneCount` / the progress bar / the title ("Ещё N шага…") stay off-by-one for any user who
actually completed the questionnaire. This is a logic error: the step should reflect the
fields the questionnaire collects.

**Fix:**

```js
const profileDone = !!(me?.onboardingCompletedAt || (me?.goal && me?.heightCm && me?.weightKg))
```

### WR-02: Checkout-launch logic is triplicated across `startPay`, `onSaved`, and `onSkip` — drift hazard

**File:** `apps/client-pwa/src/screens/sheets/CheckoutSheet.jsx:110-139, 158-182, 183-208`

The membership/PT `mutateAsync(...)`-then-`window.location.href = result.confirmationUrl`
block is copy-pasted three times (the `startPay` happy path, plus the email-gate `onSaved`
and `onSkip` callbacks). The copies already diverge: `startPay` runs the `forceOutcome` and
`!ctx.planId` demo guards first, but `onSaved`/`onSkip` skip those guards entirely, so a
falsy `ctx.planId` on the gate path would call `mutateAsync({ planId: undefined })` instead
of falling back. Any future change to the checkout call must be made in three places.

**Fix:** extract a single `launchCheckout()` helper closing over `ctx`, `promoResult`,
`idempotencyKey`, and the two mutations; call it from all three sites.

### WR-03: `_read_client_receipt_contact_or_raise` omits the `deleted_at IS NULL` guard that every other client read enforces

**File:** `apps/backend/app/modules/online_payments/service.py:118-122`

```python
row = (
    await session.execute(
        select(Client.email, Client.phone).where(Client.id == client_id)
    )
).one_or_none()
```

`fetch_client_me` (repository.py:557) and the receipt-status contact read
(service.py:843-844) both scope to alive rows with `deleted_at IS NULL`. This query does
not. A soft-deleted client whose `client_id` is still attached to an in-flight checkout
would read the deleted row's email/phone and proceed to create a real ЮKassa payment +
fiscal receipt against a deleted account, violating the D-20-IDOR soft-delete discipline.

**Fix:** `.where(Client.id == client_id, Client.deleted_at.is_(None))` so a soft-deleted
client collapses to `NotFoundError("client_not_found")`.

### WR-04: `update_client_profile` can overwrite a stored name with an empty string + uses a hand-maintained field list

**File:** `apps/backend/app/modules/client_portal/service.py:181-197`

```python
if payload.first_name is not None:
    trimmed = payload.first_name.strip()
    if len(trimmed) > _FIRST_NAME_MAX:
        raise _InvalidFirstNameError(...)
    payload = ClientProfileUpdateRequest(
        first_name=trimmed,          # may be "" after trim
        goal=payload.goal,
        height_cm=payload.height_cm,
        weight_kg=payload.weight_kg,
        onboarding_completed=payload.onboarding_completed,
        email=payload.email,
    )
```

Two problems:

1. **Empty-after-trim write.** If a caller sends `first_name="   "`, `trimmed` is `""`
   (length 0, passes the max check), and the rebuilt payload has `first_name=""` — *not*
   `None` — so `repository.update_client_profile`'s `if payload.first_name is not None`
   guard (repository.py:585) does NOT skip it, and the stored real name is overwritten with
   an empty string. Today's PWA finish path sends `name.trim() || undefined`
   (OnboardingScreen.jsx:294), so it is not reachable from this client, but the manual
   «Профиль» re-entry path and any future caller make it live. There is also no minimum
   length enforced (an all-spaces or 1-char name is accepted).

2. **Hand-maintained field list.** Re-constructing the model field-by-field means the next
   person who adds a field to `ClientProfileUpdateRequest` (schemas.py:277-294) and forgets
   this site will have that field silently dropped whenever `first_name` is present — a
   no-error data-loss footgun.

**Fix:** map empty-after-trim to `None` and use `model_copy` to avoid the brittle field
list:

```python
if payload.first_name is not None:
    trimmed = payload.first_name.strip()
    if len(trimmed) > _FIRST_NAME_MAX:
        raise _InvalidFirstNameError(...)
    payload = payload.model_copy(update={"first_name": trimmed or None})
```

### WR-05: Onboarding skip silently swallows backend failures and navigates into a redirect loop

**File:** `apps/client-pwa/src/screens/OnboardingScreen.jsx:307-315`

```js
async function handleSkip() {
  try {
    await completeOnboarding.mutateAsync()
    navigate('/home', { replace: true })
  } catch (_e) {
    // If skip fails, still navigate — worst case the redirect fires again next login
    navigate('/home', { replace: true })
  }
}
```

If the PATCH that stamps `onboarding_completed_at` fails (network/500), the user is sent to
`/home`, where the auto-redirect gate (HomeScreen.jsx:142-150) re-fires on a newbie with
empty profile and `!onboardingCompletedAt`, bouncing them straight back to `/onboarding`.
The user gets no toast, no retry, no way to recover — an unobservable loop. `handleFinish`
already surfaces `submitError`; the skip path should do the same instead of navigating on
failure.

**Fix:** on skip failure set a visible error and keep the user on the screen with a retry;
navigate only on success.

### WR-06: `useUpdateClientEmail` / skip path do not invalidate `/client/home`, so the onboarding gate may use stale `me`

**File:** `apps/client-pwa/src/lib/clientQueries.ts:225-236`

`useUpdateClientEmail.onSettled` invalidates only `clientPortalKeys.me()`, while
`useUpdateClientProfile` and `useCompleteOnboarding` invalidate both `me()` and `home()`.
After the receipt-email gate saves an email mid-checkout, the home gate's `me` read can lag.
More importantly, the `useClientMe` query has `staleTime: 30_000` (clientQueries.ts:162),
and the HomeScreen auto-redirect effect depends on `me` (HomeScreen.jsx:142-150): a user who
completes onboarding and is navigated to `/home` within the 30s window may read a stale
pre-completion `me` (no `onboardingCompletedAt`) from cache and be redirected back to
`/onboarding` before the invalidation-driven refetch resolves. Invalidation fires the
refetch but the effect can run against the stale snapshot first.

**Fix:** ensure the completion mutations `await`/settle the `me()` refetch (or set the new
`me` data directly via `setQueryData`) before navigation, and add `home()` invalidation to
`useUpdateClientEmail` for consistency.

## Info

### IN-01: `PaymentReturnScreen` reads `idempotency_key` into an unused variable

**File:** `apps/client-pwa/src/routes/PaymentReturnScreen.jsx:35`

```js
const _idempotencyKey = params.get('idempotency_key');
```

Read and never used. The doc comment claims it is "stored so retry flows can read it back,"
but no retry flow consumes it — dead today. Either wire it into a retry path or drop the
read so the code does not imply behavior that does not exist.

### IN-02: `subTotalDays` whole-day rounding can diverge from the server `daysUntilEnd` by a day

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:20-26`

`sub.total` is computed in JS via `Math.round((end - start) / 86_400_000)` over UTC-midnight
date strings, while the numerator `daysUntilEnd` comes from SQL `end_date - now()::date` in
Moscow TZ (repository.py:191). Two different rules for numerator and denominator can produce
a 1-day discrepancy or a momentary >100% on boundary days. Cosmetic — `pct` is clamped to
`[2,100]`.

### IN-03: Demo/mock fallback branches remain in the production checkout sheet

**File:** `apps/client-pwa/src/screens/sheets/CheckoutSheet.jsx:91-108`

`forceOutcome` and the `!ctx.planId` branch inject 1300ms-delayed synthetic error states in
the shipping checkout component. Harmless (require a falsy `planId` or an explicit tweak)
but they widen the production payment path's surface; consider gating behind an explicit dev
flag.

### IN-04: `goal` column length leaves little headroom for future enum values

**File:** `apps/backend/alembic/versions/0048_client_onboarding_fields.py:27`

`goal` is `String(16)` and the ORM `SAEnum(ClientGoal, length=16)` matches; the CHECK
enforces the 4 current values. The longest value (`lose_weight`, 11 chars) fits, but any
future enum addition longer than 16 chars would silently truncate / fail the CHECK — re-check
the length when extending. No action now.

### IN-05: `cast(Any, row)["key"]` pattern defeats mypy across the list mappers

**File:** `apps/backend/app/modules/client_portal/service.py:282-388`

The list mappers lean on `cast(Any, row)["key"]`, erasing type checking on raw-SQL row
dicts. This is a pre-existing file convention, not introduced by this phase; the new
`get_client_me` (lines 134-144) uses a cleaner `r: dict[str, Any] = row; r.get(...)` style
worth standardizing on. No correctness impact.
