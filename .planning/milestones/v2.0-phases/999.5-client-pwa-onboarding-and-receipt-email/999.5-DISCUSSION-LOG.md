## Email-timing contract

### Q1 — Resolve "email gate BEFORE payment" vs "receipt screen AFTER"

| Option | Description | Selected |
|--------|-------------|----------|
| Email up-front, receipt screen = confirm | Collect email before payment, write client.email, ЮKassa sends receipt; post-payment screen confirms/edits. Preserves 54-ФЗ + current gate. Matches ROADMAP proposal. | ✓ |
| Receipt screen = gate BEFORE redirect | Keep gate; on `client_email_required` show the receipt screen before the redirect, collect → save → retry checkout. | |
| Relax gate, receipt after payment | Allow payment without email; collect after success and send via ЮKassa receipts API. Closest to mockup but risks 54-ФЗ. | |

**User's choice:** Email up-front, post-payment screen = confirmation (D-01).

### Q2 — Where to collect email up-front

| Option | Description | Selected |
|--------|-------------|----------|
| Questionnaire + pre-checkout gate (fallback) | Add email to onboarding AND a one-time gate before first checkout. Covers all cases. | |
| Pre-checkout gate only | Leave questionnaire faithful to mockup; collect email via the receipt-email screen before the first payment. | ✓ |
| Questionnaire only | Add email to onboarding; no separate gate. Risk: skippers / existing clients still block. | |

**User's choice:** Pre-checkout gate only — questionnaire stays mockup-pure (D-02).

### Q3 — Behavior when client ALREADY has email

| Option | Description | Selected |
|--------|-------------|----------|
| Skip gate, show post-screen | If email present → skip pre-checkout gate; always show post-payment confirmation. Matches D-01. | ✓ |
| Skip gate, post-screen first time only | Skip gate; show post-payment screen only on first payment / freshly-collected email. | |

**User's choice:** Skip gate when email present; post-payment confirmation always shown (D-03).

## Onboarding trigger & routing

### Q1 — How the client reaches the questionnaire

| Option | Description | Selected |
|--------|-------------|----------|
| Auto on 1st newbie login + Home button | Auto-redirect on first login for newbie+empty-profile, plus re-entry via onboarding-strip on Home. | ✓ |
| Home button only | No auto-redirect; entry only via onboarding-strip. | |
| Auto on 1st login, no button | Auto-redirect only; no re-entry (edit via ProfileScreen). | |

**User's choice:** Auto-redirect on first newbie login + manual re-entry from Home (D-04).

### Q2 — What marks onboarding "do not auto-show again" + Skip behavior

| Option | Description | Selected |
|--------|-------------|----------|
| Backend flag (completed/deferred) | `onboarding_completed_at`; both «Готово!» and «Пропустить» set it. Survives device change. | ✓ |
| Derived signal from profile | Auto-redirect while profile empty; any saved field stops it. Skip-without-save re-shows next session. | |
| localStorage in frontend | Persisted dismissal flag in localStorage; no backend change but not cross-device. | |

**User's choice:** Backend flag, set by both finish and skip (D-05).

## Receipt-email screen logic

### Q1 — What «Отправить чек» does on the post-payment screen when the address is edited

| Option | Description | Selected |
|--------|-------------|----------|
| Update email for future (no re-send) | Show "sent to X"; editing updates client.email for future; current receipt not re-sent. | |
| Update + re-send receipt | Update email AND trigger a second-receipt send to the new address (ЮKassa receipts API). | |
| Show only, no editing | Info-only screen ("чек отправлен на X" + «Хорошо»); no field/editing at all. Departs from mockup. | ✓ |

**User's choice:** Post-payment screen is info-only, no editing (D-09). → The full mockup UI moves to the pre-checkout gate.

### Q2 — On the gate, what does «Чек не нужен» do (email mandatory for 54-ФЗ)?

| Option | Description | Selected |
|--------|-------------|----------|
| Remove the button on the gate | Email mandatory; only «Продолжить к оплате» proceeds. Honest but departs from mockup. | |
| «Чек не нужен» = cancel payment | Button stays but means "cancel online payment" / back to checkout. | |
| Keep as in mockup | Button proceeds to payment without email — requires relaxing the gate. | ✓ |

**User's choice:** Keep as in mockup → triggered a contradiction with D-01/D-03 (email mandatory). Surfaced to the user with the phone-receipt-fallback insight; resolved in the reconciling question below.

### Q3 (reconciling) — Reconcile «Чек не нужен» with mandatory fiscal receipt

| Option | Description | Selected |
|--------|-------------|----------|
| Email optional, fallback to phone | Rewrite gate to "email OR phone"; «Чек не нужен» → receipt to phone (SMS). Button stays honest. Needs ЮKassa phone-receipt verification. | ✓ |
| Email mandatory — remove button | Keep D-01/D-03; hide «Чек не нужен». | |
| Email mandatory — button = cancel | Keep D-01/D-03; «Чек не нужен» cancels online payment. | |

**User's choice:** Email optional with phone fallback (D-10) — the load-bearing decision that reshapes the email contract; supersedes the "gate unchanged / mandatory" part of D-01.
