<objective>
Implement server-authoritative bonus redemption end-to-end on the backend: clamp the requested
redeem at checkout, persist it on the payment row, and on payment.succeeded write the negative
ledger debit idempotently + overdraft-clamped while fixing the promo discount attribution so
stacked promo+bonus payments are correct.

Purpose: This is the REDM-01/REDM-02 core. D-06 holds — the client only sends a desired amount;
every authoritative number is server-computed; the debit lands only on the webhook.
Output: record_loyalty_redemption service fn, online_payments plumbing, checkout clamp logic,
the webhook redemption block + promo-attribution fix, and the regression test suite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PWA client → checkout API | Untrusted `loyaltyRedeemKopecks` (desired amount) crosses here; server must cap it |
| checkout core → online_payments row | Server-computed redeem persisted; client cannot write this column |
| YooKassa webhook → ledger | Only payment.succeeded triggers the debit; replays must be safe |
| principal → own balance | Redemption must only touch the principal's own client_id (IDOR) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-83-04 | Tampering | discount amount | mitigate | Server caps discount = min(requested, balance, post_promo_price-1) in client_checkout_*; client only sends a desired loyaltyRedeemKopecks (D-06). The charged amount and persisted redeem are server-computed |
| T-83-05 | Elevation/Spoofing | double-spend / overdraft | mitigate | (a) Partial UNIQUE on online_payment_id WHERE redemption + on_conflict_do_nothing → one debit per payment; (b) record_loyalty_redemption re-reads SUM balance and clamps actual_debit = min(stored, balance) so concurrent checkouts can't each drain the same balance and the ledger never goes negative |
| T-83-06 | Tampering | webhook replay | mitigate | record_loyalty_redemption is idempotent (index_elements + index_where on_conflict_do_nothing); replaying payment.succeeded inserts nothing and emits no second audit |
| T-83-07 | Information Disclosure | anti-oracle return screen | mitigate | Redemption row written ONLY on payment.succeeded; no debit on cancel/no-pay (D-06); return screen never confirms the debit before the webhook (enforced in Plan 03 UI) |
| T-83-08 | Repudiation | attribution correctness | mitigate | promo_discount = plan_price - amount - loyalty_redeem (fix); no negative amounts (max(0,...) / max(1,...) floors); regression test asserts both rows |
| T-83-09 | Elevation | IDOR | mitigate | record_loyalty_redemption uses row.client_id from the persisted online_payment (server-owned); checkout balance read uses client.id from require_client() principal only |
| T-83-SC | Tampering | npm/pip/cargo installs | accept | No new package installs — uses existing sqlalchemy/structlog/audit infra |
</threat_model>
