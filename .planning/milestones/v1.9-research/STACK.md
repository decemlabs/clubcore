## 1. Postman v2.1 Collection Generation

### Tool: `openapi-to-postmanv2@6.0.1`

**Recommended install:** workspace-level devDep (not npx) so the version is locked in `pnpm-lock.yaml`
and CI always uses the same converter binary.

```bash
pnpm add -Dw openapi-to-postmanv2 newman
```

This puts both tools in the root workspace `node_modules/.bin/` and pins them in `pnpm-lock.yaml`.

**Why `openapi-to-postmanv2` and not alternatives:**

- It is the official Postman Labs converter (`github.com/postmanlabs/openapi-to-postman`). The v1.6
  handoff collection at `.planning/handoff/v1.6-postman.json` already uses Postman schema
  `https://schema.getpostman.com/json/collection/v2.1.0/collection.json` — this tool produces exactly
  that format.
- `postman-codegen` does not exist as a published npm package (confirmed via `npm view`).
- The Postman GUI "Import from OpenAPI" does the same conversion interactively, but is not scriptable
  for CI.
- Current version is `6.0.1` (confirmed via `npm view openapi-to-postmanv2 dist-tags.latest`).

**Conversion command** (to add as pnpm script in root `package.json` or as a make target):

```bash
npx openapi2postmanv2 \
  -s apps/backend/openapi.json \
  -o .planning/handoff/clubcore-v1.11.postman_collection.json \
  -p \
  -O folderStrategy=Tags,includeAuthInfoInExample=false,requestParametersResolution=Example
```

Flags:
- `-p` — pretty-print JSON (human-readable diff)
- `folderStrategy=Tags` — groups requests by the OpenAPI `tags` field; this is why Phase 64 (Contract
  Freeze) must add `tags=[...]` to every route BEFORE Phase 65 generates the collection. Without tags,
  all requests land in a flat "default" folder.
- `includeAuthInfoInExample=false` — suppresses cookie credentials from example bodies (clean handoff)
- `requestParametersResolution=Example` — populates request bodies with example values rather than
  schema types

**Integration with the drift gate:** The converter reads `apps/backend/openapi.json` (the byte-stable
output of `apps/backend/scripts/export_openapi.py`). No changes to `export_openapi.py` are needed —
the curated spec (Phase 64) becomes the input; the converter is a downstream consumer. The resulting
`.planning/handoff/clubcore-v1.11.postman_collection.json` is a committed artifact (not gitignored),
analogous to the existing `v1.6-postman.json`.

**What the existing v1.6 collection shows:** The existing `.planning/handoff/v1.6-postman.json`
(145 KB, 74 leaf items) was generated by a prior manual process. The v1.11 collection will be larger
(54+ endpoints) and must be regeneratable deterministically from the curated `openapi.json`. The
conversion command above should be run once in Phase 65 and the output committed.

## 2. Newman CLI Smoke Runner

### Tool: `newman@6.2.2`

**Current version:** `6.2.2` (confirmed via `npm view newman dist-tags.latest` and local installed
version check). No version jump needed — 6.x is stable.

**Install:** same workspace devDep install as above (`pnpm add -Dw newman`).

**Why devDep and not `npx`:** Newman in CI needs a pinned version to be reproducible.
`npx newman@6.2.2 run ...` works but is slower (cache miss on cold runner) and doesn't appear in
`pnpm-lock.yaml`. A workspace devDep is simpler.

**Smoke invocation** (to add to CI workflow or `package.json` scripts):

```bash
newman run .planning/handoff/clubcore-v1.11.postman_collection.json \
  --environment apps/backend/newman-env.json \
  --reporters cli,junit \
  --reporter-junit-export .planning/handoff/newman-results.xml \
  --bail
```

Newman environment file `apps/backend/newman-env.json` (committed, no secrets):
```json
{
  "name": "clubcore-local",
  "values": [
    {"key": "base_url", "value": "http://localhost:8000", "enabled": true},
    {"key": "owner_email", "value": "owner@fixture.local", "enabled": true},
    {"key": "owner_password", "value": "ownerpass123", "enabled": true}
  ]
}
```

**Scope of the Newman smoke:** Not a full integration test suite — that is the role of `pytest`.
Newman verifies reachability and contract shape (status codes, response schema presence) for the 10–15
most critical endpoints: healthz, login, clients list, memberships list, membership sell, check-in,
reports revenue. Authentication (httpOnly cookies) requires pre-request scripts; the v1.6 collection
already shows how the `Set-Cookie` header is captured in environment variables between requests.

**CI integration:** Newman smoke runs against `docker compose up` with a seeded DB. It is NOT a CI gate
on every push (too slow + requires running Postgres + Redis). It is a local operator-runnable smoke for
Phase 67 walkthroughs. If a CI gate is desired, it runs in a separate CI job with `services:` (Postgres
+ Redis) that mirrors the test job setup — same as `pytest` but driven by Newman JSON.

## 3. Private OpenAPI Doc-Site

### Tool: `@redocly/cli@2.31.4`

**Recommendation: Redocly CLI, not Stoplight Elements, not swagger-ui-watcher.**

**Why Redocly CLI:**

- Single binary, zero config for basic use. `npx @redocly/cli preview-docs apps/backend/openapi.json`
  starts a hot-reloading server on `http://localhost:8080`. No HTML wrapper, no webpack config.
- Actively maintained (2.31.4 released 2025, confirmed via npm registry). Official GitHub at
  `github.com/Redocly/redocly-cli`.
- Reads the `openapi.json` directly — no copy or symlink needed. Hot-reload picks up spec changes
  on save.
- The doc-site is gitignored by definition: it is not a build artifact, it is a live preview of the
  committed spec. No generated HTML to track.
- Docker image (`redocly/cli`) is also available if a container-isolated preview is preferred:
  `docker run --rm -v $(pwd):/spec -p 8080:8080 redocly/cli preview-docs /spec/apps/backend/openapi.json`

**Why not Stoplight Elements (`@stoplight/elements@9.0.19`):**

- Elements is a React component library for embedding in an existing HTML page. Requires setting up
  an HTML wrapper + serving it. More moving parts for a private local-only doc-site.
- Better fit when embedding docs INTO an existing web app (e.g., a React admin panel). Not suited for
  standalone local preview.

**Why not `swagger-ui-watcher`:**

- Last published 2021, no updates since. SwaggerUI itself is fine but `swagger-ui-watcher` is
  unmaintained scaffolding. Redocly CLI supersedes it for the local-preview use case.

**Install (workspace devDep, optional — npx is fine for one-off use):**

```bash
pnpm add -Dw @redocly/cli
```

Or just `npx @redocly/cli@2.31.4 preview-docs apps/backend/openapi.json` per the operator runbook.
No config file needed for basic preview. If linting rules are desired in Phase 64 (Contract Freeze),
add a minimal `redocly.yaml` at the repo root:

```yaml
# redocly.yaml — minimal lint config for Phase 64 contract freeze
apis:
  clubcore:
    root: apps/backend/openapi.json
rules:
  operation-operationId: error
  tag-description: warn
  operation-summary: warn
```

This lets `npx @redocly/cli lint apps/backend/openapi.json` enforce that every operation has an
`operationId` — which is required for the Postman collection to produce clean folder names. Running
this as a CI gate (Phase 64) is a zero-infrastructure addition: same CI job, one extra step.

**Gitignore note:** The doc-site is served in-memory (hot reload). No build artifacts. Nothing to
gitignore beyond the optional `redocly.yaml` (which should be committed if used for linting).

## 4. MailHog `--profile dev` for Email Walkthrough

### Image: `mailhog/mailhog:latest`

**MailHog is not a new code dependency** — it is a docker-compose service addition under a `dev`
profile. No Python package, no npm package.

**Why MailHog:**

- SMTP trap server: accepts all mail on port 1025, provides a web UI on port 8025 for visual
  inspection. Zero configuration for the backend — just point `EMAIL_SMTP_HOST=mailhog` +
  `EMAIL_SMTP_PORT=1025`.
- However: the existing email integration (`app/integrations/email/`) uses **Yandex Cloud Postbox via
  aioboto3 SES-V2 API** — NOT SMTP. MailHog is a SMTP server and cannot intercept SES-V2 API calls.

**Critical constraint:** MailHog works ONLY if the email integration adapter has a SMTP path. The
current `EmailClient` (`app/integrations/email/client.py`) uses `aioboto3.Session.client("sesv2")`.
The `SandboxEmailClient` already provides a no-op stub that logs to structlog. There are two options:

**Option A (recommended): Use the existing `SandboxEmailClient` for the operator walkthrough.**
Set `EMAIL_PROVIDER=sandbox` in `.env` (or `docker-compose.override.yml`). The ARQ worker logs rendered
email envelopes at INFO with full `to`, `subject`, `text_preview`. The operator reads structlog output
in the docker-compose log stream instead of a browser UI. This requires ZERO new code or infra.

**Option B: Add a real SMTP adapter path + MailHog container.**
This requires adding an SMTP send path to the email integration (e.g., `aiosmtplib` Python package +
`SmtpEmailClient` class) and wiring a `provider='smtp'` branch in `factory.py`. MailHog then catches
the SMTP traffic and shows it at `http://localhost:8025`. This is a non-trivial code addition
(new adapter class, new config fields, new tests) and is out of scope for a "backend-only, no new
business features" milestone.

**Recommendation: Option A (SandboxEmailClient) for Phase 67 runbook.** The structlog output already
satisfies the evidence-capture requirement. If the team later wants MailHog visual evidence, that is a
v2.0 dev-experience task.

**IF MailHog is nonetheless required** (e.g., Phase 67 requirement is explicitly a browser-visible
email UI), the docker-compose addition is:

```yaml
# Append to apps/backend/docker-compose.yml
  mailhog:
    image: mailhog/mailhog:latest
    profiles: ["dev"]
    ports:
      - "1025:1025"   # SMTP trap
      - "8025:8025"   # Web UI at http://localhost:8025
```

And would require a new `SmtpEmailClient` adapter (tracked separately, out of v1.11 scope unless
the SMTP adapter path is explicitly added).

**Docker Compose profiles:** `docker compose --profile dev up` brings up all services including
`mailhog`. `docker compose up` (without profile) runs the production service set and skips MailHog.
This is the correct isolation pattern for dev-only services.

## 5. Idempotency-Key Hardening (CR-01/02/02b)

### Tool: Custom dependency — `app/core/idempotency.py` (already exists)

**No new package needed.** The idempotency machinery is fully implemented:

- `app/core/idempotency.py` (210 lines): `begin_idempotency`, `store_idempotency_response`,
  `load_idempotency_response`, `idempotent_response`, `verify_idempotency` dependency.
- Redis key shape: `cc:idem:{method}:{path}:{header_value}`. Route-bound (D-32-19 / D-33-16 / CR-01).
- TTL: `IDEMPOTENCY_TTL_SECONDS = 3600` (1 hour). SET NX in-flight placeholder + JSON envelope storage.
- Replay: returns `IdempotencyEnvelope` with `status_code + body_b64 + body_hash` — verbatim response replay.

**What CR-01/02/02b actually requires (from PROJECT.md context):**

- **CR-01:** Route-binding bug in original `verify_idempotency` — FIXED already (returns
  `f"{method}:{path}:{key}"` since D-33-16 fix). Verify this fix is in production paths.
- **CR-02:** Standardize `Idempotency-Key` as an OpenAPI `components/parameters/IdempotencyKey`
  reusable parameter instead of inline per-endpoint. This is a spec curation task (Phase 64),
  not a code task.
- **CR-02b:** Audit which mutating endpoints SHOULD require `Idempotency-Key` but currently don't.
  The existing `verify_idempotency` dependency is only wired to the ЮKassa online payment endpoints.
  Cash sale endpoints (`POST /api/v1/sales/*`), refund endpoints, and certain notification endpoints
  may be candidates. This is an audit + `Depends(verify_idempotency)` addition task, not a new library.

**IETF draft alignment:** The IETF draft `draft-ietf-httpapi-idempotency-key-header` (latest: -07 as
of datatracker 2024) specifies:
- Header name: `Idempotency-Key` (mixed case; HTTP headers are case-insensitive; the existing code
  reads `request.headers.get("idempotency-key")` which is correct — ASGI lowercases all headers).
- Key validity: the draft recommends UUIDv4 but allows implementation-defined formats. The existing
  `IDEMPOTENCY_KEY_PATTERN = r"^[A-Za-z0-9_:-]{1,128}$"` is broader than UUIDv4 but valid for a
  private API.
- Cache window: the draft does not mandate 24h; 1h (current TTL=3600) or 24h (86400) are both
  reasonable. The existing ЮKassa webhook uses `ex=86400` for the dedup window; the general
  idempotency cache uses `ex=3600`. **CR-02b should standardize on 24h (86400s)** to match the
  webhook discipline and give clients a consistent replay window.

**What to change in code for hardening:**

```python
# app/core/idempotency.py — only change needed
IDEMPOTENCY_TTL_SECONDS: int = 86400  # 24h, aligning with ЮKassa webhook discipline
```

This is the only code change. Everything else (verify, begin, store, load, replay) is already correct.

**No external package (`fastapi-idempotency`, `fastapi-idempotent`, `idemptx`):** These packages are
low-adoption (latest `fastapi-idempotent` is `0.0.3`, `idemptx` is `0.2.2`), add transitive
dependencies, and provide no capability beyond what `app/core/idempotency.py` already implements.
The existing code is tested, production-proven (used by ЮKassa webhook since v1.7), and follows the
codebase conventions (structlog, typed Redis, route-bound keys). Do not replace it.

## 6. Tech-Debt Sweep: Ruff + Mypy (DEFER-46-04)

### No new tools needed — clean up with existing tools

**Current state (as of 2026-05-26, verified by direct run):**

| Tool | Status | Count |
|---|---|---|
| `ruff check` | 158 errors | Fully auto-fixable subset: ~80 (`[*]` flagged); remainder manual |
| `ruff format --check` | 297 files would be reformatted | All auto-fixable |
| `mypy app` | 11 errors in 7 files | Mix: Literal narrowing (4 errors) + attr-defined (4 errors in auth models) |

**Ruff errors breakdown:**
- `RUF100` (42): unused `# noqa` annotations — auto-fix with `ruff check --fix`
- `F401` (21): unused imports — auto-fix
- `E501` (14): lines too long — manual (may require restructuring)
- `F811` (13): redefined-while-unused — may need manual resolution (test fixtures)
- `RUF059` (12): unused unpacked variables — manual
- `RUF002` (11): ambiguous Unicode in docstrings — manual (Cyrillic characters in comments)
- `I001` (10): unsorted imports — auto-fix
- Remaining ~45: various, mix of auto-fixable and manual

**Mypy errors breakdown (confirmed via `uv run mypy app`):**

Four `attr-defined` errors in `app/modules/auth/models.py` — the `User` model does not have `__all__`
or explicit re-export, causing `Module "app.modules.auth.models" does not explicitly export attribute
"User"` in four call-sites (`telegram_service.py`, `service.py`, `users/router.py`, `auth/router.py`).
Fix: add `__all__ = ["User", ...]` to `app/modules/auth/models.py`.

Four `arg-type` errors in online payments / refunds — `Literal['redirect', 'qr']` narrowing mismatches
in `online_payments/router.py` (4 callsites) and `online_refunds/settle.py` (1 callsite). Fix: narrow
the type at the boundary (add explicit `cast()` or fix the Pydantic model discriminator).

**Pre-commit hooks: NOT recommended.** The project does not use `pre-commit`. Adding it now introduces
a new tooling layer for a "no new tools" milestone. The existing CI gates (`ruff check`, `ruff format
--check`, `mypy app`, `lint-imports`) are the enforcement layer. The tech-debt sweep in Phase 63 is a
one-time batch fix, not a recurring gate change. The CI already fails on ruff/mypy errors — that IS
the pre-commit equivalent.

**Sweep order for Phase 63:**

1. `uv run ruff check --fix app tests` (auto-fix `[*]` errors: RUF100, F401, I001, F541, UP017, UP037)
2. `uv run ruff format app tests` (auto-format all 297 files)
3. Fix `app/modules/auth/models.py` `__all__` (resolves 4 mypy attr-defined errors)
4. Fix Literal narrowing in `online_payments/router.py` + `online_refunds/settle.py` (5 mypy arg-type errors)
5. Manual review of `E501` / `RUF059` / `RUF002` — accept or suppress with documented `# noqa`
6. `uv run mypy app` → 0 errors
7. `uv run ruff check app tests` → 0 errors (or only documented suppressed)
