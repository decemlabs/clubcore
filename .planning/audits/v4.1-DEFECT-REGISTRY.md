# v4.1 Defect Registry

**This is the single, authoritative defect registry for the v4.1 Codebase Hardening milestone.**
It is produced once by the read-only audit (Phase 122) and frozen at the end of that phase
(`frozen_at_commit` / `frozen_at` / `row_count_at_freeze` above are populated at freeze, in
Phase 122's final plan — see `tools/audit/README.md` for the staging→merge→freeze protocol).

Rows are never written here directly. Each of the three audit sub-passes appends rows to its
own staging file under `.planning/audits/staging/`, and `tools/audit/merge-registry.mjs` performs
the concurrent-write merge into the three tables below (D-122-04).

## Schema legend

Every row carries exactly these 11 columns, in this order:

1. `id` — category-prefixed, sequential, permanent once written (e.g. `V41-FUNC-001`, `V41-HYG-001`, `V41-INFRA-001`). Never renumbered, even if a row is later reclassified — record the reclassification in the row instead.
2. `category` — one of `FUNC` / `HYGIENE` / `INFRA`. This is the column `merge-registry.mjs` uses to route the row into its table — not the staging file it came from.
3. `severity` — one of `Blocker` (crashes / unavailable / unusable) / `Major` (works incorrectly, no crash) / `Minor` (cosmetic, zero behavioral effect).
4. `anchor` — `path:line` or `path` + symbol identifying where the defect lives.
5. `repro` — the exact steps or command that reproduces the defect.
6. `evidence` — a re-runnable artifact: command + output, log path, screenshot path, or contract-test name. Prose alone is not accepted. At audit time this is the *discovery* evidence; at `fixed+verified` it is overwritten by the *fix* evidence.
7. `disposition` — one of three states: `open` (awaiting an owning phase), `fixed+verified` / `fixed+unverified` (transient — must become `fixed+verified` or `deferred` before milestone close), `deferred` (terminal, always paired with a `reason` of `operator-pending` / `out-of-scope` / `accepted-risk`).
8. `owning_phase` — the phase number responsible for resolving this row (123-127), or the phase that will forever leave it deferred.
9. `blocks/blocked_by` — cross-references to other row IDs this row blocks or is blocked by (e.g. shared-file serialization between Phase 124 and Phase 125).
10. `locked_invariant_risk` — `yes` if this row touches a locked-invariant mechanism (see `122-CONTEXT.md` § Locked-invariant mechanics), else `no`. `yes` rows are fixed first within their owning phase.
11. `reason` — required when `disposition` is `deferred`; one of `operator-pending` / `out-of-scope` / `accepted-risk`, with a short justification.
