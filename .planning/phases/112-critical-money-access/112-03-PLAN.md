<objective>
Frontend wiring for REF-01 + TEAM-01 against the two endpoints built in 112-01 and 112-02:

- **RefundModal** (`POST /api/v1/payments/{payment_id}/refund`): an owner-gated row action in
  BOTH Cashbox (`TransactionsCard`) and the Finance payments table opens a confirmation dialog
  with the original-payment summary, an editable amount (default = full, max = original) and a
  required reason textarea (≥3 chars). On success: Sonner toast + invalidate `paymentsKeys.lists()`
  so the cashbox/finance ledger re-renders with the new refund row. Removes the
  `T-103-03-FAKEREFUND` read-only stub. The action is HIDDEN (not disabled) for reception via
  `can(role, 'refund', 'finance')`, and not rendered on refund rows themselves.

- **ChangeRoleModal** (`PATCH /api/v1/users/{user_id}/role`): a new "Изменить роль" dropdown item
  in the Settings Team list (`SectionsBottom.tsx`) for active, non-self users, owner-gated by
  `can(role, 'update', 'users')`. The modal lets the owner pick the new role and confirms; success
  toast + `usersKeys.lists()` invalidation. Includes the "role applies on next login" info callout.

All visual/interaction details (tokens, modal structure, copy, validation states, toasts) are
fixed by 112-UI-SPEC.md — implement to that contract exactly. All Russian strings come from the
UI-SPEC Copywriting Contract.

Purpose: deliver the user-facing P0 actions; close the milestone's two critical operational gaps.
Output: 2 hooks + 2 new modal components + 3 trigger sites wired (cashbox, finance, settings).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser user → admin-app UI | UI gating (`can()`) is convenience only; the backend (112-01/112-02) is the security authority |
| admin-app → backend mutating endpoints | `staffRequest` attaches cookies + `X-CSRF-Token`; 401 → refresh→retry→session_expired handled by the transport seam |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-112-14 | Elevation of Privilege | reception sees refund/role actions | mitigate | Actions HIDDEN (not disabled) via `can(role,'refund','finance')` / `can(role,'update','users')`; backend is the real authority (403). Reception-hidden verified in the human-verify checkpoint step 6. |
| T-112-15 | Tampering | over-refund via UI bypass | mitigate | UI clamps amount ≤ remaining + disables confirm, but the BACKEND (112-01) is authoritative — `over_refund`/`already_refunded` 409s surface as toasts (the UI never assumes success). |
| T-112-16 | Spoofing / CSRF | mutating requests | mitigate | `staffRequest` auto-attaches `X-CSRF-Token` from `clubcore_csrf` for POST/PATCH; no manual handling, consistent with existing hooks. |
| T-112-17 | Information Disclosure | error-toast leakage | accept | Toasts are generic Russian copy mapped from typed ApiError codes; no backend internals exposed. |
| T-112-SC | Tampering | npm/pip/cargo installs | accept | No new dependencies — all primitives (AdaptiveModal, ModalInput, ModalTextarea, ChipGroup, DropdownMenu, Sonner) already exist (per 112-UI-SPEC Registry Safety). No legitimacy gate. |
</threat_model>
