<objective>
Backend for TEAM-01: expose `PATCH /api/v1/users/{user_id}/role` (body `{role}`) so the
owner can change a staff user's role (owner ↔ reception). The change persists immediately
and is audited; the new role is reflected on the target's NEXT login (existing sessions
keep the old role — NO session invalidation, per 112-CONTEXT.md). Reception is denied
(403) because `(Action.UPDATE, Resource.USERS)` is already in `OWNER_ONLY`.

Guards mirror the existing `deactivate_user` guard chain: reject changing one's own role
(`cannot_change_own_role`) and reject demoting the last remaining active owner
(`cannot_change_last_owner_role`), reusing the existing
`repository.count_active_owners_excluding` row-lock helper.

A new audit event `user_role_changed` is pre-registered in `LOCKED_AUDIT_EVENTS` and given
a `UserRoleChangedPayload` BEFORE any callsite (INFRA-15 discipline), or `audit.emit` raises
`AuditEventNotLockedError`.

Purpose: close the P0 access gap — owner-managed staff role changes.
Output: audit registration + payload + repo update + service guard chain + schema + endpoint
+ ASGITransport tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin-app client → PATCH /users/{id}/role | Untrusted role + user_id cross here; actor is an authenticated staff principal |
| service → users table (role column) | Privilege-defining mutation; must not lock out the last owner or self-escalate without audit |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-112-08 | Elevation of Privilege | PATCH /users/{id}/role | mitigate | `require_permission(Action.UPDATE, Resource.USERS)` (OWNER_ONLY) BEFORE `verify_csrf`; reception → 403. Reception-403 test in Task 3. |
| T-112-09 | Elevation of Privilege | self role change | mitigate | `CannotChangeOwnRoleError` 409 — an actor cannot change their own role (prevents self-lock or solo self-escalation games). Test in Task 3. |
| T-112-10 | Denial of Service | last-owner lockout | mitigate | `count_active_owners_excluding` row-lock guard + `CannotChangeLastOwnerRoleError` 409 — the gym can never be left with zero owners. Test in Task 3. |
| T-112-11 | Spoofing / CSRF | mutating PATCH | mitigate | `verify_csrf` requires `X-CSRF-Token` = `clubcore_csrf` cookie; missing → 403 csrf_mismatch. Test in Task 3. |
| T-112-12 | Repudiation | role-change accountability | mitigate | NEW LOCKED `user_role_changed` audit row (actor_user_id + changed_user_id + old_role + new_role) co-committed with the UPDATE; pre-registered per INFRA-15. Audit-row test in Task 3. |
| T-112-13 | Elevation of Privilege | stale-session role | accept | Role takes effect on next login (existing sessions keep old role) — explicit user decision in 112-CONTEXT.md; bounded by access-token TTL; no immediate session invalidation by design. |
| T-112-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed in this plan. No legitimacy gate required. |
</threat_model>
