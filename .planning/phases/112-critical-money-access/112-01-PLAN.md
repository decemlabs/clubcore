<objective>
Backend for REF-01: expose `POST /api/v1/payments/{payment_id}/refund` so the owner
can refund ANY recorded payment by its id, with a required reason and a refund amount
(partial allowed, `1 ≤ amount ≤ original`). This removes the root cause of the
`T-103-03-FAKEREFUND` read-only stub — there was previously no by-id refund endpoint.

Partial-refund architecture decision (per 112-CONTEXT.md, approaches a vs b): this
plan picks **approach (b)** — keep the frozen partial-UNIQUE `uq_payments_refund_of_alive`
and the `ck_payments_amount_sign_matches_subject_kind` CHECK unchanged, and support a
SINGLE refund per original sale of any amount `1 ≤ amount_kopecks ≤ original.amount_kopecks`.
Rationale: approach (a) would require dropping/replacing a frozen UNIQUE constraint on
a money ledger, risking the append-only audit-determinism and byte-parity invariants for
marginal gain. Approach (b) honors the user's partial-refund requirement (editable amount
field, ≤ original) with ZERO Alembic migration and ZERO change to frozen ledger constraints.
NO migration task is needed (REF-01 fits entirely inside existing schema).

Purpose: close the P0 money gap — owner-issued ledger refunds for arbitrary payments.
Output: schema + service fn + router endpoint + new exceptions + ASGITransport test suite.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin-app client → POST /payments/{id}/refund | Untrusted amount_kopecks + reason + payment_id cross here; actor is an authenticated staff principal |
| service → payments ledger (append-only) | Money mutation; must preserve append-only + unique-refund invariants |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-112-01 | Elevation of Privilege | POST /payments/{id}/refund | mitigate | `require_permission(Action.REFUND, Resource.FINANCE)` (OWNER_ONLY) declared BEFORE `verify_csrf`; reception → 403. Covered by reception-403 test in Task 3. |
| T-112-02 | Tampering | amount_kopecks (over-refund) | mitigate | Service validates `1 ≤ amount_kopecks ≤ original.amount_kopecks`; Pydantic `gt=0` blocks zero/negative; `OverRefundError` 409 on excess. Test in Task 3. |
| T-112-03 | Tampering | duplicate refund | mitigate | Frozen partial-UNIQUE `uq_payments_refund_of_alive` rejects a 2nd refund; IntegrityError discriminated → `AlreadyRefundedError` 409. Approach (b) keeps the constraint. Test in Task 3. |
| T-112-04 | Tampering | refund-of-refund | mitigate | Service rejects `original.subject_kind == 'refund'` → `CannotRefundRefundError` 409. Test in Task 3. |
| T-112-05 | Spoofing / CSRF | mutating POST | mitigate | `verify_csrf` requires `X-CSRF-Token` matching `clubcore_csrf` cookie; missing header → 403 csrf_mismatch. Test in Task 3. |
| T-112-06 | Repudiation | refund accountability | mitigate | `refund_issued` audit row (already LOCKED) emits actor_user_id + reason + amount + refund_of + payment_row_hash of original; co-committed in same UoW as the ledger insert. |
| T-112-07 | Information Disclosure | 404 vs 200 enumeration of payment ids | accept | Payment ids are server-generated UUIDs; the endpoint is owner-only; enumeration value is negligible vs the operational need to report "no such payment". |
| T-112-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed in this plan (all imports already in the backend deps). No legitimacy gate required. |
</threat_model>
