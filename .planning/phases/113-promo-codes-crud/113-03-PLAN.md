<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin-app UI → /api/v1/promo-codes | User input (modal form) serialized to the backend; staffRequest attaches the CSRF token |
| can()-gating | UI hides owner-only actions; backend OWNER_ONLY (113-01) is the real authority |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-03-01 | Elevation of Privilege | PromoCard actions + create button | mitigate | Actions rendered only when can(role,'create'|'edit'|'delete','promo-codes') — reception sees nothing. Defense-in-depth only; backend OWNER_ONLY is authoritative (a forged reception write still 403s). |
| T-113-03-02 | Tampering (CSRF) | create/edit/deactivate mutations | mitigate | All writes go through staffRequest which auto-attaches X-CSRF-Token from the clubcore_csrf cookie; no manual header handling. |
| T-113-03-03 | Tampering (client-side validation bypass) | PromoCodeModal | accept | Zod safeParse gates the form, but the backend schema validators + DB CheckConstraints (113-01) are the real enforcement; a bypassed client simply gets a 422/409. |
| T-113-03-04 | Spoofing/Drift | Zod wire schema vs real backend shape | mitigate | Schemas matched to the real camelCase wire from 113-01; the 113-02 used_count test parses a real response — closes the mock↔real drift lesson. |
| T-113-03-SC | Tampering | npm/pip/cargo installs | accept | No new packages — reuses existing zod/@tanstack/react-query/sonner/radix/lucide already in admin-app. |
</threat_model>
