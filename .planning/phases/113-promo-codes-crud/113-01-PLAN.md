<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin-app client → /api/v1/promo-codes | Untrusted JSON (create/edit payloads, query params) crosses into the backend |
| service → promo_codes table | Code normalization + alive-uniqueness enforced before persistence |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-113-01 | Elevation of Privilege | All write routes (create/edit/deactivate) | mitigate | require_permission(Action.{CREATE,EDIT,DELETE}, Resource.PROMO_CODES); the three pairs are in OWNER_ONLY → reception 403. Parity test asserts backend↔FE agreement. |
| T-113-02 | Tampering (CSRF) | POST/PATCH promo routes | mitigate | verify_csrf on every write; X-CSRF-Token (clubcore_csrf cookie) required. require_permission declared BEFORE verify_csrf (RBAC-04) so 401 precedes 403. |
| T-113-03 | Tampering (uniqueness/normalization bypass) | service.create/update | mitigate | code UPPER-normalized (strip+upper) before persist; partial-unique alive index uq_promo_codes_code_alive on upper(code) enforces uniqueness; IntegrityError → 409 promo_code_already_exists. |
| T-113-04 | Tampering (invalid discount injection) | schemas validators + DB CheckConstraints | mitigate | discount_value > 0 and (percentage ⇒ ≤ 10000) validated in PromoCodeCreate/Update schemas; DB CheckConstraints discount_value_positive + discount_type IN (...) are defense-in-depth; discount_type is Literal['percentage','fixed']. |
| T-113-05 | Tampering (validity-window tampering) | schemas | accept | valid_from/valid_until are optional datetimes; ordering (until ≥ from) enforced client-side per UI-SPEC; backend accepts any window — no security impact (a misordered window simply yields an inactive code at redeem time, already handled by existing validate_promo_code). |
| T-113-06 | Tampering (mass-assignment) | request DTOs | mitigate | BackendSchemaBase sets extra='forbid'; only whitelisted fields accepted; id/is_active/created_at/deleted_at not settable via create/edit payloads (is_active is owned by the deactivate route). |
| T-113-07 | Information Disclosure | GET list (reception reads) | accept | Reception retains (LIST, PROMO_CODES) per locked decision — promo codes are shown to clients in the app anyway; no secret data. |
| T-113-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed this phase — uses existing SQLAlchemy/FastAPI/Pydantic/alembic + existing admin-app deps. No supply-chain surface added. |
</threat_model>
