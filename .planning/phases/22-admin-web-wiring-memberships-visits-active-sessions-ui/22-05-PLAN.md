<objective>
Land FE-09 — active-sessions UI consuming Phase 23's HYG-03 endpoints (`GET /api/v1/auth/sessions` + `POST /api/v1/auth/sessions/{family_id}/revoke`) on a NEW `/_protected/profile` route accessible to BOTH roles. Phase 22 closes only after FE-09 ships per CONTEXT.md D-22-2.

Purpose: Owner/reception can audit and revoke their own session families. http-only per D-22-2 (no mock impl); blocked on Phase 23 main merge for the typed API surface.

**Routing decision (Warning 2 fix — locked here):** the existing `/_protected/settings` route is owner-only (verified — `settings.tsx:6-13` calls `can(role, 'view', 'settings')` and `redirect`s reception). Reception must be able to manage their own sessions, so SessionsList CANNOT live on /settings. We ship a NEW `/_protected/profile` route accessible to both roles. The route adds a `profile` resource to `can.ts` (both-roles viewable; not in OWNER_ONLY). Reception and owner reach /profile via the existing `<ProfileMenu>` dropdown link (preferred — no sidebar entry; profile is account-management surface, not navigation).

Output: New SessionsList + LogoutAllDialog components + sessionsHooks + auth contract extension + http auth service extension + profile route + ru.ts sessions keys + contract test uplift + can.ts/registry.ts profile resource entry. Atomic-commit-per-task per CD-02.

Per D-22-2 there is NO mock impl — `services.auth.sessions` and `services.auth.revokeSession` exist only as http impls and the mock implementation throws `mock_not_implemented` (RBAC-aware reads from a fake DB would not exercise the real refresh-rotation family invariant; the value is the integration test, not the mock storyboard). Per the locked-not-discussed list, `useLogoutAll` already exists in Phase 11; this plan REUSES it (wrapped in `LogoutAllDialog`) and does NOT touch the existing logout-all mutation hook.

**Warning 2 routing decision (LOCKED):** The original draft assumed FE-09 lives on /settings. Verified: `apps/admin-web/src/routes/_protected/settings.tsx` has `beforeLoad` that calls `can(role, 'view', 'settings')` and redirects when false. The current `can.ts` OWNER_ONLY matrix gates `'view', 'settings'` to owner only. Therefore a new `/profile` route is required. Adding `profile` as a non-owner-only resource keeps both roles in scope without weakening /settings. The Profile page surface (account management) is also a more accurate semantic fit than /settings (system settings) for own-account session controls.
</rationale>
