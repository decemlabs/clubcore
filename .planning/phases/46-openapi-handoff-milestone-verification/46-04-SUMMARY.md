# Phase 46 Plan 04: Postman v2.1 Collection Handoff — Summary

OpenAPI→Postman v2.1 converter (stdlib-only, byte-stable, lifespan-free) plus the generated `.planning/handoff/v1.6-postman.json` collection for the external design team, with the internal-only `/api/v1/_internal/email/webhook` endpoint filtered out per D-46-08.

## What Shipped

1. **`apps/backend/scripts/export_postman.py`** (196 LOC, stdlib only)
   - Mirrors the `export_openapi.py` shape verbatim: module docstring, cwd-independent `pathlib.Path(__file__).resolve().parents[N]` resolution, byte-stable JSON dump via `json.dumps(..., indent=2, sort_keys=True, ensure_ascii=False) + "\n"`.
   - Reads `apps/backend/openapi.json` (NOT `create_app().openapi()`) — avoids re-running FastAPI lifespan; uses the already-byte-stable artifact from Plan 46-01.
   - Walks `paths` in sorted order; for each path walks `HTTP_METHODS` in canonical order (GET, POST, PUT, PATCH, DELETE); skips operations whose `tags` list contains `'_internal'` (D-46-08).
   - Emits Postman v2.1 schema (`https://schema.getpostman.com/json/collection/v2.1.0/collection.json`) with folder hierarchy keyed by URL path segments (`api` → `v1` → `<module>` → leaf request).
   - Deterministic Postman item IDs via `uuid.uuid5(NAMESPACE_URL, f"{method}:{path}")` — same input → same UUIDs → byte-stable across runs.

2. **`.planning/handoff/v1.6-postman.json`** (145 370 bytes, 74 leaf request items)
   - Generated by running `cd apps/backend && uv run python -m scripts.export_postman`.
   - `_internal/email/webhook` ABSENT (verified `grep -c '_internal' .planning/handoff/v1.6-postman.json` returns 0).
   - v1.6 surface present: `password-reset/request`, `password-reset/confirm`, `users/invitations/accept` (all greppable via the `url.raw` field).
   - Top-level structure: 2 folders (`api/v1/...` hierarchy); 74 leaf requests; Postman v2.1 schema marker.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing critical functionality] Added Postman v2.1 `url.raw` field**

- **Found during:** Task 2 acceptance verification.
- **Issue:** Plan's Task 2 acceptance criteria requires `grep -c 'password-reset/request' .planning/handoff/v1.6-postman.json` ≥1 (substring match on the full path). The plan's reference implementation (mirroring `v1.4-postman.json:1-15`) stores URLs only as path-segment arrays (`"path": ["api","v1","auth","password-reset","request"]`), which means the literal substring `password-reset/request` never appears in the emitted JSON. The v1.4-postman.json reference itself does NOT satisfy this grep (verified: `grep -c 'password-reset/request' .planning/handoff/v1.4-postman.json` returns 0; v1.4 has no such endpoint, but the same pathological pattern applies to any multi-segment path in v1.4).
- **Fix:** Added a standard Postman v2.1 `url.raw` field (`"{{baseUrl}}<path>"`) alongside the segment array. This is canonical Postman convention (Postman GUI generates `url.raw` for every request; design-team consumers expect it for URL previewing). Output increased from ~140 KB to 145 KB.
- **Files modified:** `apps/backend/scripts/export_postman.py` (`_build_request`).
- **Commit:** Folded into Task 1 commit `96353ae`.
- **Threat model impact:** None. `url.raw` repeats the path that's already in `url.path` — no new information disclosure surface; filter still operates on tags before this field is constructed, so `_internal` operations are never reached.

### No other deviations

No bugs uncovered, no blocking issues, no architectural questions. The two-task plan executed exactly as scoped.
