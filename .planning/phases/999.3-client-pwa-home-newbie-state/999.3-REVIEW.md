# Phase 999.3: Code Review Report

**Reviewed:** 2026-05-31
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

This phase added a server-derived `membershipState` enum (`active` | `lapsed` | `newbie`) to `/client/home` and a newbie Home state in the PWA. The backend change is small and disciplined: `client_has_any_membership` is an IDOR-safe `EXISTS` query with a mandatory `:client_id` bind, and the ternary derivation in `get_client_home` is correct and well-tested (active / lapsed / newbie all covered by integration tests). No security issues were found — IDOR scoping, raw-SQL bind discipline, and client-safe projections all hold.

The defects are concentrated in the frontend: a type/wire-format mismatch in the `HomeData` interface that masks real fields behind `unknown`, a contract drift in `deriveOnboardingSteps` where the `title` no longer matches the `remaining` count for all step states, several derivation/grammar edge cases, and a few hardcoded demo values that leak into the genuine newbie state. None rise to BLOCKER — the membership-state core path is correct — but four warnings affect correctness of the onboarding UI and the type contract.

## Warnings

### WR-01: `HomeData` interface uses snake_case for two fields the backend never emits

**File:** `apps/client-pwa/src/lib/clientQueries.ts:78-84`
**Issue:** The backend serializes every wire field as camelCase (`ResponseData`/`ContractModel` set `alias_generator=to_camel`, confirmed in `app/core/schemas.py:24-28`). `ClientHomeResponse` therefore emits `nextBooking`, `expiringSoon`, `membershipState`. But the TS `HomeData` interface declares:

```ts
interface HomeData {
  membership: unknown
  next_booking: unknown      // never present on the wire — always undefined
  expiring_soon: boolean     // never present on the wire — always undefined
  membershipState: 'active' | 'newbie' | 'lapsed'
}
```

`next_booking` and `expiring_soon` will always be `undefined` at runtime. The consuming component reads the correct camelCase keys (`HomeScreen.jsx:172` `homeData?.nextBooking`, `HomeScreen.jsx:190` `homeData?.membershipState`), so the screen happens to work — but the interface is actively misleading: any future code that trusts these two typed fields gets silent `undefined`. The interface documents a contract that does not exist.

**Fix:** Align the interface with the wire contract:
```ts
interface HomeData {
  membership: unknown
  nextBooking: unknown
  expiringSoon: boolean
  membershipState: 'active' | 'newbie' | 'lapsed'
}
```

### WR-02: `deriveOnboardingSteps` title is hardcoded to "шага" and can disagree with the badge count

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:74-76`
**Issue:** The title is built as:
```js
const remaining = 4 - doneCount
const title = `Ещё ${remaining} шага до полного старта`
```
Two problems:

1. **Grammar:** `remaining` ranges over 0..3 (doneCount is 1..4 since Step 1 is always `done`). Russian plural for `1` requires "шаг", for `2-4` "шага", for `0` "шагов". With profile+booking done, `doneCount=3` → `remaining=1` → renders "Ещё 1 шага" (incorrect; should be "1 шаг"). When everything is done, `remaining=0` → "Ещё 0 шага" — nonsensical copy that still renders because `membershipState==='newbie'` keeps the strip visible even if profile and visit are complete.
2. **Counting model mismatch:** `remaining = 4 - doneCount` counts the `next` Step 2 (Абонемент) as "remaining", but Steps 3/4 being done can drive `remaining` to 1 while the strip still presents 4 chips. The badge (`${doneCount} / 4`) and the title use two different mental models, so they can read inconsistently to the user.

The existing test only asserts `title.toContain('3')` for the fresh-newbie case (`HomeScreen.adapters.test.jsx:129`), so the grammar break at `doneCount=3` is untested.

**Fix:** Use the project `plural` helper (CLAUDE.md lists `plural` in `src/shared/i18n`) or inline a pluralizer, and decide whether `remaining` should exclude the always-`done` account step:
```js
function pluralSteps(n) {
  const mod10 = n % 10, mod100 = n % 100
  if (mod10 === 1 && mod100 !== 11) return 'шаг'
  if (mod10 >= 2 && mod10 <= 4 && (mod100 < 12 || mod100 > 14)) return 'шага'
  return 'шагов'
}
const title = remaining > 0
  ? `Ещё ${remaining} ${pluralSteps(remaining)} до полного старта`
  : 'Почти всё готово'
```

### WR-03: `pct` progress can render a misleading bar when `daysLeft > total`

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:169`
**Issue:**
```js
const pct = sub.total > 0 ? Math.max(2, Math.min(100, (sub.daysLeft / sub.total) * 100)) : 0;
```
`total` is derived from `subTotalDays(startDate, endDate)` (whole days between start and end), while `daysLeft` comes from the server's `daysUntilEnd` computed against the current date in Europe/Moscow. These are computed from different reference points: if `start_date` is in the future, or if the server's `now()` clock and the membership `start_date` disagree, `daysUntilEnd` can exceed `(end_date - start_date)`. The `Math.min(100, ...)` clamps the visual width, but `sub.daysLeft` (the raw number) is still rendered as the big number (`HomeScreen.jsx:667`), so the bar reads "full / 100%" while the headline shows more days than the plan's nominal length — an inconsistent state for a freshly-purchased or future-dated membership.

**Fix:** Clamp `daysLeft` to `total` for display, or derive `total` as `Math.max(total, daysLeft)` so the ratio is never > 1 and the headline never exceeds the bar's implied span:
```js
const total = Math.max(subTotalDays(membership.startDate, membership.endDate), daysLeft);
```

### WR-04: Newbie strip stays visible for a `newbie` who has already completed Steps 3 and 4

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:190-200`
**Issue:** The render gate keys solely on `homeData?.membershipState === 'newbie'`. `membershipState` is `newbie` whenever the client has zero membership rows (`service.py:135`) — entirely independent of profile completeness or bookings. So a client who has filled their profile (`me.birthday` + `me.gender`) and already has a booking, but has never bought a membership, sees `doneCount=3`, `badge="3 / 4"`, `title="Ещё 1 шага…"` (see WR-02), and the full newbie hero ("Остался один шаг до зала"). That copy is arguably still correct (only the membership remains), but the onboarding strip presents three already-`done` chips plus the dismiss button, and the OnboardingStrip dismissal is component-local state (`useState`) — it resets on every remount/navigation (`HomeScreen.jsx:337`), so the user cannot durably hide a strip that is mostly complete. The interaction of "always-newbie until membership bought" + "non-persistent dismiss" means a near-complete newbie repeatedly sees a mostly-done onboarding card.

**Fix:** Either (a) persist the dismissed flag (localStorage, versioned per CLAUDE.md store convention) so dismissal survives remount, or (b) collapse the OnboardingStrip to a minimal "1 step left" form once `doneCount >= 3`. At minimum, document that dismissal is intentionally ephemeral if that is the design intent.

## Info

### IN-01: `subTotalDays` rounds instead of flooring whole-day spans

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:24`
**Issue:** `Math.round((end - start) / 86_400_000)` rounds the day span. Both bounds are parsed at `T00:00:00Z`, so the difference is always an exact multiple of 86.4M ms and `round` is harmless today — but if either input ever carries a time component (e.g. a future ISO datetime instead of date-only), `round` silently produces an off-by-one. `Math.floor` matches the documented "whole-day span" intent more defensibly.
**Fix:** Use `Math.floor` and keep the `Math.max(0, …)` guard.

### IN-02: `getSubInfo`-era `total: 90` hardcode removed but hero meta chips still hardcode catalog facts

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:306-312`
**Issue:** The newbie hero renders "3 тарифа" and "от 3 500 ₽/мес" as static strings. The comment at line 298 acknowledges these are "deferred: not wired to live catalog." If the gym has more/fewer than 3 plans or a different entry price, the hero lies to the user. This is a known deferral, flagged as INFO for tracking — it should be wired to `useClientPlans()` (already available in `clientQueries.ts:164`) in a follow-up.
**Fix:** Derive the count and min price from `useClientPlans()` data, or remove the specific numbers until wired.

### IN-03: `unread = 0` hardcoded notification count

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:144`
**Issue:** `const unread = 0;` with a comment that notifications are not in the API. This dead-constant drives badge logic across three variants (`unread > 0 ? unread : null`) that can never be true. Harmless now but it is dead conditional logic. Acceptable as a documented placeholder.
**Fix:** None required; revisit when the notifications API lands.

### IN-04: `greeting` uses a hardcoded `const h = 9` demo hour

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:147-153`
**Issue:** The time-of-day greeting is computed from a fixed `h = 9` ("demo time"), so every user always sees "Доброе утро" regardless of actual local time. The comment marks it demo, but this ships in the real wired screen (not a tweaks-gated demo path), so the greeting is effectively always wrong for non-morning users.
**Fix:** Use the real local hour: `const h = new Date().getHours()` (or Europe/Moscow per the date convention) so the greeting reflects actual time.

### IN-05: `UpcomingCard` / `HomeMinimal` countdown is a fixed fake interval, not derived from the real booking

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:843, 965`
**Issue:** `useCountdown(4 * 3600 * 1000 + 12 * 60 * 1000)` hardcodes "4h12m" for both the minimal hero countdown and the UpcomingCard "через {cd.primary}" label, even though a real `nextBooking.startTime` is now available from the API. The card shows a genuine `startTime`/`startDate` but a fabricated countdown next to it — internally inconsistent (e.g. "Сегодня в 18:00 · через 4ч 12м" when 18:00 is not 4h12m away). Pre-existing pattern, but the phase wired real booking data without reconciling the countdown.
**Fix:** Compute the countdown from `new Date(nextBooking.startTime).getTime() - Date.now()`.

### IN-06: Test only weakly asserts the newbie title ("contains 3")

**File:** `apps/client-pwa/src/screens/HomeScreen.adapters.test.jsx:129`
**Issue:** `expect(title).toContain('3')` is the only title assertion and it does not catch the grammar/count defects in WR-02 (it passes for "Ещё 3 шага"). No test covers `doneCount=3` (`remaining=1`) where the copy breaks. Test coverage gives false confidence on the title contract.
**Fix:** Add an assertion on the exact title string for the profile+booking-done case to lock the corrected pluralization.
