# Phase 83 — UI Design Contract

> Visual and interaction contract for the bonus-redemption additions to CheckoutSheet.
> Generated by gsd-ui-researcher; verified by gsd-ui-checker.
>
> **Scope boundary:** Only `apps/client-pwa/src/screens/sheets/CheckoutSheet.jsx`.
> This phase is NOT a new screen — it surgically modifies the EXISTING checkout surface.
> Three changes: (1) replace `BONUS_PLACEHOLDER` with real `useClientLoyaltyBalance()` data,
> (2) wire the redemption toggle so `bonusOn = true` sends `loyaltyRedeemKopecks` in the
> checkout request and shows an estimate discount line, (3) flip `clubBonuses` flag to `true`.
>
> **Existing surface is the design reference.** All CheckoutSheet visual conventions,
> CSS classes, spacing, and typography are pre-existing. This spec covers ONLY the delta —
> new elements or wiring changes. The promo discount line (`.co-sum-row.discount`) is the
> direct analog for the new bonus discount line.

## Component Inventory

> Phase 83 modifies CheckoutSheet.jsx in three targeted places. No new component files
> are created. All visual structure already exists in the JSX — the toggle UI is fully
> built behind `CHECKOUT_FEATURE_FLAGS.clubBonuses = false`. Changes are pure wiring.

### Change 1: Real balance from `useClientLoyaltyBalance()`

**Location:** Top of `ReviewStage` component body (alongside existing `useClientMe` call).

**Remove:** `BONUS_PLACEHOLDER = { balance: 1080, toGold: 220 }` constant (line 52).

**Add:** `const { data: loyaltyBalance, isLoading: loyaltyLoading } = useClientLoyaltyBalance()`
imported from `'@/data'` (Phase 82 hook). The hook returns `{ balanceKopecks: number }`.

**Balance derivation:**
```
const balanceKopecks = loyaltyBalance?.balanceKopecks ?? 0
```

**Toggle visibility rule:** Render the bonuses section only when `balanceKopecks > 0` AND
`CHECKOUT_FEATURE_FLAGS.clubBonuses === true`. When `balanceKopecks === 0` or loading, hide
the entire "Бонусы клуба" section (including the `co-sec-label` header). This avoids
showing a zero-balance toggle that the user cannot activate meaningfully.

**Loading state:** While `loyaltyLoading === true`, hide the section (same as balance = 0
behavior). No skeleton needed — the section simply does not render until data arrives.
This matches the CardSheet pattern: "no card = no section."

**Error state:** On fetch error (`loyaltyBalance === undefined` after loading), hide the
section silently. Same pattern.

---

### Change 2: Toggle wiring — send `loyaltyRedeemKopecks` + show estimate discount line

**Location:** `ReviewStage` component body and the existing `bonusOn` toggle handler.

**Estimate computation (D-06 compliant):**

The client computes a *display-only* estimate. It is presented as an estimate, not the
authoritative charged amount (the server recomputes authoritatively via REDM-01).

```
const bonusEstimateKopecks = bonusOn
  ? Math.min(balanceKopecks, total)   // total = post-promo amount (promoResult?.newAmountKopecks ?? ctx.amount)
  : 0
const estimatedTotal = total - bonusEstimateKopecks
```

`bonusEstimateKopecks` is ONLY for display. It is NOT used to modify `total` or `discount`
state variables — those remain server-derived. The `useCountUp` hook receives `estimatedTotal`
for the pay-bar animation when bonuses are ON, but the CTA label must reflect the estimate
with a qualifier (see Copywriting below).

**Checkout request wiring:**

In `launchCheckout()`, thread `loyaltyRedeemKopecks` into both checkout mutateAsync calls:

```javascript
// Only include when bonusOn and balance > 0
...(bonusOn && balanceKopecks > 0 ? { loyaltyRedeemKopecks: balanceKopecks } : {})
```

The wire field `loyaltyRedeemKopecks` (camelCase) maps to the backend's
`ClientCheckoutRequest.loyalty_redeem_kopecks`. Send `balanceKopecks` (the full balance)
as the desired redeem amount — the server caps it authoritatively per REDM-01.

**Toggle ON handler update:**

```javascript
onClick={() => {
  const next = !bonusOn
  setBonusOn(next)
  showToast(next ? 'Бонусы будут списаны при оплате' : 'Списание бонусов отменено')
}}
```

Note the updated toast copy ("при оплате" clarifies the estimate intent per D-06).

### Change 3: Bonus discount line in summary card

**Location:** Inside `.co-sum` card, below the existing promo discount row.

**Pattern:** Direct structural analog of the existing promo discount row:

```jsx
{/* Promo discount row — existing, unchanged */}
{discount > 0 && (
  <div className="co-sum-row discount">
    <span className="co-sl-tag">
      Промокод{' '}
      <span className="co-mini">{promoResult?._validatedCode ?? promoCode}</span>
    </span>
    <span className="co-sv">−{formatMoney(discount)}</span>
  </div>
)}

{/* Bonus discount row — NEW, added immediately after promo row */}
{bonusOn && bonusEstimateKopecks > 0 && (
  <div className="co-sum-row discount">
    <span className="co-sl-tag">
      Бонусы
      <span className="co-mini">~</span>
    </span>
    <span className="co-sv">−{formatMoney(bonusEstimateKopecks)}</span>
  </div>
)}
```

The `co-mini` chip shows `~` (tilde, U+007E) to signal "estimate" — a conventional
approximation marker in Russian financial UX that does not require additional explanation.
It reuses the `.co-mini` style (10px/800/uppercase, `var(--accent-soft)` bg,
`var(--accent-deep)` text) without any CSS modification.

**Stacking with promo:** When both a promo and bonuses are active, both rows render.
The savings bar total updates to reflect the combined discount:

```javascript
const totalDiscount = discount + bonusEstimateKopecks   // for savings bar display only
const savePct = estimatedTotal < ctx.amount
  ? Math.round(totalDiscount / ctx.amount * 100)
  : 0
const payPct = 100 - savePct
```

The savings bar legend ("Ваша выгода") shows `formatMoney(totalDiscount)` when active.

**Remove:** `BONUS_PLACEHOLDER.balance.toLocaleString('ru-RU')` and

**Replace with:**
```jsx
<div className="co-bonus-sub">
```

## Interaction Contract

### Toggle ON → estimate discount appears

- User taps toggle → `bonusOn` flips to `true`
- `.co-bonus-row discount` row appears immediately below the promo row (if any) in the
  summary card
- Summary savings bar updates to include the combined discount
- `useCountUp` re-animates the pay-bar total from `total` to `estimatedTotal` (440ms
  cubic-bezier — same animation used when promo is applied, inherited)
- Pay button label prepends `~` to signal estimate
- Toast: "Бонусы будут списаны при оплате" (2600ms auto-dismiss — same `.co-toast` mechanism)

### Toggle OFF → estimate discount removed

- `bonusOn` flips to `false`
- Bonus discount row disappears
- `useCountUp` re-animates pay-bar total back to `total` (post-promo amount without bonus)
- Pay button label: `~` removed
- Toast: "Списание бонусов отменено"

### Redemption + promo stacking

- Both discount rows render simultaneously, in this order:
  1. Promo discount row (only when `discount > 0`)
  2. Bonus discount row (only when `bonusOn && bonusEstimateKopecks > 0`)
- Savings bar shows combined discount percentage
- Each row uses the existing `.co-sum-row.discount` class — no new class needed

### Checkout submit with bonuses ON

- `launchCheckout()` includes `loyaltyRedeemKopecks: balanceKopecks` in the request body
- The server responds with a `confirmationUrl` — redirect proceeds identically to the
  non-bonus path
- The actual debit is written server-side on `payment.succeeded` webhook (REDM-02)
- The return screen makes no reference to bonuses (D-06 anti-oracle unchanged)

### Balance = 0 or loading

- Entire "Бонусы клуба" section (`.co-sec-label` + `.co-bonus` card) is not rendered
- No toggle, no balance display, no empty state
- Checkout flow is identical to the pre-Phase-83 behavior

### Feature flag gate

- `CHECKOUT_FEATURE_FLAGS.clubBonuses === true` after this phase flip
- The existing `{CHECKOUT_FEATURE_FLAGS.clubBonuses && ( ... )}` guard remains; the flag
  value is changed to `true`

## Data Contract (API → UI mapping)

| Source | Field | UI usage |
|--------|-------|----------|
| `GET /client/loyalty/balance` | `balanceKopecks: int` | Toggle subtitle: `formatMoney(balanceKopecks)`. Toggle visibility: show only when `> 0` |
| Computed client-side | `bonusEstimateKopecks = min(balanceKopecks, total)` | Estimate discount row amount. Pay button `~` prefix. Savings bar combined discount |
| Checkout request body | `loyaltyRedeemKopecks: int` (wire: camelCase) | Sent when `bonusOn === true && balanceKopecks > 0`. Value = `balanceKopecks` (full balance; server caps). Maps to `ClientCheckoutRequest.loyalty_redeem_kopecks` |

**`formatMoney` usage:** All kopeck→₽ display uses the existing `formatMoney` import from
`'@/utils/format.js'`. Never divide kopecks manually in the component.

**D-06 invariant:** `total` and `discount` state variables remain server-derived.
`bonusEstimateKopecks` is a separate local computation for display only. It does not
mutate `total` or `discount`.

## Implementation Notes for Executor

1. **No new CSS classes.** All visual primitives for the bonus section already exist in
   `styles.css`: `.co-bonus`, `.co-bonus-ring`, `.co-bonus-track`, `.co-bonus-prog`,
   `.co-bonus-coin`, `.co-bonus-text`, `.co-bonus-title`, `.co-bonus-sub`,
   `.co-bonus-switch`, `.co-bonus-knob`, `.co-sum-row`, `.co-sum-row.discount`,
   `.co-sv`, `.co-sl-tag`, `.co-mini`. Use them as-is.

2. **Hook import.** Add `useClientLoyaltyBalance` to the import from `'@/data'` at line 4.
   The hook was introduced in Phase 82 and follows the same shape as `useClientMe`.

3. **BONUS_PLACEHOLDER removal.** Remove lines 51-52 entirely. The `toGold` field is not
   used — the Gold tier display is deferred.

4. **Ring SVG unchanged.** Keep the `co-bonus-ring` SVG with its static `stroke-dashoffset: 45`.
   Do not compute a dynamic progress value — the Gold tier target for the ring computation
   is deferred. The ring serves as decorative chrome only in Phase 83.

5. **Estimate in `useCountUp`.** Pass `estimatedTotal` (not `total`) to `useCountUp` when
   computing `totalDisplay`. The `deps` array must include `bonusOn` and `bonusEstimateKopecks`
   so the animation re-fires when the toggle changes.

6. **Checkout hooks.** Both `checkoutMembership.mutateAsync` and `checkoutPtPackage.mutateAsync`
   spread the bonus field identically. The backend `ClientCheckoutRequest` schema accepts
   the optional `loyaltyRedeemKopecks` field beside `promoCode` and `savePaymentMethod`.

7. **State ordering.** Add `bonusEstimateKopecks` and `estimatedTotal` as derived constants
   (not state) after the existing `total` / `discount` derivations (line 152-153).
   Derived values, not `useState`, to keep state surface minimal.

8. **Savings bar.** Compute `savePct` from `totalDiscount` (promo + bonus combined) and
   `estimatedTotal` (not `total`). This means the savings bar always reflects the full
   visual discount the user sees.
