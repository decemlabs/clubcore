Build the heart of the phase: the `charge_expiring_autopay` ARQ cron and its caller-owns-txn
service helper that finds eligible expiring memberships, claims the period (double-charge
guard), initiates the off-session YooKassa charge against the saved card, creates the
`online_payments` row (only on a successful provider response) so the existing succeeded

idempotency (DB claim row + deterministic provider idempotency key) and a fully exercised

(autopay_charges.id) and enqueues the Plan 03 failure notification keyed on that id.

<architecture_note>
**Charge-ledger method + success-DM discriminator (planner decision — resolves a CONTEXT tension).**
CONTEXT locks both "charge-ledger method='autopay'" AND "reuse the succeeded webhook, no handler
changes". A strict literal reading is contradictory: the webhook hardcodes `method="online"` at
handlers.py:457. Resolution (Task 3): add ONE additive nullable discriminator column reused from
Plan 01 — the cron sets a marker the webhook reads to choose `method="autopay"` for the ledger row
AND to select the autopay success-DM copy. This does NOT change activation logic (D-06 webhook-locked
renewal is preserved verbatim) — it only changes the ledger `method` label and the notification kind.
The simplest carrier is the `online_payments.confirmation_type` value: the cron writes
`confirmation_type='autopay'` (off-session has no real redirect/qr confirmation), and the webhook maps
`confirmation_type == 'autopay'` → recorder `method="autopay"` + `kind="autopay_charge_succeeded"`.
This avoids a new migration while keeping the change additive and reversible.

**Failure-notification idempotency anchor (planner decision — resolves the cross-plan data contract).**
The SUCCESS notification fires from the payment.succeeded webhook, which DID create an online_payments
row, so it keeps online_payment_id-based idempotency (unchanged). The FAILURE notification fires on a
DECLINE, where NO online_payments row exists (yookassa_payment_id is NOT NULL — no row without a provider
payment id). Therefore the failure path keys idempotency on the always-present autopay_charges.id via
the dedicated autopay_charge_notifications(autopay_charge_id, kind, channel) UNIQUE claim table (Plan 01).
The cron returns the declined claim ids and enqueues dispatch_autopay_failure_notification(autopay_charge_id)
post-commit.
</architecture_note>
