<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser JS → backend API | untrusted client; CSRF double-submit + httpOnly session cookies cross here |
| `clubcore_csrf` cookie (JS-readable) → X-CSRF-Token header | the double-submit secret the transport must echo correctly |
| `cc_access` / `cc_refresh` (httpOnly) | session cookies JS must NEVER read or set — only `credentials:'include'` ferries them |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-100-03 | Spoofing/Tampering (CSRF) | `staffRequest` mutating-method path | mitigate | Read `clubcore_csrf` and set `X-CSRF-Token` on every POST/PUT/PATCH/DELETE; backend constant-time-compares and rejects mismatch with 403 `csrf_mismatch`. Unit test asserts the header is present and equals the cookie. |
| T-100-04 | Tampering (cross-principal cookie rotation) | `staffRefreshOnce` | mitigate | Refresh single-flights to `/api/v1/auth/refresh` ONLY (staff path), never the client `/api/v1/client/session/refresh` — prevents rotating the wrong principal's cookies (mirrors T-69-09). |
| T-100-05 | Information Disclosure (session leak on expiry) | 401 handling | mitigate | A second 401 throws `session_expired`; the QueryClient publishes once and the app redirects to `/login` (plan 100-03) without exposing stale data or crashing; `_redirecting` flag prevents a redirect loop. |
| T-100-06 | Elevation (httpOnly bypass) | cookie access | mitigate | Transport reads ONLY `clubcore_csrf` (non-httpOnly by design); `cc_access`/`cc_refresh` are never read or written by JS — they travel solely via `credentials:'include'`. |
</threat_model>
