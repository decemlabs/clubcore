<objective>
Deliver QR self check-in: a `require_client()`-gated `GET /client/qr-token` that mints a fresh ~60s signed token (no membership pre-check), and a token-as-credential `POST /client/check-in` (NOT `require_client()`-gated) that derives `client_id` strictly from the verified QR `sub` claim and creates a visit through the existing anti-fraud path with `channel='client_qr'`. This is the security-critical surface of the phase — anti-replay (expired token + daily-UNIQUE), token-confusion isolation (distinct typ/aud), and structurally-impossible cross-client check-in. Plan 01 supplied the token helpers + the `client_qr` channel migration; Plan 03 established the client_portal write endpoints this builds alongside.
Output: `create_visit_client_qr` wrapper in `visits/service.py` + its Protocol slot + main wiring; QR token + check-in schemas; qr-token issue + check-in endpoints; replay/cross-client/duplicate integration tests; one blocking human-verify checkpoint on the security behavior.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gym scanner → POST /client/check-in | UNAUTHENTICATED endpoint; the signed QR token is the sole credential |
| QR token → identity | client_id derives only from the verified sub claim — no body/path param |
| QR token ↔ access/refresh token | distinct typ/aud must make them non-interchangeable |
| repeated scans → visits table | TTL + daily-UNIQUE bound replay |
