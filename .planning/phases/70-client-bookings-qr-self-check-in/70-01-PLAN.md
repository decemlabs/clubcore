<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| token issuance → token verification | A signed QR token crosses from issuance (Plan 04) to a verifier; the token format/claims defined here are the security contract |
| migration → runtime DDL | The CHECK constraint defines which `channel` literals the DB will accept at insert time |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-70-01 | Spoofing | encode_qr_token / decode_qr_token | mitigate | HS256 signature over settings.secret_key; decode rejects InvalidTokenError -> "invalid_token". A forged/tampered token fails signature verification. |
| T-70-02 | Elevation of Privilege | decode_qr_token typ/aud assertion (D-70-08) | mitigate | Distinct typ='qr_checkin' + aud='qr'; decode asserts both. A leaked QR token cannot authenticate require_client(); an access/refresh token is rejected at decode_qr_token. Unit-tested in Task 1. |
| T-70-03 | Repudiation / Replay | exp claim + qr_token_ttl_seconds | mitigate | ~60s TTL; decode maps ExpiredSignatureError -> "token_expired". Replay window is bounded; daily-UNIQUE (Plan 04) blocks successful same-day replay. |
| T-70-04 | Tampering | ck_visits_channel CHECK | mitigate | DB-level CHECK restricts channel to an allow-list; 'client_qr' added explicitly, no open-ended values. Migration round-trip tested. |
</threat_model>
