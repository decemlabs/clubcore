<objective>
Build the client→staff forward path (BRDG-01): when a client sends a message (text and/or
photo), forward it to the configured staff Telegram chat via an ARQ task enqueued AFTER the
DB commit. The DM carries the client's name+phone+body; photo attachments are forwarded as
real inline images. After a successful staff DM, write the `chat_forwarding_log` Redis anchor
(`cc:messaging:tg_msg:{tg_message_id}` → `{thread_id, client_id}`, TTL 7 days) that Plan 02's
reply handler consumes. The bridge is a logged no-op when `STAFF_TELEGRAM_CHAT_ID` is unset.

Purpose: Lets a single-gym operator read client chat in Telegram without an admin UI.
Output: `forward_to_staff` ARQ task, `send_photo` sender, `staff_telegram_chat_id` config field,
WorkerSettings + ctx wiring, and the post-commit enqueue seam in the messaging router.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API (POST /messages) | Authenticated client principal; body validated; attachment IDOR-checked upstream (Phase 92) |
| API→Redis (chat_forwarding_log) | Routing anchor written by the worker; key derived from staff-side tg_message_id |
| worker→Telegram (outbound DM) | PII (client name+phone+body) leaves the system to the configured staff chat only |
| worker→S3 (photo bytes) | object_key read from the committed message's owned attachment row only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-93-01 | Information Disclosure | forward_to_staff outbound DM (PII: name+phone+body) | mitigate | DM target is ALWAYS settings.staff_telegram_chat_id (server config), never a payload/runtime-derived chat_id (Task 2). When unset, no DM is sent (no-op) — PII cannot leak to an unconfigured destination. |
| T-93-02 | Tampering / IDOR | photo bytes read from S3 (object_key) | mitigate | object_key is resolved in the router from repository.get_owned_attachment(result.attachment.id, client_id=principal) — the same IDOR-gated row the client already owns (Phase 92 T-92-07/T-92-12). The worker never builds a key from user input; the attachment_id is enqueued only when result.attachment exists on the committed message (Task 3). |
| T-93-03 | Denial of Service | Telegram 429 rate-limit cascade in the request path | mitigate | Forward is enqueued strictly AFTER commit via ARQ (never synchronous in-transaction); _max_tries=2/_expires=20 bound retries; the client send returns regardless of forward outcome (Task 3 / D-42-13 precedent). |
| T-93-04 | Repudiation | forwarded message has no durable trace | accept | The client message_sent audit row (Phase 90) already records the originating message co-transactionally; the forward is a side-effect of an audited event. Forward success/failure is structlog-logged ("client_message_forwarded"). A separate forward-audit is deferred (no security value for single-gym v2.5). |
| T-93-05 | Tampering | chat_forwarding_log anchor written on a failed/partial send | mitigate | Redis SET happens ONLY when SendResult.ok is True AND a staff-side message_id was returned (Task 2). A failed send writes no anchor — so a stale/absent anchor degrades to Plan 02's "не могу определить тред" drop, never a misroute. |
| T-93-SC | Tampering | npm/pip installs | mitigate | No new third-party packages introduced (python-telegram-bot, arq, aioboto3, redis, structlog all already in uv.lock). No package-install task — Package Legitimacy Gate N/A for this plan. |
</threat_model>
