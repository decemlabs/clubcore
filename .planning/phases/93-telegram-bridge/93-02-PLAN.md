<objective>
Build the staff→client reply path (BRDG-02 + BRDG-03): a staff member's native Telegram Reply
on a forwarded message is routed to the correct client thread using the `chat_forwarding_log`
Redis anchor written by Plan 01, persisted via `record_staff_message`, and delivered to the
client over the live WS connection (new_message + reply-as-read read_receipt). Echo-loops and
misroutes are made impossible: `is_bot` + `update_id` dedup break loops; a stale/missing anchor
drops the message with a staff hint rather than falling back to the most-recent thread.

Purpose: Lets staff answer clients directly from Telegram (admin-web frozen until v2.6).
Output: `staff_reply_handler`, the `HandlerContext.messaging_service` field, and the
`telegram_bot.py:main()` wiring (import + ctx construction + MessageHandler registration).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram→worker (inbound update) | Untrusted inbound update; only messages from STAFF_TELEGRAM_CHAT_ID are honored |
| Redis→worker (anchor lookup) | Routing decision derives client/thread from the anchor only; absent anchor = drop |
| worker→DB (record_staff_message) | client_id sourced from the anchor (server-written), never from the inbound message body |
| worker→client (WS publish) | new_message/read_receipt frames; channel derived from anchored client_id only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-93-06 | Spoofing / Authz | inbound staff-reply updates | mitigate | The MessageHandler is registered with `tg_filters.Chat(staff_telegram_chat_id)` so only messages from the configured staff chat reach the handler; a defensive in-handler `chat_id == settings.staff_telegram_chat_id` check returns early otherwise (Task 2). Messages from any other chat are never honored. |
| T-93-07 | Tampering / IDOR (misroute) | reply routing — client A's reply leaking to client B | mitigate | client_id/thread_id come ONLY from the chat_forwarding_log anchor keyed by the staff-side reply_to.message_id. A stale/missing anchor DROPS the message with a staff hint — there is NO most-recent-thread fallback (Task 2 / BRDG-03 / SC-2). Anti-misroute is proven by the ≥2-anchor test. |
| T-93-08 | Tampering (echo loop) | bot's own outbound re-ingested as a staff reply | mitigate | Triple guard: `effective_user.is_bot` early-return; `_dedupe_update_id` SET-NX on update_id (replay skip); and the chat_forwarding_log presence requirement (a bot echo has no anchor → dropped). Each client message appears exactly once per direction (SC-3 / BRDG-03). |
| T-93-09 | Information Disclosure | staff message body / PII over WS to client | mitigate | publish_new_message/publish_read_receipt carry only ids/timestamps to `cc:messaging:client:{client_id}` derived from the anchored client_id (Phase 90/91 T-90-04/T-91-IDOR); full payloads are never published (P5). The client fetches the body via the existing IDOR-safe REST path. |
| T-93-10 | Repudiation | staff reply lacks an audit trail | mitigate | `chat_staff_reply_sent` (pre-registered LOCKED_AUDIT_EVENTS / INFRA-15) is emitted co-transactionally (before commit) with the staff message insert (Task 2), so the audit row and the message commit atomically. |
| T-93-SC | Tampering | npm/pip installs | mitigate | No new third-party packages (python-telegram-bot, redis, structlog already in uv.lock). No package-install task — Package Legitimacy Gate N/A for this plan. |
</threat_model>
