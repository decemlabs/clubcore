## Warnings

### WR-01: Sessions conditional probe assumes `get` operation, will fail when Phase 23 ships sessions with a different shape

**File:** `packages/api-client/src/schema.contract.test.ts:60-64`

**Issue:** The probe is structured so that if `/api/v1/auth/sessions` lands in `paths`, it MUST expose a `get` operation:

```ts
type _SessionsProbe = _HasSessions extends true
  ? AssertNonNever<paths['/api/v1/auth/sessions' & keyof paths]['get']>
  : true
```

D-21-2 explicitly states the contract test must "compile whether or not Phase 23 has merged." Today it does — when sessions are absent, `_HasSessions` is `false` and the probe collapses to `true`. But the moment Phase 23 ships, this probe activates the `get` branch. If the sessions surface ships with only `POST` (mint a session), `DELETE` (revoke a session), or `POST /sessions/revoke`-style endpoints (a plausible RBAC-style design where listing your own sessions is read via `/auth/me`-adjacent routes), then `paths['/api/v1/auth/sessions']['get']` resolves to `undefined` / `never`, `AssertNonNever` returns `false`, and the tuple/assignment in `_sessionsCheck: _SessionsProbe = true` will fail to compile. This is the opposite of the intent — the probe is supposed to stay green across the merge boundary, not turn red.

**Fix:** Keep the probe purely structural — only assert that the path key exists, not that any specific operation exists. The whole point of D-21-2 is to forward-guard without coupling to Phase 23's exact verb shape:

```ts
// Existence-only probe: stays green regardless of which verbs Phase 23 ships.
type _SessionsProbe = HasPath<'/api/v1/auth/sessions'> extends boolean ? true : false
const _sessionsCheck: _SessionsProbe = true
```

Or, if you want the probe to actually do something useful when Phase 23 has merged, narrow it to `keyof paths['/api/v1/auth/sessions']` extending one of `'get' | 'post' | 'delete'`:

```ts
type _SessionsProbe = _HasSessions extends true
  ? keyof paths['/api/v1/auth/sessions' & keyof paths] extends never
    ? false
    : true
  : true
```

That asserts "sessions has at least one verb defined" without locking in which verb.

### WR-02: `expect(_checks).toHaveLength(9)` is a magic number duplicating tuple arity

**File:** `packages/api-client/src/schema.contract.test.ts:71`

**Issue:** The runtime assertion hardcodes `9` to match the tuple length on lines 45-55. Adding or removing a static check (e.g., when a Phase 22 surface adds a new endpoint to pin) requires the developer to remember to bump this number. There is no compile-time link between the tuple shape and the number `9`, so a forgotten update silently changes a length-mismatch failure into a working-but-stale test. The test's whole job is to catch drift; ironically it has its own drift surface.

**Fix:** Read the length from the array itself — the runtime `expect` exists only to keep Vitest from skipping the file, not to validate arithmetic:

```ts
expect(_checks.every((v) => v === true)).toBe(true)
expect(_sessionsCheck).toBe(true)
```

`every(v => v === true)` is also stronger: it actually checks each compile-time gate evaluated to `true`. The current `toHaveLength` only checks the array's length, not its contents.

## Info

### IN-01: Tuple-element types are inferred from `true | false` pair, hiding compile failures behind a runtime equality

**File:** `packages/api-client/src/schema.contract.test.ts:45-55`

**Issue:** The assignment

```ts
const _checks: [_PlansListGet, ...] = [true, true, ..., true]
```

does correctly fail at compile time if any `_*` alias resolves to `false` (since `false` is not assignable to the literal `true`). This is the intended mechanism. However, because `AssertNonNever` returns `false` (not `never`) on failure, the tsc error message will say "Type `false` is not assignable to type `true`" — which is informative but doesn't name *which* path resolved to never. When this test goes red in CI, the developer has to bisect by eye.

**Fix (optional):** Encode the failure as a branded never with a path tag, so the tsc error names the offending path:

```ts
type AssertNonNever<T, Tag extends string> = [T] extends [never]
  ? { __error: `${Tag} resolved to never` }
  : true
type _PlansListGet = AssertNonNever<paths['/api/v1/membership-plans']['get'], 'GET /membership-plans'>
```

Not a defect — the current version works; this is a maintainability nudge.

### IN-02: Comment on line 35 mis-describes openapi-typescript behavior

**File:** `packages/api-client/src/schema.contract.test.ts:35-36`

**Issue:** The comment reads:

```
// requestBody guard — openapi-typescript v7 types absent bodies as `never`,
// so a non-empty POST body must NOT collapse to never.
```

openapi-typescript v7 does not type absent bodies as `never` — it types them as `requestBody?: never` (an *optional* property whose type is `never`), which is structurally different. When you index `['post']['requestBody']` on a verb that has no body, you get `never | undefined` → simplifies to `undefined` in a non-`exactOptionalPropertyTypes` context. The current `AssertNonNever<_MembershipsPostBody>` test happens to pass for the `/memberships POST` case because the body IS defined, but the comment's mental model is slightly off.

**Fix:** Tighten the comment to reflect what openapi-typescript actually does:

```ts
// requestBody guard — openapi-typescript v7 emits `requestBody?: never` for
// bodyless verbs and a `{ content: {...} }` object for verbs with a body.
// Asserting non-never here pins that POST /memberships still has a body.
```
