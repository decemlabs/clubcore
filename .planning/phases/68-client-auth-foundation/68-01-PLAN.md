<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DB schema → both principals | A single otp_codes row must not be claimable by both a staff user and a client (ownership confusion) |
| migration → production data | Additive migration must not corrupt or lock existing staff OTP/refresh rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-68-01 | Elevation | otp_codes row ownership | mitigate | `ck_otp_codes_principal_xor` CHECK forces exactly one of (user_id, client_id) non-null — a row can never carry both principals |
| T-68-02 | Tampering | otp_codes existing rows | mitigate | column added as nullable with no default; existing staff rows keep user_id non-null and satisfy the XOR automatically; no backfill writes |
| T-68-03 | Spoofing | client refresh token uniqueness | mitigate | `token_hash` UNIQUE constraint on client_refresh_tokens prevents two families sharing a token hash |
| T-68-04 | Denial | migration lock on otp_codes | accept | additive ADD COLUMN nullable + CHECK NOT VALID-equivalent is fast on a single-gym dataset; low row count, low risk |
</threat_model>
