## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → backend `/api/v1/clients/*` | Authenticated FE sends create/update payloads; backend validates with `extra="forbid"` + `EmailStr` + Pydantic |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-01 | Tampering | createInputToRequest output | mitigate | Adapter only OMITS empty-string optionals — it never substitutes `null`. Backend Phase 8 D-01 distinguishes "absent (no change)" from "explicit null (forbidden in v1.1)". Adapter never sends `null`, so `extra="forbid"` cannot reject the body and Pydantic cannot interpret a no-op as a clear-field. |
| T-11-02 | Information Disclosure | responseToClient field selection | accept | FE drops backend-only fields (`gender`, `tags`, `emergencyContact`, `telegramUserId`, `createdByUserId`, `updatedAt`) by destructuring/projecting only what `Client` defines. No PII is exposed beyond what Phase 10's UI already rendered from the mock; the adapter is strictly narrower. |
| T-11-03 | Denial of Service | fullName composition with whitespace-only inputs | mitigate | `.filter(Boolean)` + `.trim()` collapse `' '`-only or empty parts so a malformed backend row cannot render an unbounded run of separators or break list virtualisation. |
| T-11-04 | Validation bypass via empty string | EmailStr / EmailStr-equivalent on backend | mitigate | createInputToRequest omits any optional whose FE value is `''`; the backend only sees absent keys (allowed) or non-empty strings (validatable). Empty-string `email` cannot reach `EmailStr`. |

</threat_model>
