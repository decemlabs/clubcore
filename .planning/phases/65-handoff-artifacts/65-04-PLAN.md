**Idempotency-Key semantics (from 66-CONTEXT.md + v1.11-idempotency-audit.md):**
- Header format regex: `^[A-Za-z0-9_:-]{16,128}$`
- Scope: USER-scoped (Redis key `cc:idem:{user_id}:{method}:{path}:{key}`) — two different users may reuse the same key string without collision (D-11-IDM-USER security fix).
- TTL: 24h (86400s) replay window.
- Verbatim replay: returns the cached FIRST-SUCCESS response body+status — NOT live DB state. Point readers to the resource GET for current state.
- Absent key on a Category-A endpoint: `422 idempotency_key_required`.
- Same key + different request body: `422 idempotency_key_reuse` (body-hash mismatch).
- Client guidance: generate a fresh UUIDv4 per logical operation; reuse the SAME key only for retries of that operation.
- Category-A endpoint list: source from `.planning/handoff/v1.11-idempotency-audit.md` (the `A` classified rows: memberships create/cancel/freeze/unfreeze/renew, online-payments sells, pt-packages create/cancel/refund, pt-sessions, bookings create/cancel, recurring-templates, time-off, trainer-slots). Refunds (`refund_membership`, `refund_membership_online`, `refund_pt_package_online`) are classified B (DB-guarded) — note they do NOT take a header Idempotency-Key.
- ЮKassa webhook: separate `cc:yk:webhook:*` dedup — NOT user-scoped header idempotency (D-11-IDM-WEBHOOK); may mention for completeness.
