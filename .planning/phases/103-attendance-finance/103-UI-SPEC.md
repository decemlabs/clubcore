## Surface 1: Check-In Flow (Attendance Page)

**Requirement:** ATT-01. Reception + owner can check a client in via `POST /api/v1/visits {clientId}`.

### 1.1 Entry Point: Check-In Button

The existing `AttendancePage.tsx` has `AttendancePageHead` — add a primary check-in button to the page head actions area (right side, same pattern as P102 FAB or P101 "Добавить клиента").

- **Both roles** (reception + owner): button is rendered. `can(role, 'check_in', 'visits') === true` for both.
- Button anatomy: `inline-flex h-[38px] items-center gap-[7px] rounded-full bg-fg text-bg px-[14px] text-[13px] font-semibold` (existing primary action button pattern). `dark:bg-primary dark:text-[#06120c]`.
- Icon: `UserCheck` (Lucide), `size-[14px]`.
- Label: `«Чек-ин»`.
- Click: opens the Check-In Modal (see §1.2).

### 1.2 Check-In Modal

**Component pattern:** `AdaptiveModal` (existing). Reuses the client-picker anatomy from `BookingModal.tsx` (P102 `BookingModal` — same `Section`, `ModalInput`, `ResultList`, `ResultItem`, `Loader2` pattern). Do NOT port the QR scanner from the old mock `CheckinModal.tsx` — that was mock-only.

**Modal header:**
- Icon: `IconChip` tone=`'accent'`, icon=`UserCheck` (Lucide)
- Title: `«Чек-ин»`
- Description: `«Найдите клиента и отметьте его визит»`

**Body (in order):**

**Section** `«Клиент»` (required):
- `ModalInput` icon=`Search` placeholder=`«Найти по имени или телефону…»` — debounced 300 ms, queries `GET /api/v1/clients?q={value}&pageSize=8`.
- While searching (1+ chars, query in-flight): show `Loader2` spinner inside the input (right side, `size-4 animate-spin text-fg-subtle`).
- Search results: `ResultList` + `ResultItem` (existing `fields.tsx` primitives). Each row shows client initials circle + full name + phone. Max 8 results (no pagination in picker).
- Selected client: show selected `ResultItem` with `active={true}` highlight. Deselect `X` button at the right of the selected row (reset to search input, `XIcon size-4`).
- No results: inline `EmptyState` (no icon, no icon tile) — body only: `«Клиент не найден»` in `text-[13px] text-fg-subtle text-center py-4`.

**Pre-validation note** (optional, shown when `GET /visits/_meta` is loaded and cacheable):
- If current time is outside `gymHoursStart`–`gymHoursEnd` from `_meta`: show a `Callout` tone=`'warn'` icon=`TriangleAlert` below the picker BEFORE client is selected:
  `«Сейчас вне часов работы зала. Чек-ин может быть отклонён.»`
- This is a soft warning only — the POST is still allowed; server makes the final call.

**Footer actions:**
```
[ Отмена (ghost) ]   [ Отметить визит (primary) ]
```
- Primary button disabled until a client is selected.
- While mutation in-flight: primary button shows `Loader2 size-[18px] animate-spin` + disabled; ghost also disabled. `onOpenChange` suppressed.

### 1.3 Optimistic List Update

On submit (before server responds):

1. Optimistically prepend a new row to the visits list (TanStack Query `onMutate` pattern from P101 memberships freeze / P102 booking race handling):
   - Constructed row: `{ id: 'optimistic-{uuid}', clientId, checkedInAt: new Date().toISOString(), gymDate: todayISO, channel: 'reception', checkedInBy: currentUserId, clientName: selectedClient.fullName, _optimistic: true }`.
   - Render the optimistic row with `opacity-60` and a `Loader2 size-3.5 animate-spin text-fg-subtle` in the aside position (instead of the time value).
2. On success: close modal + remove optimistic row + invalidate `visitKeys.list(filter)` → refetch. Show `toast.success('Визит зафиксирован', { description: selectedClient.fullName })`.
3. On error (any — including 409): rollback optimistic row via `onError` context. Show the specific error state (see §1.4).

### 1.4 The 3 Distinct 409 States

All three 409 sub-states surface inside the Check-In Modal as an inline `Callout` component (`tone='danger'`, `icon=TriangleAlert`) below the selected client row. Do NOT close the modal. Do NOT use a toast for these — the user must see the specific reason to act.

The `error.code` from the backend response envelope `{ code, message, fields? }` determines which copy is shown:

| `error.code` | Callout heading | Callout body |
|---|---|---|
| `outside_gym_hours` | `«Вне часов работы»` | `«Зал сейчас закрыт. Чек-ин невозможен до открытия.»` |
| `no_active_membership` | `«Нет активного абонемента»` | `«У клиента нет действующего абонемента. Оформите абонемент перед регистрацией.»` |
| `duplicate_checkin` | `«Уже отмечен сегодня»` | `«Этот клиент уже был отмечен сегодня. Повторный чек-ин невозможен.»` |

For any other non-409 error (5xx, network): show generic `Callout tone='danger'`: `«Не удалось выполнить чек-ин. Проверьте соединение и попробуйте ещё раз.»`. Reset button to normal (not loading). Modal stays open.

**After a 409 Callout is shown:**
- Primary button is re-enabled (not `disabled`) — user can select a different client.
- Selecting a new client clears the Callout (reset error state on client-selection change).

## Surface 3: Date-Range Picker (Load, Cashbox, Finance)

**Requirement:** D-103. All three owner-only pages need a `from`/`to` date filter. Default range: last 30 days (`toDate = today`, `fromDate = today - 29 days`).

### 3.1 Component Anatomy

Reuse existing `ModalInput type=date` pattern wrapped in a `FieldRow cols=2` — placed in the page head actions area or in a compact toolbar row below the page head, consistent with existing page layouts. No new component family needed.

**Desktop layout** (≥ sm breakpoint): two date inputs side-by-side with a label `«Период»` above:
```
[ Период:  [ С: __ . __ . ____ ]   [ По: __ . __ . ____ ] ]
```

**Mobile layout** (< sm breakpoint): stack vertically.

**Input anatomy:**
- Label above: `text-[12.5px] font-semibold text-fg-muted`
- Input: native `<input type="date">` styled via existing `ModalInput`-equivalent Tailwind classes — `h-9 rounded-[10px] border-[0.5px] border-border bg-surface px-3 text-[13px] text-fg focus:outline-none focus:ring-2 focus:ring-primary-soft focus:border-primary`.
- `«С»` input: `max` attribute set to today (no future from-dates).
- `«По»` input: `min` attribute set to `fromDate`; `max` attribute set to today.

### 3.2 Validation

Client-side validation fires on blur or before query send. Do NOT send invalid ranges to the server.

| Validation | Trigger | Treatment |
|---|---|---|
| Inverted range (`toDate < fromDate`) | blur on either field, or on submit | Show inline error below the range row: `«Дата "По" должна быть позже даты "С"»` in `text-[12px] text-danger mt-1`. Query not fired. |
| 366-day cap (`toDate - fromDate > 365 days`) | blur or submit | Show inline error: `«Максимальный период — 365 дней»` in `text-[12px] text-danger mt-1`. Query not fired. Backend returns 422 for this; client validation prevents the call. |
| Valid range | — | Fire query. Clear any existing validation error. |

**Default state on page mount:** no validation error shown; range is `[today-29, today]` (valid).

**Query firing:** fires on blur off the second date field (not on every keystroke). Debounce: 0 ms (fire immediately after valid blur). Loading spinner appears inside the chart/heatmap area while re-fetching (the charts show `PageLoading` skeleton, not the entire page skeleton).

### 3.3 Partial-Loading State for Re-fetch

On date range change (valid), the existing chart/table area shows a loading state WITHOUT replacing the page head or KPI strip (those stay visible from the previous data). The chart/table area specifically renders `<PageLoading />` or a section-level `Skeleton` (`h-[320px] w-full rounded-xl`). This is preferable to a full-page skeleton on re-filter.

## Surface 4: Report Data-States + Zero-Fill (Load + Finance)

**Requirement:** ATT-02 (Load), FIN-01 (Finance). Sparse backend buckets must not produce NaN in the UI.

### 4.1 Load Page — `GET /api/v1/reports/visits`

Response shape: `{ daily[{date, count}], hourly[{hour, count}], averagePerDay, fromDate, toDate }`. Buckets are sparse (only non-zero returned).

**Zero-fill rule (client-side, in the data-transform layer — e.g. `features/load/api.ts`):**

**Hourly buckets:** generate all 24 hours `0..23`. For each hour, look up the sparse `hourly` array by `hour` value; use `count` if found, else `0`. Result: always 24 data points. The `IntensityHeatmap` and `AreaTrendChart` receive complete arrays — no NaN.

**Daily buckets:** generate all calendar days from `fromDate` to `toDate` (inclusive). For each day, look up sparse `daily` array by `date`; use `count` if found, else `0`. Result: complete day series covering the full range. `AreaTrendChart` receives this complete array.

**Zero-fill bucket rendering:**
- A bucket with `count === 0` renders as `0` in the chart tick label and `'0'` in the heatmap cell text.
- Heatmap cell level for `count === 0`: `'none'` (lightest shade) — NOT blank, NOT NaN.
- Chart Y-axis starts at `0` when all buckets are zero (avoids "auto" scale showing NaN).

**LoadKpis strip:** replace mock `LoadKpi` structure with values derivable from the real response:
- `averagePerDay` → `«Среднее в день»` KPI value.
- `daily.reduce(sum)` → `«Всего визитов»` KPI value (total in range).
- The existing `LiveNowCard` (real-time zone occupancy data) has no real backend endpoint in Phase 103 — **hide `LiveNowCard`** entirely (remove from `LoadPage` render, not deleted from disk). Add `// TODO Phase 104: wire LiveNow to real-time endpoint`.

### 4.2 Finance Page — `GET /api/v1/reports/revenue`

Response shape: `{ buckets[{period, netKopecks, byMethod{cash, online}, bySubjectKind{membership, pt_package}}], fromDate, toDate, groupBy }`.

**Zero-fill rule:**
- When `groupBy=day`: fill all calendar days in range with `{ period: dateStr, netKopecks: 0, byMethod: {cash:0, online:0}, bySubjectKind: {membership:0, pt_package:0} }` for any missing dates.
- When `groupBy=month`: fill all months in range with zero buckets.
- `netKopecks` may be negative (net of refunds). Format with `formatMoney(netKopecks)` — existing helper handles signed values.

**Finance page restructure:** the current mock `FinancePage` has three tabs (`Реестр платежей`, `Неудачные`, `Выплаты тренерам`). Phase 103 wires it to two real data sources: revenue report + payments (online slice). The existing tab structure is simplified:

| Tab | Source | Notes |
|-----|--------|-------|
| `«Выручка»` (revenue tab) | `GET /reports/revenue` | Revenue chart (existing `RevenueChart` / `AreaTrendChart`) + groupBy day/month toggle |
| `«Онлайн-платежи»` (online tab) | `GET /payments?method=online` (paginated) | Table of online payment rows — reuse cashbox ledger row anatomy |

Remove the `«Неудачные»` and `«Выплаты тренерам»` tabs (no real backend for failed-payment aggregation or trainer payouts in this view — payroll wired in P102 PayoutsTab). Remove `«Экспорт»` button (CSV export deferred to Phase 104).

**GroupBy toggle** (revenue tab only): a `ChipGroup`-style toggle (2 options, existing `fields.tsx` `ChipGroup` or simple button pair):
| value | label |
|-------|-------|
| `day` | `«По дням»` |
| `month` | `«По месяцам»` |

Default: `day`. Fires new query on toggle.

**Revenue chart:** reuse `AreaTrendChart` (existing `components/charts/AreaTrendChart.tsx`). Map `buckets` to `TrendPoint[]` where `label = period`, `value = netKopecks / 100` (display in rubles, not kopecks, for Y-axis readability). Tooltip renders `formatMoney(bucket.netKopecks)`.

### 4.3 Load + Finance — Page-Level Data States

| State | Component | Notes |
|-------|-----------|-------|
| Loading (initial) | `<PageLoading />` | Skeleton for entire page area |
| Loading (date-range re-fetch) | Section-level `<Skeleton className="h-[320px] w-full rounded-xl" />` | Page head + KPI strip stay visible |

## Surface 5: Cashbox Ledger — Real Data (Refund Rows + Daily Totals)

**Requirement:** FIN-02. `GET /api/v1/payments` returns paginated `PaymentResponse` items including refund rows (`refundOf != null`). Daily totals are computed client-side.

### 5.1 Refund Row Visual Treatment

Real `PaymentResponse` fields:
- `amountKopecks` — signed integer (negative for refunds).
- `refundOf` — `string | null` — if not null, this is a refund row.
- `method` — `'cash' | 'online'`.
- `subjectKind` — `'membership' | 'pt_package'`.

**Refund row rendering** (in the ledger `TransactionsCard`-equivalent):

| Field | Non-refund row | Refund row (`refundOf != null`) |
|-------|---------------|--------------------------------|
| Icon chip | `bg-primary-soft text-primary-deep` (membership) or `bg-surface-3 text-fg-muted` (pt_package) | `bg-danger-soft text-danger` · `Undo2` icon (existing `TX_ICON.refund` pattern) |
| Title | `«Абонемент»` / `«PT-пакет»` | `«Возврат»` |
| Amount text | `text-fg font-bold tabular-nums` + `«+»` prefix | `text-danger font-bold tabular-nums` + `«−»` prefix |
| Amount value | `formatMoney(Math.abs(amountKopecks))` | `formatMoney(Math.abs(amountKopecks))` |

The `«−»` prefix for refunds uses the minus sign character (`−`, U+2212), not a hyphen — consistent with existing `TransactionsCard.tsx` `refund ? '−' : '+'` pattern.

**No refund action button in the cashbox ledger.** The refund action is on the membership/PT detail (wired in P101). The cashbox shows refund rows READ-ONLY. Do NOT add a "Вернуть" or "Оформить возврат" button to the ledger row. Remove the existing mock dropdown menu item "Оформить возврат" from `TransactionsCard.tsx`.

**Optional link:** a refund row may optionally display a small `«→ Абонемент»` text link (if `subjectId` is available) navigating to `ROUTES.client(clientId)` — implement only if `subjectId` + `clientId` are available in `PaymentResponse` and the routing is straightforward; otherwise omit.

### 5.2 Client-Side Daily Totals

The real `GET /payments` response has no aggregate — daily totals are computed client-side in the data-transform layer.

**Algorithm** (in `features/cashbox/api.ts` or a `computeDailyTotals()` utility):
1. Group `items` by `receivedAt` date (gymDate equivalent — truncate to MSK date using `date-fns` + `Europe/Moscow` TZ).
2. For each date group, sum `amountKopecks` (signed — refunds subtract automatically).
3. Result: `DailyTotal[]` = `[{ date: string, totalKopecks: number }]` sorted ascending.

**Daily total display:** render a date-separator row between groups of payments for the same day.

```
─────  Пятница, 13 июня  ─────  Итого: +184 200 ₽
```

Anatomy of the date-separator row:
- Full width `div` with `border-t-[0.5px] border-border`.
- Date label: `text-[11.5px] font-semibold text-fg-muted` — `formatDateRu(date)` with weekday (e.g. `«Пятница, 13 июня»`).
- Daily total: `text-[11.5px] font-bold tabular-nums` to the right — `formatMoney(totalKopecks)`.
- Background: `bg-surface-2` to distinguish from transaction rows.
- No clickable interaction.

If `totalKopecks < 0` (net negative day — refunds exceed sales): amount in `text-danger`.
