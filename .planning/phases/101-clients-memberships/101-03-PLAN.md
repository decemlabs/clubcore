- `POST /api/v1/memberships/{id}/freeze` body `{}` + Idempotency-Key → `{ data }`. reception+owner.
- `POST /api/v1/memberships/{id}/unfreeze` body `{}` + Idempotency-Key → `{ data }`. reception+owner.
- `POST /api/v1/memberships/{id}/renew` body `{}` + Idempotency-Key → 201 `{ data }`. reception+owner.
- `POST /api/v1/memberships/{id}/refund` body reason (required 1-200) — **NO Idempotency-Key** (UI-SPEC §3.2) → `{ data }`. REFUND perm (reception+owner per B-07).
- `Membership` wire: id, clientId, status (active|frozen|expired|cancelled), planSnapshot (MembershipPlan), paidAmountKopecks, paidAt?, startDate, endDate, freezeDaysUsed, freezeDaysRemaining?, currentFreezePeriod?, previousMembershipId?, notes?, createdAt.

PT-packages (`app/modules/pt_packages/router.py`):
- `POST /api/v1/pt-packages` (sell) body clientId, planId, **amountKopecks (required; 422 amount_mismatch if != plan price)** + Idempotency-Key → `{ data: PtPackage }`. reception+owner.
- `GET /api/v1/pt-packages?clientId=` + `GET /{id}` → reception+owner.
- `POST /api/v1/pt-packages/{id}/cancel` body **reason required 1-200** + Idempotency-Key → `{ data }`. **OWNER_ONLY.**
- `POST /api/v1/pt-packages/{id}/refund` body reason 1-200 + Idempotency-Key → `{ data }`. reception+owner (B-07).
- `PtPackage` wire: id, clientId, status (active|exhausted|expired|cancelled), planSnapshot, sessionsTotal, sessionsUsed, sessionsRemaining, amountKopecks, createdAt.

**Idempotency-Key (no transport change):** pass via the existing `headers` field —
`staffRequest('post', path, { body, headers: { 'Idempotency-Key': crypto.randomUUID() } })`.
`crypto.randomUUID()` MUST be called at submit time (per attempt), not at hook init — so a
retry of the same mutation gets a NEW key (prevents the backend from treating a real
second attempt as a replay). NOTE: refund deliberately sends NO Idempotency-Key.

**Optimistic vs non-optimistic (CONTEXT decision — do not deviate):** freeze + unfreeze are the
ONLY optimistic mutations (onMutate→cancelQueries→snapshot→setQueryData→onError rollback→onSettled
invalidate; exact shape in 101-PATTERNS §features/memberships/api.ts). sell, renew, cancel, refund are
non-optimistic (onSuccess invalidate + toast; onError toast).

**can() facts (verified):** membership cancel = `can(role,'cancel','memberships')` OWNER_ONLY; pt-package
cancel = `can(role,'cancel','pt-packages')` OWNER_ONLY. Refund is reception+owner (NOT can()-gated).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin-app → staff API | Sell/lifecycle writes cross here; backend is authority on access, idempotency, refund auth |
| submit-time → Idempotency-Key | Per-attempt UUID determines whether the backend treats a request as new vs replay |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-101-08-DOUBLECHARGE | Tampering | sell/freeze/unfreeze/renew/cancel mutations | mitigate | `crypto.randomUUID()` generated INSIDE mutationFn at submit time → each user-initiated attempt carries a fresh Idempotency-Key (no double-charge on a genuine retry; a network-retry of the SAME in-flight attempt reuses its key). Key never generated at hook init (would replay-collapse distinct attempts). |
| T-101-09-CANCELPRIV | Elevation of Privilege | membership/pt-package cancel | mitigate | `can(role,'cancel','memberships'|'pt-packages')` HIDES cancel for reception (defense-in-depth only). Backend cancel is OWNER_ONLY and is the real boundary; a leaked 403 → non-blocking toast «Отмена … доступна только владельцу.». |
| T-101-10-REFUNDAUTH | Elevation of Privilege | refund (membership + pt-package) | mitigate | Refund requires REFUND perm (reception+owner per B-07) — backend authoritative. UI enforces full-only + required reason (1-200) at the boundary; no amount field exists, so partial-refund tampering is impossible from the UI. Backend re-validates `MembershipRefundRequest` (forbids amountKopecks). |
| T-101-11-IDOR | Information Disclosure | useMembershipsByClient / membership get | mitigate | Reads are by id/clientId; backend `require_*` is the authority. UI does not assume access; 403/404 collapses to an inline error, never a cross-client render. |
| T-101-SC | Tampering | npm installs | mitigate | No new packages installed this plan (sonner/zod present); no install task → slopcheck N/A. |
</threat_model>
