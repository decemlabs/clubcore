<interface_context>
**Backend wire contract (camelCase via Pydantic aliases — confirmed in 101-PATTERNS / 101-CONTEXT):**
- `GET /api/v1/clients` query params: `q` (>=2 chars else None), `tag`, `gender` (male|female), `createdFrom`, `createdTo`, `hasTelegram` (bool), `sort` (`created_at_desc` | `last_name_asc`), `page`, `pageSize` → `{ data: { items, total, page, pageSize } }`. reception+owner.
- `GET /api/v1/clients/{id}` → `{ data: Client }`. reception+owner.
- `POST /api/v1/clients` body `ClientCreateRequest` = lastName, firstName, middleName?, phone, email?, birthday?, gender?, tags?, notes?, emergencyContact?, telegramUserId? → `{ data: Client }`. reception+owner.
- `PATCH /api/v1/clients/{id}` (partial) → `{ data: Client }`. reception+owner.
- `DELETE /api/v1/clients/{id}` → 204 (no body). **OWNER_ONLY.**
- `Client` wire shape: id, lastName, firstName, middleName?, phone, email?, birthday?, gender?, tags[], notes?, telegramUserId?, createdAt (see 101-PATTERNS ClientSchema).
- Error envelope `{ code, message, fields? }`; transport throws `ApiError` carrying `.code`/`.message`/`.fields`. 422 `fields` is `Record<string,string>`.

**Transport facts (no change to client.ts):**
- `staffRequest(method, path, init)` — `init.query` for querystring, `init.params` for `{id}` interpolation, `init.body` for JSON, `init.headers` passthrough.
- `staffRequest` already sets CSRF + credentials; success unwraps nothing — the raw `{data:...}` body is returned, so the queryFn does `Schema.parse(raw).data`.
- Re-export `ApiError` from `features/clients/api.ts` (auth precedent D-100-03-APIERROR-REEXPORT) so page/modal layers can `instanceof ApiError` without importing `@/api/client` (ESLint `import/no-restricted-paths` boundary).

**can() facts (verified in shared/session/can.ts):** client delete is `can(role, 'delete', 'clients')` — OWNER_ONLY. There is NO membership-status filter on the backend.

**format helpers:** money = `formatRub(kopecks)` from `@/lib/format` (NOT `formatMoney`); dates = `formatDateRu`.
</interface_context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin-app → staff API | All client reads/writes cross here; backend is the authority on access (IDOR + owner-only) |
| 422/403/4xx envelope → UI | Untrusted error text rendered to staff; must not leak PII or crash |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-101-01-IDOR | Information Disclosure | `useClient(id)` / `GET /clients/{id}` | mitigate | UI never assumes access by id; 404/403 from backend collapses to PageError, not a partial render of another client's data. Backend `require_*` is the authority; UI does not filter client-side. |
| T-101-02-OWNERDEL | Elevation of Privilege | client DELETE button | mitigate | `can(role,'delete','clients')` HIDES delete for reception (defense-in-depth only); backend DELETE is OWNER_ONLY and is the real boundary. A 403 surfaces as a non-blocking toast, never a crash (AUTH-03). |
| T-101-03-PII-ERR | Information Disclosure | 422/5xx error rendering in modals | mitigate | Render `err.message`/field strings as-is (already server-curated Russian); never echo raw request body or stack. Generic fallback copy when `message` absent. |
| T-101-04-INPUT | Tampering | ClientCreate/Update form input | mitigate | Zod mirrors backend constraints (phone regex, tags caps, notes max) at the boundary; backend re-validates (422). Client-side Zod is UX, server is authoritative. |
| T-101-SC | Tampering | npm installs | mitigate | No new packages installed this plan (zod, @hookform/resolvers, sonner already present); no install task → slopcheck N/A. |
</threat_model>
