## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-38-04-01 | T (Tampering) | trainer_id in PtPackageCreateRequest | mitigate | Server validates via resolve_trainer_by_id; rejects inactive (409) or non-existent (404). Client cannot bind an inactive trainer. |
| T-38-04-02 | E (Cross-module privilege) | refund_pt_package reading bookings table | mitigate | Raw `sa.text()` with `# noqa: TABLE_REF cross-module SQL per D-34-04a / Phase 38 D-38-11`. NO direct import of Booking ORM. `lint-imports` modules-independent enforced. |
| T-38-04-03 | D (Refund orphans bookings) | refund without guard | mitigate | PKG-03 guard fires BEFORE FSM transition. Operator must cancel bookings first. Order verified in test. |
| T-38-04-04 | D (Race: refund + concurrent booking-create) | new booking inserted between count query and FSM transition | accept | Test demonstrates: in v1.5 single-zal scale, operator-driven refund vs. operator-driven booking is not a hot path. The bookings row count is read inside the same UoW; concurrent INSERT would not commit until refund UoW completes (Postgres MVCC), so a confirmed booking inserted AFTER the count check would not be visible during refund. If it lands after, the partial UNIQUE / FK ensures consistency. Documented; mitigation upgrade deferred. |
| T-38-04-05 | S (Spoofing trainer_id) | request body trainer_id | mitigate | Server-side existence + is_active check; client cannot spoof. |
| T-38-04-06 | I (Info disclosure via 404 vs 409) | trainer_not_found vs trainer_inactive | accept | Per existing pt_sessions convention; small leak of trainer existence acceptable at gym-staff trust scale. |
</threat_model>
