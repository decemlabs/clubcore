<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated visitor → GET /i/<code> | Public resolver; no auth; anti-enumeration (always 200) |
| sessionStorage pending code → POST /client/referral/capture | Code is a hint only; referee identity comes from the authenticated principal, not the stored code |
| authenticated friend (OnboardingScreen) → capture endpoint | require_client() principal = referee (IDOR-safe) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-98-10 | Spoofing / Elevation | referral capture identity | mitigate | Referee identity is the require_client() principal server-side (Phase 96); the sessionStorage code is only the referrer hint, never trusted as identity. Capture runs post-auth inside RequireAuth. |
| T-98-11 | Tampering | sessionStorage pending code | accept | A user can set/alter 'clubcore:pendingReferral' to any code; server enforces self-referral block + already-bound idempotency (Phase 96), so a forged code yields only a no-op or a legitimate-by-design binding. No trust placed in the value beyond being a referrer code. |
| T-98-12 | Information Disclosure | /i/<code> resolver landing | mitigate | Resolver returns first name only (Phase 96 T-96-06); landing renders only referrerFirstName + bonus preview; invalid codes show a neutral landing (no enumeration oracle, no error page) |
| T-98-13 | Denial of Service | capture best-effort | accept | Capture failure is swallowed (_e + noop) and never blocks onboarding; a failed capture degrades gracefully (no binding) rather than blocking the user |
| T-98-SC | Tampering | npm installs | mitigate | No new npm packages introduced; nothing to vet |
</threat_model>
