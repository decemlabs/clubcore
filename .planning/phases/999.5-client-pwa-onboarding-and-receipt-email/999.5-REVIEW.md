# Phase 999.5: Code Review Report

**Reviewed:** 2026-05-31
**Depth:** deep
**Files Reviewed:** 14
**Status:** issues_found

## Summary

Phase 999.5 delivers three features across backend and frontend: a 4-step onboarding questionnaire (OnboardingScreen), a pre-checkout receipt-email collection gate (ReceiptEmailGate), and backend D-09/D-10 receipt-contact fields on the payment-status response.

The architecture is generally sound: IDOR is structurally blocked (no `client_id` in PATCH body), the D-10 gate correctly routes email vs phone to separate ЮKassa receipt keys, the anti-oracle is preserved (receipt fields only in `succeeded` branch), and the onboarding flag prevents redirect loops. No ORM model imports appear in the cross-module repository layer.

Two critical defects stand out: a whitespace-only `first_name` bypasses the non-empty guard and writes an empty string to the DB, and the `CheckoutSheet` `onDone` prop is accepted in the signature but never called after a successful payment. Four warnings covering the fiscal-receipt IDOR join weakness, a missing `navigate` dependency in `HomeScreen`'s effect, the email-gate `saving` local state shadowing the mutation, and a stale-cache race on the email-gate path complete the non-trivial findings.

## Critical Issues

### CR-01: Whitespace-only `first_name` writes empty string to DB

**File:** `apps/backend/app/modules/client_portal/service.py:181-195`

**Issue:** The service strips `first_name` and validates that its length does not exceed 24 characters, but it never checks that the trimmed result is non-empty. A payload of `{"firstName": "   "}` (all whitespace) passes both the `is not None` guard and the `len(trimmed) > 24` check with `trimmed = ""`, then a new `ClientProfileUpdateRequest` is constructed with `first_name=""` and committed to the `clients` table. `clients.first_name` is `NOT NULL` at the DB level but has no `CHECK (first_name <> '')`, so the empty write succeeds. Subsequent reads from `/client/me` and the greeting in HomeScreen return an empty string for `firstName`, silently breaking the display and corrupting the permanent profile record for the client.

**Fix:**
```python
if payload.first_name is not None:
    trimmed = payload.first_name.strip()
    if not trimmed:                          # <-- add this guard
        raise _InvalidFirstNameError("first_name must not be blank")
    if len(trimmed) > _FIRST_NAME_MAX:
        raise _InvalidFirstNameError(
            f"first_name must be at most {_FIRST_NAME_MAX} characters"
        )
    payload = ClientProfileUpdateRequest(
        first_name=trimmed,
        ...
    )
```

### CR-02: `CheckoutSheet` `onDone` prop is accepted but never called

**File:** `apps/client-pwa/src/screens/sheets/CheckoutSheet.jsx:32`

**Issue:** `CheckoutSheet` declares an `onDone` prop in its destructured signature (`{ ctx, onClose, onDone, forceOutcome }`), but `onDone` is never invoked anywhere in the component — neither in the `startPay` success path, nor in the `onSaved`/`onSkip` callbacks inside the email-gate branch. Instead, every successful path does `window.location.href = result.confirmationUrl` (a hard navigation away from the SPA). The caller in `App.jsx` (line 311) passes no `onDone` prop, so this is currently a dead API, but it means: (a) any future caller that relies on `onDone` to know checkout succeeded will never get the callback; (b) if `window.location.href` navigation is suppressed in a test or demo environment and `forceOutcome === 'ok'` is used, no success state is signalled at all. This is a dead code + latent integration bug.

**Fix:** Either remove `onDone` from the prop signature if it is intentionally not used (to avoid misleading callers), or call it on the succeeded path. For example after `window.location.href = result.confirmationUrl`:
```jsx
// If onDone is to be kept, invoke it as a side-effect before navigation:
onDone?.();
window.location.href = result.confirmationUrl;
```
If the intent is that navigation replaces the sheet entirely and `onDone` is vestigial, delete it from the destructure and document that the sheet closes via hard navigation.

## Warnings

### WR-01: Fiscal-receipt IDOR join is vulnerable to cross-client oracle when `membership_plan_id` is shared

**File:** `apps/backend/app/modules/client_portal/service.py:799-832`

**Issue:** The `get_client_payment_status` function joins `fiscal_receipts → payments → memberships → online_payments` to find the receipt URL for the current `op_id`. However, the join path (`online_payments.membership_plan_id = memberships.plan_id`) is plan-scoped, not client-scoped on the `online_payments` side — it only adds `m.client_id = op.client_id` on the memberships side. If two clients share the same `plan_id`, the inner subquery `SELECT m.id FROM memberships m INNER JOIN online_payments op ON op.membership_plan_id = m.plan_id WHERE op.id = :op_id AND m.client_id = op.client_id` is correct in isolation (op_id is already validated to belong to the current client by `fetch_client_payment_status`). The risk is the `ORDER BY m.created_at DESC LIMIT 1` heuristic: when a client has bought the same plan twice, the most recent membership row is selected and the corresponding fiscal receipt may not match the payment being queried. This is an INTEGRITY defect (wrong receipt URL returned for a repeated plan purchase), not a full IDOR, but it can surface a wrong receipt link to the paying client.

**Fix:** Scope the subquery to the `online_payment` row's own creation timestamp by joining through `payments.subject_id` directly to the membership activated by the webhook, rather than using a heuristic `ORDER BY ... LIMIT 1`. If the exact membership-id-per-online-payment linkage is not persisted, consider adding an `online_payment_id` FK to `memberships` when it is activated by the webhook.

### WR-02: `navigate` missing from `HomeScreen` `useEffect` dependency array

**File:** `apps/client-pwa/src/screens/HomeScreen.jsx:142-150`

**Issue:** The onboarding redirect effect lists `[homeData, me, navigate]` as its dependencies. In React 18+ (and the project's React 19) `useNavigate` returns a stable function reference across renders, so this is not a bug in practice, but the ESLint `react-hooks/exhaustive-deps` rule will flag it as a warning since `navigate` is included but could also mask real exhaustive-deps issues if the linter is already suppressing warnings here. More substantively: the effect has no early-return when both `homeData` and `me` are still `undefined` (loading), but both checks use `homeData?.membershipState === 'newbie'` and `me && ...` which implicitly guard the undefined case. The actual bug risk is that `navigate` is included in the dep array but is not used inside the effect's condition-check path — only in the `navigate('/onboarding', ...)` call. If `navigate` were ever to change identity on re-render, the effect would rerun and re-check the condition, but because `me.onboardingCompletedAt` is updated by `onSettled` invalidation, the re-check is harmless. Rate this as WARNING because the pattern is fragile and will fail `react-hooks/exhaustive-deps` lint.

**Fix:** The dependency array is correct for the current logic. If the linter is not already enforcing this, add a comment explaining why `navigate` is listed (stable identity, included for correctness completeness), or remove `navigate` from the dep array and add a `// eslint-disable-line` comment:
```jsx
// eslint-disable-next-line react-hooks/exhaustive-deps
}, [homeData, me]);
```

### WR-03: Email-gate `saving` local state duplicates (and can diverge from) `updateEmail.isPending`

**File:** `apps/client-pwa/src/screens/sheets/ReceiptEmailGate.jsx:35,59-69`

**Issue:** `ReceiptEmailGate` maintains its own `saving` boolean state alongside `useUpdateClientEmail` which already exposes `isPending`. Both the button's `disabled` check and the spinner branch read the local `saving` flag. If `updateEmail.mutateAsync` throws before `setSaving(false)` runs in `finally`, the `finally` block does execute correctly. However, if the component unmounts mid-mutation (user navigates back), the `setSaving` call in `finally` will fire on an unmounted component. In React 18+ (and React 19) this does not throw (the warning was removed), but the state update is silently discarded. More importantly, the `saving` guard `if (!validate(email) || saving) return` in `handleSaveEmail` deduplicates rapid taps, but so does `updateEmail.isPending`. The duplicate state is not a correctness bug in isolation but is a maintainability hazard — a future refactor might remove one and break the other.

**Fix:** Remove `saving`/`setSaving` state and derive from `updateEmail.isPending`:
```jsx
const saving = updateEmail.isPending;
// Remove: const [saving, setSaving] = React.useState(false);
// Remove: setSaving(true); ... setSaving(false);
```

### WR-04: `receipt_phone` is exposed when `client_email` is falsy but not `None` (e.g., empty string)

**File:** `apps/backend/app/modules/client_portal/service.py:851-855`

**Issue:** The contact-row read logic is:
```python
client_email = contact_row["email"]
client_phone = contact_row["phone"]
receipt_email = client_email if client_email else None
receipt_phone = client_phone if client_email is None else None
```
`receipt_phone` is populated when `client_email is None`, but `receipt_email` is treated as absent when `client_email` is falsy — which includes the empty string `""`. If a client somehow has `email = ""` in the DB (this can occur if the service validation described in CR-01 is fixed but a legacy data path allows it), then `receipt_email = None` (falsy guard) and `receipt_phone = None` (because `client_email is None` is `False` for `""`), so both receipt contact fields are `None`. The ЮKassa receipt would then have been sent using `customer_email=""` (the falsy path in `_sell_subject_core` passes `email=""` as `customer_email`). The inconsistency between the two falsy checks means the status endpoint and the actual ЮKassa receipt are not aligned.

**Fix:** Use a single consistent guard. Change to `is None` checks throughout or normalize empty-to-None at write time:
```python
receipt_email = client_email if client_email else None
receipt_phone = client_phone if not client_email else None  # match falsy, not identity
```
Or, preferred: enforce at the write path that `email` is stored as `NULL` when blank (i.e., normalize `""` → `NULL` in `update_client_profile`).

### IN-01: `onboarding_completed` truthiness check silently ignores `False`

**File:** `apps/backend/app/modules/client_portal/repository.py:600`

**Issue:** The repository check is `if payload.onboarding_completed:` which treats `False` the same as `None` (neither sets the timestamp). The schema comment documents the field as a flag that is only meaningful when `True` (once set, `onboarding_completed_at` is never cleared). However, the Pydantic schema declares it as `bool | None = None`, which means a caller could send `onboardingCompleted: false` expecting it to be a no-op, and it is — but the asymmetry is undocumented and could confuse future maintainers. More importantly, if the product ever needs a "reset onboarding" path this silently ignores that payload.

**Fix:** Document the intent explicitly in the schema and service docstring. If reset is out of scope, add a comment in the repository:
```python
# onboarding_completed: True-only flag — False and None are treated as "no-op" (D-05).
if payload.onboarding_completed is True:
    sets.append("onboarding_completed_at = now()")
```

### IN-02: `create_receipt` in `yookassa/client.py` accepts only `customer_email`, not `customer_phone`

**File:** `apps/backend/app/integrations/yookassa/client.py:478-528`

**Issue:** `create_receipt` has `customer_email: str` as a required parameter and builds `"customer": {"email": customer_email}` unconditionally. With D-10 relaxing the payment gate to accept phone-only clients, a future code path that issues a standalone fiscal receipt for a phone-only client (e.g., a refund receipt) would be unable to pass phone instead of email through this method — it would have to fabricate an email or silently fail. Currently this is not exercised by the phase's changed paths (the webhook-driven `fiscal_receipts` flow calls `create_receipt` only from a staff/webhook path that already has an email), but the API inconsistency between `create_payment` (supports both) and `create_receipt` (email-only) is a latent future bug.

**Fix:** Add an optional `customer_phone: str | None = None` parameter to `create_receipt` and build the customer dict using the same D-10 pattern as `create_payment`:
```python
async def create_receipt(
    self,
    *,
    payment_id: str,
    customer_email: str | None = None,
    customer_phone: str | None = None,
    ...
```
