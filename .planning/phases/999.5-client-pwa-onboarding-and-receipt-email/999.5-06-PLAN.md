<objective>
Fix Issue 1 (MAJOR, UAT test 10): the deterministic per-`(subject_kind, plan_id, client_id, UTC-date)` membership Idempotence-Key (`_derive_idempotency_key`, online_payments/service.py:93) excludes the receipt contact. Phase 999.5's email-OR-phone gate makes the SAME client+plan+day produce different receipt bodies (phone-only via «Чек не нужен» vs email via the gate). Reusing the deterministic key with a changed body → ЮKassa HTTP 400 `invalid_request`, `parameter=Idempotence-Key` → mapped to `permanent_error` → 502 `yookassa_permanent_error`. The existing retry-key fallback (service.py:304) only fires when an `existing` online_payments row is found, but a ЮKassa-rejected attempt INSERTs no row, so the burned key is reused for ~24h and locks the client out.

Implement diagnosis option (b): on a ЮKassa Idempotence-Key collision, retry `create_payment` ONCE with a fresh key, even when no local row exists. Gate the retry narrowly on the ЮKassa error envelope `parameter == "Idempotence-Key"` so unrelated 400s are NOT retried. The existing replay short-circuit (service.py:260) runs FIRST, so genuine same-body double-taps still replay the existing row — replay safety is preserved.

Purpose: unblock real membership checkout end-to-end without weakening the day-key replay/double-tap protections (uq_online_payments_idempotency_key + the partial double-tap index).
Output: a one-retry escape hatch wired through the typed result, with TDD coverage.
</objective>
