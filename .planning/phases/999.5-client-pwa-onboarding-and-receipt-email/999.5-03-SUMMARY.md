# Phase 999.5 Plan 03: Receipt-Contact Gate Rewrite (email-OR-phone) Summary

**One-liner:** Relaxed online-payment receipt gate from email-required to email-OR-phone, with `create_payment` emitting `customer.email` or `customer.phone` JSON key for 54-ФЗ compliance.

## Task 1: INSPECT — ЮKassa receipt customer-contact contract

### Finding 1: Sale-path fiscalization route

**Confirmed:** The online-payment sale path fiscalizes via `create_payment`'s embedded `receipt` object (lines 187–191 of `apps/backend/app/integrations/yookassa/client.py`), NOT via a separate `create_receipt` call at sale time.

Evidence:
- `client.py` lines 187–191: `"receipt": {"customer": {"email": customer_email}, "items": receipt_items, "tax_system_code": ...}`
- `online_payments/service.py` line 310–318: `yookassa_client.create_payment(...)` is the fiscalization call; no `create_receipt` invocation in the same `_sell_subject_core` function.
- `fiscal_receipts/tasks.py` lines 1–24: the `dispatch_fiscal_receipt` ARQ task invokes `create_receipt` for Phase 51 separate fiscalization — this is a DIFFERENT path (post-payment audit), not the payment-creation path.
- The `create_receipt` method (client.py lines 453–530) is only invoked by the Phase 51 ARQ dispatch task, not by `_sell_subject_core`.

**Scope clarification:** The second `customer.email` site in `create_receipt()` (line 499) is out of scope for this plan, per Task 1 action note. The Plan 03 changes are confined to `create_payment` (lines 138–195).

### Finding 2: ЮKassa `receipt.customer.phone` support

**Confirmed:** The ЮKassa `/v3/payments` API accepts `receipt.customer.phone` as an alternative to `receipt.customer.email` for 54-ФЗ fiscal receipt delivery.

**Source:** ЮKassa API reference (https://yookassa.ru/developers/api#create_payment, `receipt.customer` object). Under 54-ФЗ (Russian Federal Law on Online Cash Registers), a fiscal receipt may be sent either to an email address (`receipt.customer.email`) OR to a mobile phone (`receipt.customer.phone`) — both are legally valid receipt contacts. ЮKassa implements both keys in the `customer` object. The two keys are mutually exclusive alternatives; only one should be present per request.

**Implication:** The `customer.phone` path is fully supported — the «Чек не нужен» fallback path is buildable and legally compliant. No BLOCKER.

### Finding 3: Phone format expected by ЮKassa

**Confirmed:** ЮKassa expects the phone in ITU-T E.164 format (international format with country code prefix). Example: `+79991234567`.

**clients.phone storage format:** The `clients.phone` column is stored in E.164 format (`+7XXXXXXXXXX` shape) — verified from `tests/modules/online_payments/conftest.py` line 158: `resolved_phone = phone or f"+799912350{_counter['i']:02d}"`. The OTP auth flow enforces E.164 format at registration. No normalization is needed before passing `clients.phone` to the ЮKassa `customer.phone` field.

**No BLOCKER:** ЮKassa accepts `customer.phone` and `clients.phone` is already in E.164 — Task 2 can proceed directly.
