## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Plan inaccuracy / spec adapter mismatch] Plan grep checks for snake_case property keys in OpenAPI spec returned 0; actual emitted keys are camelCase via Pydantic alias generator**
- **Found during:** Task 1 (Step 4 verification — `grep -F '"trainer_full_name"' apps/backend/openapi.json` returned 0)
- **Issue:** The plan's `<verify>` automation expected `"trainer_full_name"` / `"slot_start_time"` / `"created_by_user_id"` as JSON property keys in `openapi.json`. The Sportzal backend's `BackendSchemaBase` (or a parent `ContractModel`) uses a Pydantic `alias_generator`/`populate_by_name` configuration that emits property keys as **camelCase** (`trainerFullName`, `slotStartTime`, `createdByUserId`). Confirmed by inspecting `spec['components']['schemas']['BookingResponse']['properties']` → `['cancelReason', 'cancelledAt', 'clientId', 'completedAt', 'createdAt', 'createdByUserId', 'id', 'noShowAt', 'ptPackageId', 'slotId', 'slotStartTime', 'status', 'trainerFullName']`.
- **Fix:** Verified the 40-02 Task 2 schema extensions are present under their camelCase aliases instead. The underlying source Pydantic models DO use snake_case attribute names (`apps/backend/app/modules/bookings/schemas.py:197-198` defines `trainer_full_name: str` and `slot_start_time: datetime` on `BookingResponse`); the alias generator converts them at the OpenAPI surface. Grep counts under camelCase: `"trainerFullName"` → 6 occurrences, `"slotStartTime"` → 4 occurrences, `"createdByUserId"` → 8 occurrences. `BookingResponse.createdByUserId` schema confirmed as `anyOf [{format:uuid,type:string}, {type:null}]` (D-40-05 Optional relaxation captured).
- **Files modified:** None (verification-only adjustment)
- **Verification:** `python3` introspection of regenerated `openapi.json` `components.schemas.BookingResponse.properties.createdByUserId` → `{"anyOf": [{"format": "uuid", "type": "string"}, {"type": "null"}], "title": "Createdbyuserid"}` — exactly matches D-40-05 contract.
- **Committed in:** `52f5bac` (atomic regen commit; the data was already present, only the verification gate was off-spec)

## Issues Encountered

- The `export_openapi.py` runner's `print(f"Wrote {target} ({len(payload)} bytes).")` message prints the **Python string length** (`len(payload)` = character count) rather than the **UTF-8 byte count** that actually lands on disk. For Cyrillic-bearing payloads this under-reports by ~the count of 2-byte UTF-8 chars. The first regen printed `213020 bytes` but `wc -c apps/backend/openapi.json` reported `213354` bytes. Investigated initially as a possible non-determinism / partial-write bug; confirmed via `diff` of two consecutive regen outputs that the actual disk bytes are stable (`BOTH_BYTE_STABLE=OK`). Not a defect — just a misleading log line; logged here for future executors. (Out-of-scope tweak — not addressed in this plan.)
