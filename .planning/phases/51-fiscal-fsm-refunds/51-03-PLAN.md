<objective>
Extend the ЮKassa integration adapter (Phase 48) with a `create_receipt` method (POST /v3/receipts) for 54-ФЗ fiscalization. This is the integration-layer method that the Phase 51 `dispatch_fiscal_receipt` ARQ task (plan 51-05) will call.

Purpose: Phase 48 shipped `create_payment`, `get_payment`, `create_refund`, `get_refund` but NOT `create_receipt` — receipts were originally to be embedded inline in `POST /v3/payments` (FISCAL-03 Scenario 1). For refund receipts (kind='refund'), there is no inline embed possible — they need their own POST /v3/receipts call, hence this client extension.

The method mirrors `create_refund` (line 350) byte-for-byte: same classification taxonomy (`ok`/`validation_error`/`transient_error`/`permanent_error`), same idempotency-key header (`Idempotence-Key`), same never-re-raise discipline, same structlog event naming.

Output: 1 method added to `client.py` + 1 dataclass expanded (or confirmed) in `types.py` + 3 respx fixtures + at least 3 unit tests covering ok/transient/permanent classifications.
</objective>

try:

        json=body,
