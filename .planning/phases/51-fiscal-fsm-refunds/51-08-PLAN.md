<objective>
Ship REFUND-01: the operator-facing POST endpoints that initiate an online refund. Operator (reception or owner) calls `POST /api/v1/online-payments/memberships/{id}/refund` (or `.../pt-packages/{id}/refund`), the service applies Phase 32 guards, calls ЮKassa `POST /v3/refunds`, INSERTs an `online_refunds(status='pending')` row, emits an `online_refund_initiated` audit, and returns 202 + the refund identifier.

**Errata #2 resolution — Option A (preferred):**
PATTERNS.md errata #2 flagged that CONTEXT D-51-01's proposed new package `app/api/v1/online_payments/` collides with the existing `app/modules/online_payments/router.py` mount at `/online-payments`. The recommended resolution is **Option A — append the two new refund POST routes to the existing `app/modules/online_payments/router.py`** rather than creating a parallel package. Less disruption; keeps the online-payments user-facing namespace cohesive. This plan implements Option A.

(The schemas — `OnlineRefundRequest` / `OnlineRefundResponse` — were already shipped in plan 51-02 inside `app/modules/online_refunds/schemas.py`, NOT in a separate `app/api/v1/online_payments/schemas.py`. The router imports from there.)

**Call-then-INSERT discipline (D-51-09 preferred variant):**
The service calls ЮKassa BEFORE any DB write. On `classification == "ok"`, it INSERTs the OnlineRefund row with the real `yookassa_refund_id` already populated. The trade-off — a leaked ЮKassa refund-creation if the DB INSERT fails afterward — is reconciled by the poll_pending_refunds cron (plan 51-09) via the `uq_online_refunds_yookassa_refund_id` UNIQUE backstop on retry.

Output: 1 new service file + 1 modified router file (2 endpoints added) + 4 test files covering happy paths, guard rejections, idempotency-key replay, and ЮKassa classification mapping.

    session: AsyncSession,
    actor: CurrentUser,
    *,
    membership_id: UUID | None = None,
    pt_package_id: UUID | None = None,
    idempotency_key: UUID,
    reason: str | None,
    yookassa_client: YooKassaClient,

    """Phase 51 REFUND-01 initiate (D-51-08/09).

    Caller passes EXACTLY ONE of membership_id or pt_package_id (router enforces by
    splitting into two endpoints calling this with the correct kwarg).

    Sequence:
      1. Idempotency-Key replay check — if a row with this key exists, return 202
         with the existing row's data (D-51-Discretion Idempotency-Key on /v3/refunds).
      2. Specific-first guards (D-32-11 lineage):
         a. Load Membership (or PtPackage) → 404 if missing.
         b. status='frozen' → 409 must_unfreeze_first (B-08).
         c. has_renewal_descendants(...) → 409 cannot_refund_renewed_source (B-09).
         d. `_assert_refund_can_transition(subject_row, target='cancelled')` (refund-local helper defined in this same file) → 409 invalid_transition.
         e. Locate the original OnlinePayment row by (client_id, membership_plan_id|pt_package_plan_id) — 404 online_payment_not_found.
         f. Locate the original Payment ledger row by op.id → 404 original_payment_not_found.
      3. D-51-09 call-then-INSERT:
         a. await yookassa_client.create_refund(payment_id=op.yookassa_payment_id,
                                                amount_kopecks=abs(original_payment.amount_kopecks),
                                                idempotency_key=str(idempotency_key)).

            - validation_error  → raise ValidationAppError(ErrorCode.YOOKASSA_VALIDATION_ERROR.value)
            - transient_error   → raise ServiceUnavailableAppError(ErrorCode.YOOKASSA_UNAVAILABLE.value)
            - permanent_error   → raise BadGatewayAppError(ErrorCode.YOOKASSA_PERMANENT_ERROR.value)
