<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process env -> Settings | env vars deserialized into typed `Settings` (pydantic-settings) — boundary where attacker-controlled env (in compromised host) flows into app config |
| pyproject.toml -> resolved deps | dependency resolver pulls code from PyPI — supply-chain boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Tampering | uv.lock supply-chain | mitigate | Pin upper bounds (`<3`, `<26`, `<23`) on all three new deps; `uv lock --check` runs in CI to block unintended drift |
| T-04-02 | Information disclosure | `secret_key`, `cookie_secure` | mitigate | `secret_key` already typed as `SecretStr` (existing); `cookie_secure: bool` ensures coercion (Pitfall G) — never logged; `Settings.__repr__` will not expose `SecretStr` payload |
| T-04-03 | Elevation of privilege | `cookie_secure=False` in production | accept (Phase 4) / mitigate (Phase 5) | Phase 4 ships the field with dev-friendly default; Phase 5's `create_app` will add `assert environment != "prod" or cookie_secure` startup assertion. Documented in .env.example comment "prod startup ASSERTS true" |
| T-04-04 | Denial of service | TTL fields set to extreme values | accept | env is operator-controlled; bounds (`int`) prevent type confusion. Future: add Pydantic `Field(ge=...)` validators if abuse vectors appear |
| T-04-05 | Spoofing | algorithm-confusion if `pyjwt` <2.12.1 | mitigate | Pin `pyjwt>=2.12.1,<3` — 2.x requires explicit `algorithms=` argument on decode; algorithm confusion attack pre-empted at the library level. Plan 04-07 enforces `algorithms=["HS256"]`. |
</threat_model>
