## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PWA client → client_portal API | The cancel request crosses from the browser to the session-scoped, CSRF-protected client endpoint. The client supplies only its own booking id; the server re-checks ownership. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-77-01 | Information Disclosure (IDOR) | POST /booking/{id}/cancel | accept | No new vector — endpoint already collapses non-owned booking to 404 (anti-oracle, T-71-28). The PWA passes only its own `b.id`; server re-validates ownership. No client-side trust placed in the id. |
| T-77-02 | Tampering | useCancelBooking mutateAsync call site | mitigate | No raw user input is interpolated into the path beyond the existing booking id param (typed `{ bookingId: string }`). Error copy is static RU strings; backend error bodies are mapped, never rendered verbatim, so a malicious 409/error body cannot inject markup. |
| T-77-03 | Denial of Service (double-submit) | cancel-confirm button | mitigate | Button is disabled while `isPending` (D-77-02), preventing rapid duplicate cancel calls from a single confirm; backend cancel is idempotent on already-cancelled bookings. |
| T-77-SC | Tampering | npm/pnpm installs | accept | No new packages installed — uses existing useCancelBooking hook and the established Vitest/Testing-Library harness. No legitimacy gate required. |

**No new external dependency and no new endpoint are introduced; no high-severity threat exists for FIX-01.** The only network call is to an already-shipped, ASVS-L1-reviewed, session-scoped, IDOR-safe endpoint.
