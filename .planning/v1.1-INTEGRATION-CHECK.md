## Summary

- Phases inspected: 10 (phases 01-03 are v1.0 skeleton; phases 04-10 are the v1.1 surface)
- Provides/Consumes mismatches: 1
- E2E flow gaps: 3 (clients flow blocked; auth flow has one fragile-by-design corner)

- Affected requirement IDs: FE-01, FE-04, CLIENTS-01, CLIENTS-06, CLIENTS-07, AUTH-TG-01, AUTH-TG-03, INFRA-05

The backend (phases 04-09) is wired end-to-end and the OpenAPI/typegen pipeline is correct. The break sits at the Phase 10 ↔ Phase 8/9 boundary: the admin-web `Client` domain type and the http service layer were not updated to match the actual backend `ClientResponse` shape. Auth flows are wired correctly; only the access-cookie-only-expired path through `/auth/me` is by-design fragile.

## Verdict

**issues_found**

The backend half of v1.1 (phases 04-09) is internally well-wired: every Provides → Consumes link verifies, the OpenAPI export is byte-stable, the api-client's typegen, single-flight refresh, and CSRF injection all match the backend contract, and RBAC parity holds 1:1. The break is concentrated at the Phase 8 ↔ Phase 10 boundary on the **Clients** surface: the admin-web `Client` domain type and `ClientCreateInput` contract were not updated to match the actual `ClientResponse` / `ClientCreateRequest` shape that ship in `openapi.json` and the codegen pipeline does not catch the drift because the FE intentionally keeps its domain types hand-rolled.

Concretely, an operator running `VITE_API_MODE=http` against the real backend can:
- Log in via email/password — works
- Log in via Telegram OTP — works (modulo the dead `expiresAt` contract field)
- Have refresh / logout / 401-loop guards behave correctly
- See the clients list — the ФИО column is empty everywhere (`fullName` is undefined)
- Open a client detail — the delete dialog title is broken
- Create a client — the form submit returns 422 (`extra fields not permitted`) on every attempt
- Edit a client — the optimistic update throws a `TypeError` before the request leaves the browser
- Soft-delete a client (as owner) — works on the wire

Findings F-01 and F-02 are BLOCKER for the milestone success criterion "Visiting `/clients/*` with `VITE_API_MODE=http` lists/searches/creates/edits/(owner-)deletes clients via @sportzal/api-client; mutations use onMutate/onError/onSettled for optimistic updates with rollback". The remaining findings (F-03, F-04, F-05, F-06) are MINOR and do not block milestone closure on their own.

The fix is a Phase 10 follow-up: either (a) update `entities/client/types.ts` and `contracts/clients.ts` to mirror `ClientResponse`/`ClientCreateRequest`, fan out the `lastName/firstName/middleName` split into the Table/Form/Dialog components, and rename `birthDate` → `birthday`; or (b) introduce an explicit shape adapter in `services/http/clients.ts` that maps backend → FE domain in both directions. The first option is cleaner because it eliminates the parallel domain model.
