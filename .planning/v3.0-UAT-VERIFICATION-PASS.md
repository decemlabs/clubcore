## Found, NOT fixed (needs decision)

- **REV-01 (HIGH)** — revoke-invitation is broken two ways: `useRevokeInvitation` POSTs
  **no body** (backend `InvitationRevokeRequest` body is required → 422), AND it passes
  `user.id` while the endpoint needs the **invitation token row id** (`UserSchema` doesn't
  expose it). Fixing needs a **backend** contract change (accept user_id and resolve the
  pending invite, or surface the token id in `GET /users`) — outside the frontend-only,
  no-new-endpoints v3.0 scope. Deactivate (active user) works; only the pending-invite
  revoke path is broken. **Flagged as a follow-up.**
  - **RESOLVED 2026-06-14 (quick `260614-jt7`, commits `1c527287`/`06bf3d8d`/`f8edf168`/`83f054f9`).**
    Variant B: `GET /users` now surfaces `invitationTokenId` (the live token row id); the
    FE passes it + a `{ reason }` body. Additionally, per product decision, revoke now
    soft-deletes the pending placeholder user so the row disappears from «Доступы команды».
    Live-browser verified end-to-end: invite → revoke → **204** → row gone.
