## 1. Login as owner / reception

`POST /api/v1/auth/login` принимает `{email, password}`, проверяет Argon2id-hash через
`apps/backend/app/modules/auth/router.py:69-89`, и при успехе:

- Ставит cookie `sz_access` (HTTP-only, `Path=/`) — короткоживущий access JWT.
- Ставит cookie `sz_refresh` (HTTP-only, `Path=/api/v1/auth`) — узкоскоупный refresh token (минимизация exposure).
- Ставит cookie `sportzal_csrf` (НЕ httpOnly, `Path=/`) — JS-readable, см. § 3.
- Возвращает `ResponseEnvelope[LoginResponse]` с `data.user` (UserPublic).

Обе роли (`owner`, `reception`) используют один и тот же endpoint; RBAC дальше
прописан per-route (см. `OWNER_ONLY` frozenset в `apps/backend/app/core/rbac.py`).

```bash
curl -i -s -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -c cookies.txt \
  -d '{"email":"verify_owner@local.dev","password":"<owner-password>"}'
```

При успехе: `HTTP/1.1 200 OK` + три `Set-Cookie` заголовка + body
`{"data":{"user":{"id":"...","role":"owner",...}}}`. Cookie jar `cookies.txt`
далее используется для всех последующих запросов.

## 2. Refresh rotation family

`POST /api/v1/auth/refresh` читает `sz_refresh` cookie напрямую (без авторизационной
dependency — истёкший access cookie не должен блокировать refresh, см.
`apps/backend/app/modules/auth/router.py:92-119`). Семантика — **rotation family**:
старый refresh инвалидируется, выдаётся новый. Параллельные клиенты должны
шарить один in-flight refresh (single-flight discipline) — иначе race вызовет
`session_expired` на всех, кроме первого.

См. **`packages/api-client/README.md` § Single-flight refresh** — runtime
contract: module-scoped `inFlightRefresh: Promise<Response> | null`, любой 401
от non-`/auth/*` пути триггерит ОДИН refresh, параллельные запросы ждут тот же promise.

```bash
curl -i -s -X POST http://localhost:8000/api/v1/auth/refresh \
  -b cookies.txt -c cookies.txt
```

При успехе: `HTTP/1.1 200 OK` + три обновлённых `Set-Cookie`, body `{"data":null}`.

## 3. CSRF on mutating requests

Каждый mutating HTTP verb (POST / PATCH / PUT / DELETE) **должен** содержать header
`X-CSRF-Token: <значение sportzal_csrf cookie>`. Backend проверяет совпадение через
`verify_csrf` dependency; mismatch → `403 csrf_mismatch`. GET / HEAD / OPTIONS
от CSRF освобождены (соответствует server-side `_SAFE_METHODS` short-circuit,
Phase 6 D-04).

Дополнительно, mutating endpoints, изменяющие money/membership state, требуют
`Idempotency-Key: <UUID>` header (см. `apps/backend/app/core/idempotency.py` —
two-phase Redis claim защищает от double-submit). Отсутствие ключа → `422
idempotency_key_required`. Re-submit с тем же ключом и тем же телом → cached 200;
тем же ключом и **разным** телом → `422 idempotency_key_reuse`.

См. **`packages/api-client/README.md` § CSRF** — fetcher автоматически читает
cookie и проставляет header на mutating methods.

```bash
CSRF=$(awk '/sportzal_csrf/ {print $7}' cookies.txt)
curl -i -s -X POST http://localhost:8000/api/v1/memberships \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF" \
  -H "Idempotency-Key: $(uuidgen)" \
  -b cookies.txt \
  -d '{"clientId":"<uuid>","planId":"<uuid>","amountKopecks":300000}'
```

## 4. Telegram OTP (client-app path)

Three-step flow для self-service client app:

1. **Start**: `POST /api/v1/auth/telegram/start` — backend минтит deep-link token,
   возвращает `{deepLinkUrl, deepLinkToken}`. URL ведёт на `t.me/<bot>?start=<token>`.
2. **Status (poll)**: `GET /api/v1/auth/telegram/status?token=<deepLinkToken>` —
   `{bound: false}` пока пользователь не нажал Start в боте; `{bound: true}` после
   того, как bot worker записал 6-значный OTP code (DMed to user).
3. **Verify**: `POST /api/v1/auth/telegram/verify` с `{deepLinkToken, code}` —
   issue cookies идентично `/login` (см. § 1) + emit `login_success` с
   `channel='telegram'`.

Backend reuse: bot worker — отдельный long-polling процесс
(`apps/backend/app/workers/telegram_bot.py`); он же серверит `/checkin` для существующих
membership-holders. Endpoints **не** авторизованы — identity живёт в body, CSRF
exempt (Phase 6 D-09).

```bash
curl -i -s -X POST http://localhost:8000/api/v1/auth/telegram/start \
  -H "Content-Type: application/json"
# → 200 {"data":{"deepLinkUrl":"https://t.me/...","deepLinkToken":"abc..."}}
```

## 5. Logout-all

`POST /api/v1/auth/logout-all` уничтожает ВСЕ alive families текущего пользователя
(не только текущую сессию) + чистит cookies caller'а
(`apps/backend/app/modules/auth/router.py:225-237`). Это nuke-option для
"подозреваю что меня скомпрометировали" UX.

Требует `X-CSRF-Token` (mutating). Остальные сессии того же пользователя
становятся невалидны на следующем mutating request (CSRF проверка пройдёт, но
access cookie уже rejected) ИЛИ на следующем refresh (refresh row removed) — клиент
видит 401 и редиректит на `/login`.

```bash
CSRF=$(awk '/sportzal_csrf/ {print $7}' cookies.txt)
curl -i -s -X POST http://localhost:8000/api/v1/auth/logout-all \
  -H "X-CSRF-Token: $CSRF" \
  -b cookies.txt -c cookies.txt
# → 200 {"data":null}, cookies cleared on response.
```
