## 1. Docker Compose bring-up

Стек запускается одной командой из директории `apps/backend/`.
`migrate` — one-shot сервис (Alembic `upgrade head`), гарантирован `condition:
service_completed_successfully` до старта `backend` и воркеров.

```bash
cd apps/backend

# Скопируйте .env.example в .env, заполните секреты (SECRET_KEY, OWNER_EMAIL/PASSWORD, etc.)
cp .env.example .env
# <отредактируйте .env>

# Запуск: postgres + redis → migrate → backend + telegram-bot + arq-worker
docker compose up --build
```

При успехе: в stdout появляются строки вида
`backend-1  | INFO:     Application startup complete.`
Убедитесь, что `migrate-1 exited with code 0` (Alembic applied all migrations,
HEAD — Phase 59/60 ревизии: recurring templates + time-off + trainer-usage
report tables).

Smoke-check — backend отвечает:

```bash
curl -i http://localhost:8000/api/v1/health
# → HTTP/1.1 200 OK  {"data":{"status":"ok"}}
```

## 2. Payroll golden-path (owner-only, eyeball-match с фикстурными константами)

Этот сценарий проверяет детерминированную арифметику из
`apps/backend/tests/integration/payroll/test_payroll_preview.py`:

```
Pure-pct golden:  revenue 100 000 kop, bps 1500 (15%) → commission 15 000, total 15 000
Pure-fixed golden: session_fee 50 000 kop × 3 сессии → fixed 150 000, commission 0
Hybrid golden:    pct 1000 bps + fixed 30 000/сессия, 2 сессии, revenue 200 000 →
                  commission 20 000 + fixed 60 000 = total 80 000
```

Точное число `total_kopecks`, возвращаемое `GET /payroll/preview`, зависит от
того, какой фикстурный seed развёрнут в локальном Postgres (поставщик
демо-данных). Оператор eyeball-матчит против таблицы констант выше или,
если seed детерминирован, против ожидаемого значения из теста.

**Шаг 2.1 — Login as owner, сохранить cookie jar + извлечь CSRF:**

```bash
curl -i -s -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -c cookies.txt \
  -d '{"email":"verify_owner@local.dev","password":"<owner-password>"}'
```

При успехе: `HTTP/1.1 200 OK` + три `Set-Cookie` (`sz_access`, `sz_refresh`,
`sportzal_csrf`) + body `{"data":{"user":{"id":"...","role":"owner",...}}}`.

```bash
# Извлеките CSRF-токен из cookies.txt для mutating-вызовов ниже:
CSRF=$(awk '/sportzal_csrf/ {print $7}' cookies.txt)
echo "CSRF=$CSRF"
```

Подставьте `<TRAINER_ID>` — UUID существующего тренера (получить можно через
`GET /api/v1/trainers` под owner-сессией). Период ниже соответствует
фикстурам preview-теста (`2026-04-01..2026-04-30`).

**Шаг 2.2 — Установить compensation config (PUT, INSERT-only versioned):**

```bash
curl -i -s -b cookies.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF" \
  -X PUT "http://localhost:8000/api/v1/payroll/trainer-configs/<TRAINER_ID>" \
  -d '{
    "commissionPctBps": 1500,
    "sessionFeeKopecks": null,
    "effectiveFrom": "2026-01-01"
  }'
```

При успехе: `HTTP/1.1 200 OK` + ResponseEnvelope с
`data.id` (новой версии конфига), `data.commissionPctBps = 1500`,
`data.sessionFeeKopecks = null`, `data.effectiveFrom = "2026-01-01"`.
Каждый PUT вставляет НОВУЮ строку; прошлые версии не модифицируются (PAY-01 / D-58-10).

**Шаг 2.3 — Read-only accrual preview (GET, zero-persistence):**

```bash
curl -i -s -b cookies.txt \
  "http://localhost:8000/api/v1/payroll/preview?trainerId=<TRAINER_ID>&periodStart=2026-04-01&periodEnd=2026-04-30"
```

При успехе: `HTTP/1.1 200 OK` +
`{"data":{"sessionCount":N,"fixedKopecks":X,"commissionKopecks":Y,"totalKopecks":X+Y}}`.

Оператор eyeball-матчит `totalKopecks` против ожидаемого значения из
seed-фикстуры (например, при pure-pct 15% и выручке 100 000 kop из фикстур
preview-теста → `commissionKopecks = 15000`, `totalKopecks = 15000`).

Preview — read-only: НИ одна строка `trainer_payroll_accruals` не
вставляется, НИ одно audit-событие не эмитится (D-58-12 / PITFALL 1).

**Шаг 2.4 — Append accrual ledger entry (POST):**

```bash
curl -i -s -b cookies.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF" \
  -X POST "http://localhost:8000/api/v1/payroll/accruals" \
  -d '{
    "trainerId": "<TRAINER_ID>",
    "periodStart": "2026-04-01",
    "periodEnd": "2026-04-30"
  }'
```

При успехе: `HTTP/1.1 201 Created` + ResponseEnvelope с
`data.id` (UUID нового accrual), `data.accrualKopecks` равным
`totalKopecks` из шага 2.3 (расчёт идёт через тот же
`service.compute_accrual_components` — drift-free, PITFALL 1 / T-58-23).
Сохраните `data.id` как `<ACCRUAL_ID>` для следующего шага.

Идемпотентность: повторный POST с тем же `(trainerId, periodStart, periodEnd)`
вернёт `HTTP/1.1 409` с `code: "payroll_period_already_run"` (T-58-27 / D-58-06).

**Шаг 2.5 — Mark accrual paid (POST, pending→paid однократный переход):**

```bash
curl -i -s -b cookies.txt \
  -H "X-CSRF-Token: $CSRF" \
  -X POST "http://localhost:8000/api/v1/payroll/accruals/<ACCRUAL_ID>/mark-paid"
```

При успехе: `HTTP/1.1 200 OK` + ResponseEnvelope с
`data.status = "paid"` и непустым `data.paidAt` (UTC ISO timestamp).
Повторный mark-paid того же accrual → `HTTP/1.1 409` (transition guard,
PAY-04 / D-58-08).

Это live cross-validation `apps/backend/tests/integration/payroll/`
goldens (VER-02 / PAY-01..04 / ROADMAP Phase 58 SC).

## 3. Recurring schedule + time-off golden-path (owner-only)

Этот сценарий проверяет создание и деактивацию recurring slot template +
создание и удаление time-off блока. Оператор подтверждает, что
slot-генератор уважает time-off окна (REC-04 / TOFF-03 acceptance) через
`GET /api/v1/trainer-slots`.

Убедитесь, что вы залогинены как owner (cookies.txt + `$CSRF` из §2.1).
Подставьте `<TRAINER_ID>` — тот же UUID, что и в §2.

**Шаг 3.1 — Создать recurring template (POST):**

```bash
curl -i -s -b cookies.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF" \
  -X POST "http://localhost:8000/api/v1/recurring-templates" \
  -d '{
    "trainerId": "<TRAINER_ID>",
    "dayOfWeek": 1,
    "startTime": "10:00:00",
    "endTime": "11:00:00",
    "validFrom": "2026-06-01",
    "validUntil": "2026-12-31"
  }'
```

При успехе: `HTTP/1.1 201 Created` + ResponseEnvelope с
`data.id` (UUID нового template), `data.isActive = true`,
`data.dayOfWeek = 1` (вторник ISO). Сохраните `data.id` как `<TEMPLATE_ID>`.

DTO-уровень проверки (T-59-06 double gate): `dayOfWeek ∈ [0,6]`,
`endTime > startTime`, `validUntil >= validFrom` если задан.

**Шаг 3.2 — Список recurring templates (GET, reception+owner; пагинация):**

```bash
curl -i -s -b cookies.txt \
  "http://localhost:8000/api/v1/recurring-templates?trainerId=<TRAINER_ID>&page=1&pageSize=20"
```

При успехе: `HTTP/1.1 200 OK` +
`{"data":{"items":[...],"total":N,"page":1,"pageSize":20}}`.
В `items` присутствует template из §3.1.

Внимание: GET reception-accessible per D-59-08 (booking flow требует
read-доступ к расписанию у ресепшен).

**Шаг 3.3 — Создать time-off блок, перекрывающий recurring окно (POST):**

```bash
curl -i -s -b cookies.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF" \
  -X POST "http://localhost:8000/api/v1/time-off" \
  -d '{
    "trainerId": "<TRAINER_ID>",
    "blockStart": "2026-06-02T07:00:00Z",
    "blockEnd":   "2026-06-02T09:00:00Z",
    "reason": "Семейные обстоятельства"
  }'
```

При успехе: `HTTP/1.1 201 Created` + ResponseEnvelope с
`data.id` (UUID time-off), `data.reason`, `data.blockStart`/`blockEnd`
в UTC. Сохраните `data.id` как `<TIME_OFF_ID>`.

`blockStart = 2026-06-02T07:00:00Z` = `2026-06-02 10:00 MSK` —
перекрывает recurring окно вторника (`dayOfWeek = 1`,
`startTime = 10:00:00`) на 1 час. DTO-уровень проверки (T-59-07):
оба timestamp обязаны быть timezone-aware (`Z` суффикс),
`blockEnd > blockStart`.

Если у тренера уже забронированы слоты внутри указанного окна, ответ —
`HTTP/1.1 409` с `code: "time_off_booked_conflict"`. Чтобы форсировать,
повторите запрос с `?force=true` (TOFF-03).

**Шаг 3.4 — Список time-off (GET, reception+owner):**

```bash
curl -i -s -b cookies.txt \
  "http://localhost:8000/api/v1/time-off?trainerId=<TRAINER_ID>&page=1&pageSize=20"
```

При успехе: `HTTP/1.1 200 OK` + paginated envelope.
В `items` присутствует блок из §3.3.

GET reception-accessible per D-59-08.

**Шаг 3.5 — Eyeball-check: time-off уважается slot-генератором.**

```bash
curl -i -s -b cookies.txt \
  "http://localhost:8000/api/v1/trainer-slots?trainerId=<TRAINER_ID>&fromDate=2026-06-02&toDate=2026-06-02"
```

Ожидаемое: в response `data.items` НЕТ слота на `2026-06-02 10:00–11:00 MSK`
(перекрыт time-off блоком из §3.3). Это live валидация REC-04 / TOFF-03
acceptance criterion: recurring-templates автоматически материализуются
в слоты, но time-off окна вырезают их из генерации.

**Шаг 3.6 — Деактивировать recurring template (POST):**

```bash
curl -i -s -b cookies.txt \
  -H "X-CSRF-Token: $CSRF" \
  -X POST "http://localhost:8000/api/v1/recurring-templates/<TEMPLATE_ID>/deactivate"
```

При успехе: `HTTP/1.1 200 OK` + ResponseEnvelope с
`data.id = <TEMPLATE_ID>`, `data.isActive = false`.

**Шаг 3.7 — Удалить time-off блок (DELETE):**

```bash
curl -i -s -b cookies.txt \
  -H "X-CSRF-Token: $CSRF" \
  -X DELETE "http://localhost:8000/api/v1/time-off/<TIME_OFF_ID>"
```

При успехе: `HTTP/1.1 204 No Content` (тело пустое).

## 4. Trainer-usage report — JSON + CSV/Excel Cyrillic check (owner-only)

Этот сценарий проверяет агрегированный отчёт по тренерам за период
(RPT-01..04) и live-валидирует CSV-дисциплину Phase 60 D-60-11
(UTF-8 BOM + RFC-4180 dialect → Excel открывает без mojibake).

Убедитесь, что вы залогинены как owner (cookies.txt из §2).
Период ниже произвольный (подставьте окно, для которого есть фикстурные
данные — `2026-05-01..2026-05-31` соответствует
`apps/backend/tests/integration/reports/test_reports_trainers.py` happy-path).

**Шаг 4.1 — JSON-отчёт (GET):**

```bash
curl -i -s -b cookies.txt \
  "http://localhost:8000/api/v1/reports/trainers?fromDate=2026-05-01&toDate=2026-05-31"
```

При успехе: `HTTP/1.1 200 OK` + ResponseEnvelope с
`data.fromDate = "2026-05-01"`, `data.toDate = "2026-05-31"`,
`data.trainers = [...]`. Каждая строка содержит
`sessionCount`, `hoursTotal`, `uniqueClientsCount`, `utilizationPct`,
`revenueKopecks`, `totalAccruedKopecks`, `totalPaidKopecks`.

Оператор eyeball-матчит `sessionCount`, `revenueKopecks`,
`totalAccruedKopecks` против фикстур-сидов из
`apps/backend/tests/integration/reports/test_reports_trainers.py` (точные
числа зависят от того, какой demo-seed развёрнут).

Ordering: список упорядочен по `sessionCount` DESC, затем по имени
ASC (D-60-03 deterministic ordering).

**Шаг 4.2 — CSV-скачивание (GET с `Accept: text/csv`):**

```bash
curl -i -s -b cookies.txt -OJ \
  "http://localhost:8000/api/v1/reports/trainers.csv?fromDate=2026-05-01&toDate=2026-05-31"
# Сохраняется как `trainers.csv` (имя из Content-Disposition)
```

При успехе: `HTTP/1.1 200 OK` +
`Content-Type: text/csv; charset=utf-8` +
`Content-Disposition: attachment; filename="trainers.csv"`.
Первые 3 байта файла — `EF BB BF` (UTF-8 BOM, Phase 56 D-13 / Phase 60 D-60-11).

Быстрая проверка BOM:

```bash
head -c 3 trainers.csv | xxd
# → 00000000: efbb bf                                  ...
```

**Шаг 4.3 — Открыть `trainers.csv` в Excel (Windows) или LibreOffice
Calc / Numbers (macOS).**

Откройте файл двойным кликом (Excel) или Файл → Открыть
(LibreOffice / Numbers).

Ожидаемое:
- Файл открывается сразу, без диалога импорта кодировки.
- Имена тренеров с кириллицей (например, "Анна Петрова", "Иван Сидоров")
  отображаются корректно — БЕЗ `?`, `Ã` или прочих mojibake-артефактов
  (валидирует UTF-8 BOM из шага 4.2).
- Колонки kopecks (`revenueKopecks`, `totalAccruedKopecks`,
  `totalPaidKopecks`) — целые числа.
- Колонки дат (`fromDate`, `toDate`) — формат `YYYY-MM-DD`.
- Колонка `utilizationPct` для тренеров без `weeklyCapacityHours` —
  пустая ячейка (НЕ `null` строкой, НЕ `0`) (D-60-11).

Если кириллица отображается как `?` или `Ã` — BOM повреждён;
зафиксируйте скриншот и сообщите команде backend. Это блокер
для милестоун-релиза v1.9.

Это live cross-validation
`apps/backend/tests/integration/reports/test_reports_trainers.py`
CSV-голденов (RPT-03 / EXP-04 / T-56-07 / Phase 60 D-60-11).

## 5. Reception 403 enumeration — 12 owner-only routes

Все 12 mutating + read-aggregate endpoints v1.9 поверхности — owner-only:
`(VIEW, REPORTS)`, `(VIEW, COMPENSATION)`, `(CREATE, COMPENSATION)`,
`(VIEW, PAYROLL)`, `(LIST, PAYROLL)`, `(CREATE, PAYROLL)`,
`(EDIT, PAYROLL)`, `(REFUND, PAYROLL)`, `(EDIT, SCHEDULE_SLOTS)`,
`(DELETE, SCHEDULE_SLOTS)` входят в `OWNER_ONLY` frozenset
(`apps/backend/app/core/permissions.py:62-141`). Reception получает
`403 forbidden` (T-58-17 / T-58-22 / T-58-26 / T-59-* mitigate).

**Важно — НЕ в 403-перечислении (reception-accessible per D-59-08
booking flow):**
- `GET /api/v1/recurring-templates` — список templates
- `GET /api/v1/time-off` — список time-off блоков

Эти GET-LIST endpoints специально оставлены доступными для ресепшен,
потому что booking-поток нуждается в чтении расписания и блокировок.
Оператор подтверждает reception-403 только на 12 owner-gated routes
ниже.

**Шаг 5.1 — Login as reception:**

```bash
curl -i -s -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -c cookies_reception.txt \
  -d '{"email":"verify_reception@local.dev","password":"<reception-password>"}'
# → HTTP/1.1 200 OK  {"data":{"user":{"role":"reception",...}}}

CSRF_REC=$(awk '/sportzal_csrf/ {print $7}' cookies_reception.txt)
echo "CSRF_REC=$CSRF_REC"
```

**Шаг 5.2 — Прогон 12 owner-only routes под reception-сессией.**

Каждый из 12 запросов ниже должен вернуть `HTTP/1.1 403 Forbidden` с
телом `{"code":"forbidden","message":"..."}`.

Подставьте `<TRAINER_ID>`, `<ACCRUAL_ID>`, `<TEMPLATE_ID>`,
`<TIME_OFF_ID>` любыми валидными UUID — в reception-сессии 403 срабатывает
ДО валидации body / path, поэтому несуществующие UUID допустимы.

```bash
# 1. PUT /api/v1/payroll/trainer-configs/{trainer_id} — set comp config
curl -i -s -b cookies_reception.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF_REC" \
  -X PUT "http://localhost:8000/api/v1/payroll/trainer-configs/00000000-0000-0000-0000-000000000001" \

# 3. GET /api/v1/payroll/preview — read-only accrual preview

  "http://localhost:8000/api/v1/payroll/preview?trainerId=00000000-0000-0000-0000-000000000001&periodStart=2026-04-01&periodEnd=2026-04-30"

# 4. POST /api/v1/payroll/accruals — append accrual
curl -i -s -b cookies_reception.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF_REC" \
  -X POST "http://localhost:8000/api/v1/payroll/accruals" \
  -d '{"trainerId":"00000000-0000-0000-0000-000000000001","periodStart":"2026-04-01","periodEnd":"2026-04-30"}'

# 5. GET /api/v1/payroll/accruals — paginated list
curl -i -s -b cookies_reception.txt \
  "http://localhost:8000/api/v1/payroll/accruals?page=1&pageSize=20"

# 6. POST /api/v1/payroll/accruals/{accrual_id}/mark-paid — mark paid
curl -i -s -b cookies_reception.txt \
  -H "X-CSRF-Token: $CSRF_REC" \
  -X POST "http://localhost:8000/api/v1/payroll/accruals/00000000-0000-0000-0000-000000000002/mark-paid"

# 7. POST /api/v1/recurring-templates — create recurring template
curl -i -s -b cookies_reception.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF_REC" \
  -X POST "http://localhost:8000/api/v1/recurring-templates" \
  -d '{"trainerId":"00000000-0000-0000-0000-000000000001","dayOfWeek":1,"startTime":"10:00:00","endTime":"11:00:00","validFrom":"2026-06-01"}'

# 8. POST /api/v1/recurring-templates/{template_id}/deactivate — deactivate
curl -i -s -b cookies_reception.txt \
  -H "X-CSRF-Token: $CSRF_REC" \
  -X POST "http://localhost:8000/api/v1/recurring-templates/00000000-0000-0000-0000-000000000003/deactivate"

# 9. POST /api/v1/time-off — create time-off block
curl -i -s -b cookies_reception.txt \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: $CSRF_REC" \

# 11. GET /api/v1/reports/trainers — JSON trainer-usage report
curl -i -s -b cookies_reception.txt \
  "http://localhost:8000/api/v1/reports/trainers?fromDate=2026-05-01&toDate=2026-05-31"

# 12. GET /api/v1/reports/trainers.csv — CSV trainer-usage report
curl -i -s -b cookies_reception.txt \
```

Ожидаемое: все 12 запросов возвращают `HTTP/1.1 403 Forbidden` + тело

Это ручная кросс-валидация RBAC-граней, автоматизированных в

reception → 403 across all OWNER_ONLY routes) +
