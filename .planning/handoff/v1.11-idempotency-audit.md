# v1.11 Idempotency Audit — Endpoint Classification

**Phase:** 66-idempotency-hardening
**Requirement:** IDM-01
**Produced by:** 66-01-PLAN.md
**Date:** 2026-05-29

This document is the **single source of truth** for the classification of every
mutating endpoint (POST/PATCH/PUT/DELETE) under `apps/backend/app/api/v1/`.
Downstream plans 66-03 (IDM-07 wiring) and 66-04 (IDM-04 `$ref` injection)
consume the **Category-A operationId set** at the bottom of this document
verbatim.

---

## Classification Rubric (D-66-CLASSIFY-RUBRIC)

| Class | Meaning | Criteria |
|-------|---------|----------|
| **A** | Enforce `Idempotency-Key` | Financial / value-creating mutations (sales, refunds, payment creation); membership state transitions that emit audit events or charge; any POST create NOT already guarded by a DB uniqueness gate making double-submit harmless. |
| **B** | Exempt | Read-only routes; the ЮKassa webhook (separate `cc:yookassa:webhook:` dedup, D-11-IDM-WEBHOOK); naturally idempotent absolute-value PATCH/PUT and soft-delete DELETE — UNLESS they emit audit events on every call, in which case → A. |
| **C** | Inconsistent → move to A | Endpoints that **should** be A but lack `Depends(verify_idempotency)` today; become IDM-07's wiring list. |

> **Key principle:** already-wired = A (✓). Should-be-wired but not yet = C (IDM-07 target). Exempt = B.

## Refund Endpoints — Explicit A-vs-B Decision (T-66-02)

This section documents the deliberate classification decision required by the threat model.

### Cash refunds: `refund_membership`, `refund_pt_package`

- `refund_membership` (operationId: `refund_membership`): **B** — DB partial UNIQUE `uq_payments_refund_of_alive` is the load-bearing guard. Router docstring explicitly says no Idempotency-Key (D-32-20). Second call → 409 `already_refunded`.
- `refund_pt_package` (operationId: `refund_pt_package`): **A (already wired)** — this is a cash refund of a PT package and `verify_idempotency` IS present at pt_packages/router.py:469. Classified A and included in CATEGORY_A_OPERATION_IDS.

### Online refunds: `refund_membership_online`, `refund_pt_package_online`

Both classified **B — DB-guarded**:

**Why B and not A/C:** The endpoints accept a caller-supplied `idempotency_key` in the request **body** (not header), which is forwarded verbatim to the ЮKassa `Idempotence-Key` header. The ЮKassa-facing idempotency is thus already operator-contractual via the body field. Additionally, the DB layer has a `partial UNIQUE` constraint (`uq_online_refunds_alive_per_online_payment` on `(payment_id) WHERE status != 'failed'`) that raises `RefundAlreadyInFlightError` (409 `refund_already_in_flight`) on concurrent duplicate. The service explicitly documents: *"partial UNIQUE backstop. Mirror of Phase 25 D-25-22 freeze-race shape."* Adding a header-level `Idempotency-Key` would be a redundant third layer without additional safety. The 202 (async) return further means the header-replay pattern (return identical response) does not cleanly apply — the response is an acceptance of the refund initiation, not a completed refund.

**This decision is binding for 66-03 and 66-04:** `refund_membership_online` and `refund_pt_package_online` are **excluded** from `CATEGORY_A_OPERATION_IDS`.
