<objective>
Restore `pt_packages.sessions_remaining` when an OWNER-initiated cancellation voids a PT booking, so a client never loses a prepaid PT session due to a gym-side cancellation (WR-06). Two call paths: `cancel_slot` booked-cascade and `create_time_off(force=True)` booked-cascade. Restore happens in the SAME atomic commit as the booking cancellation, only when a real consumed session exists to give back, and is recorded by a new `pt_session_credit_restored` audit event.

Purpose: Closes the pre-v1.9 WR-06 documented limitation. Product decision LOCKED 2026-05-26 (Option B — always restore on owner cancellation).
Output: A reusable cross-module credit-restore helper in schedule/service.py, a new locked audit event + payload, the limitation NOTE removed, and regression tests in both schedule integration test files.
</objective>

<critical_domain_finding>
**Read this before implementing — it determines correctness.**

`create_booking` does NOT decrement `sessions_remaining`; it only guards `sessions_remaining > 0`
(bookings/service.py:982). The decrement happens at CHECK-IN via `record_pt_session`
(pt_sessions/service.py:299 `atomic_decrement_pt_package`), which simultaneously flips the
linked booking `confirmed → completed` (BOOKING_STATUS_TRANSITIONS: completed is terminal).

Both owner-cancel cascades flip ONLY `confirmed` bookings (`WHERE slot_id=:sid AND status='confirmed'`).
A `confirmed` booking has, by definition, NOT consumed a session (consumption would have made it
`completed`, which the cascade's predicate excludes). Therefore a blind "+1 on every cascade" would
OVER-CREDIT — gifting a session that was never deducted. The locked constraint already resolves this:
"restore only when there is a real session to give back, mirroring how the decrement happened."

The session→booking link is `pt_sessions.booking_id` (nullable FK, models.py:103). A consumed,
not-yet-cancelled session for the booking is: a `pt_sessions` row WHERE `booking_id=:bid` AND
`cancelled_at IS NULL`. That row's existence is the sole arbiter of "a credit was consumed for this
booking." Restore = increment pt_packages by exactly the count of such live sessions (0 or 1 in
practice — one session per booking) AND mark those pt_sessions cancelled, mirroring `cancel_pt_session`
(pt_sessions/service.py:458-475 `mark_cancelled` + `atomic_increment_pt_package`).

This makes the restore idempotent and race-safe: once the pt_session is flipped to cancelled, a retry
finds no live session and no-ops. Task 0 (checkpoint) confirms this interpretation with the owner
before implementation, because under the current FSM the literal WR-06 scenario ("force-cancel a
confirmed booking that lost a prepaid session") can only manifest if a consumed session exists for a
confirmed booking — which the consumption-keyed approach handles correctly either way.
</critical_domain_finding>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| owner action → cross-module write | An owner-authenticated cancel triggers a write to `pt_packages`/`pt_sessions` rows owned by another module via raw SQL. |
| concurrent cancel / retry → balance mutation | Two overlapping force-cancels (or a retry) could each attempt to restore the same session. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-999.1-01 | Tampering | `_restore_pt_credit_for_cancelled_booking` increment | mitigate | Restore gated on a live pt_session (`booking_id=:bid AND cancelled_at IS NULL`) flipped to cancelled in the same UoW; ceiling predicate `sessions_remaining < session_count_snapshot` + CHECK prevents over-credit beyond purchased count. |
| T-999.1-02 | Repudiation | balance change without trace | mitigate | Every restore emits `pt_session_credit_restored` with before/after balance + booking_id, atomic with the mutation (INFRA-15 audit discipline). |
| T-999.1-03 | Elevation/abuse | free-session exploit via repeated cancel | mitigate | Idempotent restore: once the pt_session is cancelled, the `cancelled_at IS NULL` predicate excludes it → 0 rows → no second increment; verified by no-double-restore test. |
| T-999.1-04 | Denial of Service | partial write leaving inconsistent balance | accept | All mutations + audit share the single end-of-function `session.commit()` (SVC001); any raise rolls the whole UoW back — no partial state. |
</threat_model>
